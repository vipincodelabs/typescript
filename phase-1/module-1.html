▶ What is TypeScript Beginner
Simple Explanation
TypeScript is JavaScript with a built-in spell-checker for your logic. You label each variable with what kind of value it holds, and if anything ever breaks that contract, TypeScript warns you before you run the code.
Technical Explanation
TypeScript is a statically-typed superset of JavaScript developed and maintained by Microsoft. It extends JavaScript with optional type annotations that the TypeScript compiler (tsc) validates at compile time. Those annotations are then stripped away, producing standard JavaScript that runs in any environment that supports JS.

TypeScript was released publicly in 2012 after being built internally at Microsoft. It was designed to solve the problem of writing large-scale JavaScript applications — the kind where a single typo buried deep in a callback chain can crash production and produce a near-useless error message. Every valid JavaScript file is also a valid TypeScript file; you can migrate gradually without rewriting anything.

The Problem

JavaScript was designed in 1995 for adding small interactions to web pages. Today it powers applications with hundreds of thousands of lines, dozens of developers, and complex data flows. The language was never built for that scale. Without types, a function silently receives the wrong kind of value, produces garbage output, and the error only surfaces hours later in production — if you're lucky enough to notice it at all.

javascript (no types)
// This looks fine. It crashes silently at runtime.
function getFullName(user) {
  return user.firstName + ' ' + user.lastName;
}

getFullName({ name: 'Alice' });
// Returns: "undefined undefined"  ← no error thrown, just wrong output

getFullName(null);
// Throws: Cannot read properties of null  ← crashes at runtime

The Solution

typescript
// TypeScript catches both mistakes before you run anything.
interface User {
  firstName: string;
  lastName: string;
}

function getFullName(user: User): string {
  return user.firstName + ' ' + user.lastName;
}

getFullName({ name: 'Alice' });
// Error: Property 'firstName' is missing in type '{ name: string }'

getFullName(null);
// Error: Argument of type 'null' is not assignable to parameter of type 'User'

Both bugs are caught instantly in your editor — no running the code, no refreshing the browser, no searching through stack traces.

Use TypeScript When…

  • Building an app with more than a few hundred lines. The type system starts paying off quickly as complexity grows.
  • Working on a team. Types are machine-verified documentation — they tell your teammates exactly what a function expects and returns, without reading the implementation.
  • Building a public API or library. Consumers get autocomplete and error checking for free via the generated .d.ts declaration files.
  • Refactoring existing code. Renaming a function or changing its parameter type in TypeScript propagates errors everywhere it's used — nothing slips through silently.
  • Your project will live for more than a few months. TypeScript pays its setup cost back many times over as requirements change.

Skip TypeScript When…

  • Writing a one-off script. A 30-line Node.js script that runs once to rename files does not need a tsconfig.json. Use plain JS.
  • Rapid-prototyping with an unknown shape. When you genuinely don't know the data structure yet, fighting the type system adds friction. Start in JS with allowJs: true, add types once the shape stabilises.
  • Your team has zero TypeScript experience and a hard deadline. Migrating mid-project under pressure introduces more bugs than types prevent. Plan a proper migration with time to do it right.
  • The library you're wrapping has no type definitions. If @types/somelibrary doesn't exist and the library's API is large and complex, you can end up writing more type boilerplate than application code.

What the Compiler Actually Does

  1. Parsing: tsc reads your .ts files and parses them into an Abstract Syntax Tree (AST) — a tree representation of your code's structure.
  2. Type-binding: The compiler walks the AST and assigns a type to every identifier — every variable, parameter, and return value.
  3. Type-checking: It validates every operation against those types. Assigning a string to a number variable? Error. Calling a method that doesn't exist on the type? Error.
  4. Emit: If type-checking passes (or if noEmitOnError is false), tsc writes .js output files. All type annotations, interfaces, and type aliases are completely removed — the output is plain JavaScript.
  5. Nothing survives to runtime: Types are a development-time tool only. A running TypeScript program is indistinguishable from JavaScript.

The compiled output for a simple typed function looks exactly like what a skilled JavaScript developer would write by hand — TypeScript adds zero runtime overhead.

typescript input
function add(a: number, b: number): number {
  return a + b;
}
javascript output (after tsc)
function add(a, b) {
  return a + b;
}
// All type annotations stripped. Zero runtime difference.

Type Annotation Syntax

typescript
// Variable annotation: name: Type
let username: string = "Alice";
//  ^^^^^^^^  ^^^^^^   ^^^^^^^
//  variable  type     value (must match the type)

// Function parameter and return type annotations
function greet(name: string): string {
//              ^^^^  ^^^^^^   ^^^^^^
//              param type     return type (after the closing paren)
  return `Hello, ${name}!`;
}

// Type inference — you don't always need to write the type
let count = 0;
// TypeScript infers: count is number — no annotation needed

count = "hello";
// Error: Type 'string' is not assignable to type 'number'

// Object type annotation
let user: { name: string; age: number } = { name: "Bob", age: 30 };
//        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//        inline object type shape

The colon (:) is the annotation operator. It appears after a name to declare its type. Return types go after the closing parenthesis of the parameter list. TypeScript can infer most types from the right-hand side — you only need to annotate where inference isn't possible or where you want to be explicit.

Mistake 1 — Using any to silence TypeScript errors
Wrong
typescript
const data: any = fetchUserFromAPI();
// No error — but you've disabled TypeScript for this entire variable
console.log(data.nme); // typo of "name" — TypeScript can't catch it
Correct
typescript
interface User { name: string; email: string }
const data: User = fetchUserFromAPI();
console.log(data.nme); // Error: Property 'nme' does not exist on type 'User'

Using any completely opts that variable out of type checking. It's contagious — once one variable is any, anything derived from it is also any. Always define the expected shape.

Mistake 2 — Assuming types survive to runtime
Wrong
typescript
function process(value: string | number) {
  if (value instanceof String) { // WRONG — primitive 'string' ≠ String object
    return value.toUpperCase();
  }
}
Correct
typescript
function process(value: string | number): string {
  if (typeof value === "string") { // typeof works at runtime
    return value.toUpperCase();
  }
  return value.toFixed(2);
}

TypeScript types are erased before running. Use typeof for primitive checks at runtime, instanceof only for class instances.

Mistake 3 — Skipping strict: true in tsconfig

Without strict: true, TypeScript allows implicit any, doesn't check for null/undefined access, and misses a large class of real bugs. Always enable strict mode from the start — it's much harder to add later.

1. Enable strict: true from day one
Strict mode enables a bundle of compiler checks (strictNullChecks, noImplicitAny, etc.) that catch the most common categories of bugs. Adding it later to an existing project is painful.
2. Let TypeScript infer where it can
Writing const count = 0 is cleaner than const count: number = 0 — the type is obvious from the value. Save explicit annotations for function signatures and complex shapes where the type isn't self-evident.
3. Always annotate function signatures explicitly
Function parameter and return types are the API surface of your code. Explicit annotations here make intent clear, prevent accidental return type changes, and give better error messages to callers.
4. Never use any as a shortcut
Use unknown when the type is genuinely unknown (then narrow with typeof/instanceof), or take the time to define the correct type. any silently disables type-checking for anything it touches.
5. Install @types/* for every JS library you use
Without type definitions, TypeScript treats the whole library as any. Run npm i -D @types/node @types/express etc. to get typed APIs for your dependencies.
What is TypeScript, and how does it relate to JavaScript? Easy
TypeScript is a statically-typed superset of JavaScript developed by Microsoft. All valid JavaScript is also valid TypeScript. TypeScript adds optional type annotations that are checked at compile time, then stripped to produce plain JavaScript. The output runs anywhere JavaScript runs — browsers, Node.js, Deno — with zero runtime overhead from TypeScript itself.
What happens to TypeScript types at runtime? Easy
Types are completely erased by the TypeScript compiler before the code runs. At runtime, a TypeScript program is indistinguishable from the JavaScript a developer would have written by hand. This means you cannot use instanceof MyInterface at runtime — interfaces don't exist after compilation. For runtime type validation you need a separate library like Zod.
What is the difference between a TypeScript type error and a JavaScript runtime error? Medium
A TypeScript type error is a static analysis failure — the compiler finds it before you run any code. A JavaScript runtime error occurs while the program is actually executing, often far from where the real mistake was made. TypeScript's goal is to convert runtime errors into compile-time errors, catching them during development rather than in production where they affect users.
Why do large engineering teams choose TypeScript over JavaScript? Medium
Three main reasons: (1) Refactoring safety — renaming a function or changing its signature immediately surfaces every broken callsite as a compile error. (2) IDE productivity — autocomplete and inline error messages from TypeScript's language server dramatically speed up development. (3) Living documentation — type signatures describe what every function expects and returns, and unlike comments, they're enforced by the compiler so they can't go stale.
If TypeScript types are erased at runtime, how do you validate data from an external API? Hard
TypeScript only validates code you write statically — it cannot validate data arriving at runtime from a network request, database, or file. For runtime validation you use a library like Zod, which validates the shape of incoming data and returns a typed result. Zod's z.infer<typeof schema> pattern extracts a TypeScript type from your validation schema, keeping static types and runtime checks in sync from a single source of truth.

How TypeScript Improves Engineering Productivity

TypeScript's impact on team productivity comes from the Language Server Protocol (LSP). The TypeScript language server (tsserver) runs in the background in your editor. It reads your entire project's type graph and uses it to power:

  • Autocomplete: When you type user., the editor shows every property defined on that type — no guessing, no docs lookup
  • Go-to-definition: Click any identifier to jump to where it's defined, even across packages
  • Find all references: Instantly see everywhere a function or type is used — essential before refactoring
  • Rename symbol: Rename a function or type and every usage is updated atomically across the entire repo
  • Inline errors: Mistakes are underlined red in the editor milliseconds after you type them — before you save, compile, or run anything

These tools work because TypeScript knows the shape of every value at every point in the program. JavaScript editors can only guess based on usage patterns; TypeScript editors know.

Mistake 3 — Keeping strict: false to reduce initial error count

Non-strict TypeScript gives a false sense of safety. Teams enable strict mode only to discover hundreds of hidden nullability bugs. Start strict from day one — it's much less painful than adding it later.

1. Create a shared types/ folder for domain models

2. Migrate gradually with allowJs: true

3. Run tsc --noEmit in CI
Adding a type-check step to your CI pipeline prevents type errors from ever reaching production. It takes seconds to run and catches the entire class of compile-time bugs.
4. Use @ts-expect-error instead of @ts-ignore
@ts-expect-error fails the build if the error it suppresses no longer exists — this prevents dead suppressions from accumulating. @ts-ignore silently stays even when the underlying issue is fixed.
5. Document migration progress with a tsconfig.strict.json ratchet
Keep a strict tsconfig that includes only already-migrated files, and expand it incrementally. This lets you enforce strict checks on converted code while not blocking work on unconverted files.

▶TypeScript vs JavaScriptBeginner
Simple Explanation
JavaScript is the language your browser runs. TypeScript is JavaScript with extra rules written on top. You write TypeScript, the compiler checks your rules, then strips them away and gives you normal JavaScript. At runtime, they're identical.
Technical Explanation
TypeScript is a strict syntactic superset of JavaScript — every JS program is a valid TS program, but not vice versa. TypeScript adds: type annotations, interfaces, enums, access modifiers, generics, and a compile step. All of these are erased before runtime. The runtime behavior of TypeScript and JavaScript is identical for equivalent code.

The key conceptual difference is when errors are caught. JavaScript is dynamically typed — the engine discovers type mismatches at runtime, often in production. TypeScript is statically typed — the compiler discovers them at build time, on your machine, before anyone runs the code.

What JavaScript Lacks at Scale

JavaScript was designed to be forgiving — it silently coerces types, allows calling undefined values, and accepts anything. That flexibility is fine for small scripts but catastrophic in large systems where a silent bug can go undetected for weeks.

javascript — silent failure

What is the relationship between TypeScript and JavaScript? Easy
TypeScript is a strict superset of JavaScript — all valid JS is valid TS. TypeScript adds optional type annotations and a compile step. The compiler checks types, then strips them to produce plain JavaScript. At runtime the two are identical; TypeScript only exists at development time.
What are the main things TypeScript adds to JavaScript? Easy
TypeScript adds: type annotations, interfaces, type aliases, enums, generics, access modifiers (public/private/protected), and the non-null assertion operator. Of these, only enums generate runtime code (an object). Everything else is erased before the output JS is emitted.
Can TypeScript catch all JavaScript bugs? Medium
No. TypeScript catches type-level bugs at compile time — passing the wrong shape, accessing a non-existent property, calling something that might be null. It cannot catch logic bugs (wrong algorithm), runtime data errors (bad API response), or any behavior that only manifests at execution time. TypeScript is one layer of a multi-layer quality strategy that also includes unit tests, integration tests, and runtime validation.
Does TypeScript add any runtime overhead to JavaScript? Medium
No. TypeScript types are completely erased during compilation. The emitted JavaScript is identical to what a skilled developer would write by hand — no TypeScript runtime, no type-checking overhead, no extra library needed. The only overhead is the compile step itself, which happens at build time, not at runtime.
How does TypeScript's type system differ from Java's? Hard
TypeScript uses structural typing (also called duck typing) — if an object has all the properties a type requires, it satisfies that type, regardless of what class it was created from. Java uses nominal typing — a type is only compatible if it explicitly declares it implements a particular interface or extends a class. This means in TypeScript you can pass any object that "looks like" a User to a function expecting a User; in Java you'd need it to explicitly implement the User interface.

▶Static TypingIntermediate
Simple Explanation
Static typing means you declare what kind of value a variable holds before the program runs, and the system verifies every assignment and function call against that declaration. If anything doesn't match, the error is reported at compile time — not in production.
Technical Explanation
In a statically-typed system, the type of every expression is known at compile time. The type checker performs a formal proof that the program is type-correct before execution begins. TypeScript implements optional static typing — you can omit annotations and TypeScript will infer types from context, but every value still has a type known to the compiler.

The opposite of static typing is dynamic typing, which is what JavaScript uses. In a dynamic type system, types are associated with values at runtime, not with variables at write time. A variable x can hold a number on one line and a string on the next — the interpreter finds out what's there only when it executes.

The Dynamic Typing Problem

In a dynamically-typed language, the only way to know if a function is being called correctly is to run it. That's fine for small scripts. In a system with dozens of interconnected functions, a type mistake in one layer can surface as a completely unrelated error several layers deeper — and only in production, after real users encounter it.

javascript — runtime type error, far from the source
// Layer 1: fetches a user from DB, accidentally returns string ID instead of number

// Layer 2: passes it along
function getUserOrders(userId) { return db.find({ userId }); }

// Layer 3: the error explodes here with a cryptic message
function calculateDiscount(userId) {
  const count = getUserOrders(userId).length;
  return userId * 0.1 + count; // NaN — "42" * 0.1 is NaN in edge cases

When Static Typing Pays Off Most

  • Functions with non-obvious parameter shapes. If a function takes an object, annotate its shape — callers don't have to read the implementation to know what to pass.
  • Return types of public functions. Annotating return types creates a contract — if the implementation accidentally returns the wrong thing, the error is on the function author's side, not the caller.
  • Union types representing states. Use status: 'loading' | 'success' | 'error' instead of a plain string — TypeScript will enforce exhaustive handling of all states.
  • Data coming from one layer to another. Annotate every function that crosses a layer boundary (DB → service → route → response) — this is where type mismatches cause the most damage.
  • Shared utility functions. Any function called from more than one place should have explicit types so every caller benefits from the contract.

When Static Typing Adds Friction Without Value

  • Throwaway variables inside a function body. Let TypeScript infer — const doubled = nums.map(n => n * 2) doesn't need a type annotation.
  • Highly dynamic metaprogramming. When you're building a system that creates objects or functions at runtime based on user input, static types can become unwieldy. Use Record<string, unknown> and narrow at runtime.
  • Test data builders in unit tests. Internal test helpers that create partial objects don't need the full rigour of production types.
  • Quick scripts you'll run once. Writing a type for a five-line CSV processor you'll run once is overhead without benefit.

How TypeScript's Type Checker Works

  1. Type inference: For every value without an explicit annotation, TypeScript infers the type from context. const x = 5 gives x the type number. const arr = [1, 2, 3] gives arr the type number[].
  2. Type widening vs narrowing: TypeScript starts with a wide inferred type and narrows it based on control flow. After if (typeof x === 'string'), TypeScript knows x is string inside that block.
  3. Structural compatibility: When checking if a value is assignable to a type, TypeScript checks structure, not identity. An object { name: string; age: number } is assignable to Person if Person requires name and age — regardless of whether it was created from a Person class.
  4. Soundness vs practicality: TypeScript deliberately sacrifices some theoretical soundness (e.g., allowing covariant arrays) for practical usability. It aims to be useful, not mathematically perfect.

What is the difference between static and dynamic typing? Easy
In static typing, the type of every variable is known at compile time — before the code runs. The type checker validates correctness upfront. In dynamic typing (like JavaScript), types are associated with values at runtime — the interpreter discovers type mismatches only during execution. TypeScript gives JavaScript static typing while still compiling to JavaScript.
What is type inference in TypeScript? Easy
Type inference means TypeScript automatically determines the type of a value from context, without requiring an explicit annotation. If you write const x = 5, TypeScript infers x is number. If you write const arr = ["a", "b"], TypeScript infers string[]. You still get full type checking without writing the type yourself.
What is type narrowing? Medium
Type narrowing is when TypeScript refines a broader type to a more specific one based on control flow. After if (typeof value === 'string'), TypeScript knows value is string inside that block — even if its declared type was string | number. TypeScript tracks types through typeof, instanceof, truthiness checks, and custom type guards.
What is structural typing and how does TypeScript use it? Medium
Structural typing means type compatibility is determined by shape, not by name or declaration. If two types have the same properties, they are compatible — even if they were never declared to be related. TypeScript uses structural typing: a function expecting { name: string } accepts any object with at least a name: string property, regardless of its class. This is different from Java/C# where types must explicitly declare relationships.
What is the never type and how is it used for exhaustive checking? Hard
never is TypeScript's "impossible" type — a value of type never can never exist. It's used for exhaustive checking: assign a union type to a never variable in the default branch of a switch. If you handle all union members, TypeScript is satisfied. If you add a new member later and forget the switch, TypeScript reports an error because an unhandled value can't be assigned to never. This turns missing case bugs into compile errors.

▶Compilation ProcessIntermediate
Simple Explanation
TypeScript can't run directly in the browser or Node.js. It must first be translated into JavaScript. That translation is called compilation, and it's done by a tool called tsc — the TypeScript compiler. Compilation checks your types and produces clean JavaScript files.
Technical Explanation
The TypeScript compiler (tsc) performs two separate tasks: type-checking (static analysis of type correctness) and transpilation (transforming TypeScript syntax into a target JavaScript version). These are logically independent — tsc --noEmit type-checks without producing output, and transpileOnly mode (used by ts-jest, esbuild, swc) skips type-checking for faster builds.

In modern toolchains, TypeScript is rarely compiled directly by tsc in production. Bundlers like Vite, esbuild, and SWC handle the transpilation step (much faster, strip-only), while tsc --noEmit runs separately for type checking in CI. Understanding both modes helps you configure your build correctly.

Why a Compile Step Is Needed

JavaScript engines (V8, SpiderMonkey) only understand JavaScript — they can't parse TypeScript syntax like : string or interface User { ... }. TypeScript needs to be stripped of all type information before it can run. The compile step also gives you control over the JavaScript version you target: write modern TypeScript, output ES5 for older browsers.

Compilation Modes and When to Use Each

  • tsc (full compile): For libraries that ship JavaScript files. Generates .js + .d.ts declaration files. Use when publishing to npm.
  • tsc --noEmit (type-check only): In CI pipelines and editor integrations. Fast, pure validation — no output files. The safest way to confirm your code is type-correct before deploying.
  • tsc --watch: During development, recompiles on every file save. Useful for Node.js servers; most frontend devs use Vite/Webpack instead.
  • Bundler-handled transpilation (Vite, esbuild, SWC): These tools strip TypeScript types with no type-checking, purely for speed. Run tsc --noEmit separately to still catch errors.
  • ts-node / tsx: Run TypeScript files directly in Node.js without a manual compile step. Useful for scripts and development servers.

Don't Rely on tsc Alone When…

  • You need fast hot-reload in a large frontend project. tsc recompiles everything on change. Use Vite or esbuild for transpilation and run tsc --noEmit separately.
  • You're using a monorepo with many packages. tsc --build (project references) is necessary; plain tsc won't understand the dependency graph.
  • You need source maps for debugging in production. Make sure your tsconfig has sourceMap: true and your bundler preserves them — it's not automatic in all setups.

TypeScript Compilation Pipeline

  1. Scanner: Reads source characters and produces a stream of tokens (const, identifier, :, string, etc.)
  2. Parser: Consumes tokens and builds an Abstract Syntax Tree (AST) — a tree representing the structure of your code
  3. Binder: Walks the AST and creates a Symbol table — maps every identifier to its declaration and scope
  4. Type checker: Traverses the AST using the symbol table, assigns types to every node, and validates operations (most of the work happens here)
  5. Emitter: Walks the type-checked AST and writes .js output — type annotations are dropped, syntax is downleveled if needed, source maps are generated

Steps 1–4 are pure analysis (no side effects). Step 5 is optional — you can type-check without emitting with --noEmit. This is why "just type-check" mode is much cheaper than full compilation.

What does the TypeScript compiler do? Easy
The TypeScript compiler (tsc) does two things: it type-checks your code (verifying that all type annotations are consistent), and it transpiles TypeScript to JavaScript (removing type annotations and downleveling modern syntax to the target version). These steps are independent — --noEmit skips the transpilation and only type-checks.
What is tsc --noEmit used for? Easy
tsc --noEmit runs the full type-checking pipeline but produces no output files. It's used in CI pipelines and editor integrations to verify type correctness without writing anything to disk. It's the cheapest way to ensure your codebase has no type errors — faster than a full build and safe to run in any environment.
Why don't tools like Vite and esbuild catch TypeScript errors? Medium
Vite, esbuild, and SWC use "strip-only" transpilation — they remove TypeScript syntax (annotations, interfaces) purely by text transformation, with no semantic analysis. This is extremely fast but performs zero type checking. You must run tsc --noEmit as a separate step to catch type errors. The two jobs (fast bundling vs correct typing) are deliberately separated in modern toolchains.
What are .d.ts declaration files? Medium
Declaration files (.d.ts) contain only TypeScript type information — no executable code. They describe the API of a JavaScript module in terms of types so TypeScript projects can use the module with full type safety. When you install @types/express, you're installing declaration files for the Express library. When you compile a TypeScript library with declaration: true, tsc generates them automatically alongside the JavaScript output.
What is the difference between target and module in tsconfig? Hard
target controls which JavaScript syntax features tsc outputs — ES5 down-levels arrow functions, const, and template literals to ES5 equivalents; ES2022 keeps modern syntax intact. module controls how module imports/exports are compiled — CommonJS outputs require() (Node.js default), ESNext/NodeNext outputs import/export statements (ES modules). You can independently target old syntax with modern modules or vice versa.

▶Setting up tsconfig.jsonIntermediate
Simple Explanation
tsconfig.json is the settings file for your TypeScript project. It tells the compiler where to find your source files, what JavaScript version to output, and how strict to be when checking types. Every TypeScript project needs one.
Technical Explanation
tsconfig.json configures the TypeScript compiler's behavior for a project. It specifies compiler options (type-checking strictness, output target, module system, path aliases), the set of files to include or exclude, and can extend base configurations. When tsc runs, it walks up the directory tree from the current working directory to find the nearest tsconfig.json.

Running npx tsc --init generates a starter tsconfig.json with every option documented in comments. In practice, you only need 10–15 options for a typical project — the rest can be left at their defaults.

Why a Config File Is Needed

TypeScript has dozens of compiler options that affect how it checks types and what JavaScript it produces. Without a config file, you'd need to pass all of these as command-line flags every time you run tsc. tsconfig.json captures the project's settings in version control so every developer on the team compiles with identical settings.

Different projects have radically different needs: a React frontend targeting modern browsers uses different options than a Node.js API targeting an older runtime, which differs from a library that ships type declarations. The config file is how you express those requirements precisely.

bash
# Without tsconfig.json — you'd need all of this on every tsc call:
npx tsc src/**/*.ts --target ES2022 --strict --module NodeNext --outDir dist --sourceMap

# With tsconfig.json — all options captured in one file:
npx tsc

Key Options and When They Matter

  • strict: true — Always. Enables the full safety net: strictNullChecks, noImplicitAny, strictFunctionTypes, and more. The single most important option.
  • target — Set based on your runtime environment. ES2022 for modern Node.js or browsers; ES5 only if you're targeting ancient browsers.
  • module + moduleResolution — NodeNext for modern Node.js ESM, CommonJS for older Node.js, ESNext + Bundler for bundled frontend apps.
  • outDir / rootDir — Set these to separate source from compiled output cleanly.
  • paths — Configure import aliases like @/lib/utils → ./src/lib/utils so you avoid long relative paths.
  • lib — Controls which built-in types are available. DOM for browser APIs, ES2022 for modern JS globals. Don't include DOM in a pure Node.js project.

Options to Avoid or Be Careful With

  • Don't set strict: false just to reduce initial error count. You'll have a false sense of safety and a painful migration when you eventually enable it.
  • Don't set target: "ES3" or "ES5" unless you genuinely need IE support. It generates verbose, hard-to-read output and doesn't reflect modern JavaScript.
  • Don't use skipLibCheck: true as a permanent fix. It silences errors in node_modules declaration files — sometimes necessary temporarily, but investigate the underlying issue.
  • Don't rely on paths alone for import aliases in bundled apps. TypeScript resolves them for type-checking, but your bundler (Vite, Webpack) needs its own alias config too.

How tsconfig.json Is Resolved

  1. When you run tsc, it looks in the current directory for tsconfig.json. If not found, it walks up the directory tree until it finds one or reaches the filesystem root.
  2. The config can extend another config file — your project config adds or overrides settings from a base. This is how @tsconfig/node20, @tsconfig/strictest, etc. work.
  3. include and exclude use glob patterns. If neither is specified, TypeScript includes all .ts files in the project directory recursively.
  4. The strict flag is a shorthand for enabling: strictNullChecks, noImplicitAny, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, strictBuiltinIteratorReturn, noImplicitThis, and alwaysStrict.

tsconfig.json defines how the project is compiled. If it's in .gitignore, different developers compile with different settings — leading to bugs that appear on one machine but not another. Always commit it.

Wrong

Mistake 3 — Mismatching module and moduleResolution

In modern TypeScript, module and moduleResolution should be paired: NodeNext/NodeNext, ESNext/Bundler, or CommonJS/Node. Mixing them (e.g., module: ESNext + moduleResolution: Node) causes cryptic import errors that are hard to trace.

1. Always set strict: true — it's the most important option
It enables 8+ individual checks that catch the most common bugs. Start every project with it; never remove it.
2. Set rootDir and outDir explicitly
Prevents compiled files from appearing in your source directory and makes the project structure predictable for every developer on the team.
3. Use extends in monorepos to share a base config
A shared tsconfig.base.json ensures consistent strictness across all packages without copy-pasting the same options everywhere.
4. Keep include explicit — don't compile everything by accident
Without an include array, TypeScript includes all .ts files recursively, including test utilities, scripts, and temporary files you don't want in production builds.
5. Add noUnusedLocals and noImplicitReturns for cleaner code
These are not part of strict but they catch dead code and missing returns — both common sources of bugs. Add them once your codebase is clean enough to handle them.
What is tsconfig.json and why does a TypeScript project need one? Easy
tsconfig.json is the TypeScript compiler's configuration file. It specifies which files to compile, what JavaScript version to target, how strict the type-checking should be, and dozens of other options. Without it, you'd have to pass every option as a command-line flag. With it, the project's compilation settings are captured in version control and shared across the entire team.
What does strict: true enable? Easy
strict: true is shorthand for enabling a bundle of individual checks: strictNullChecks (prevents null/undefined access), noImplicitAny (errors on parameters without explicit types), strictFunctionTypes, strictPropertyInitialization, noImplicitThis, and others. It's the single most important option — without it, TypeScript misses the most common bugs.
What is the difference between include, exclude, and files in tsconfig? Medium
include specifies glob patterns for files to compile. exclude specifies patterns to skip (defaults to node_modules, outDir). files lists individual files explicitly. If none are specified, TypeScript includes all .ts files recursively. In practice, include: ["src/**/*"] is the most common pattern — it compiles everything in src/ and nothing outside it.
How does extends work in tsconfig.json? Medium
extends lets one tsconfig inherit settings from another. The child config's options override the parent's. This is heavily used in monorepos — a tsconfig.base.json at the root defines shared settings (strict, target, esModuleInterop), and each package's tsconfig extends it and adds package-specific settings (outDir, module, jsx). Community packages like @tsconfig/node20 provide opinionated base configs you can extend.
What's the difference between target ES2015 and ES2022 in practical terms? Hard
target controls which JavaScript features tsc down-levels in the output. With ES2015, TypeScript transforms arrow functions, const/let, template literals, and classes into ES5 equivalents. With ES2022, TypeScript assumes the runtime supports modern features natively — arrow functions, optional chaining, nullish coalescing, and class fields are emitted as-is without transformation. This produces cleaner, smaller output and runs faster. Use ES2022 or higher for modern Node.js (18+) and evergreen browsers.
