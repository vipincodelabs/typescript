Function Types Beginner

Simple Explanation

A function type tells TypeScript exactly what kinds of values a function accepts and what it gives back. Think of it like a job contract — it specifies what inputs are required and what output is promised.

Technical Explanation

A function type in TypeScript is a type annotation that describes the signature of a function — its parameter types and return type. TypeScript uses structural typing to verify that any function assigned to a typed variable matches the expected shape. This is a purely compile-time construct; all annotations are erased in the JavaScript output.

The Problem Without Function Types

In JavaScript, you can pass any function anywhere. If you write a utility that expects a comparator (a, b) => number, nothing stops you from accidentally passing (name) => name.toUpperCase(). The bug only surfaces at runtime — often in production.

javascript
// JavaScript — bug at runtime, no warning
function sortUsers(arr, compareFn) {
  return arr.sort(compareFn);
}
sortUsers([3,1,2], (a) => a.name); // wrong! no error until runtime

The Fix With Function Types

typescript
type Comparator = (a: number, b: number) => number;

function sortNums(arr: number[], compareFn: Comparator): number[] {
  return arr.sort(compareFn);
}

// Error: Argument of type '(a: number) => string' is not assignable
// to parameter of type 'Comparator'
sortNums([3,1,2], (a) => a.toString());

Use Function Types When…

  • Passing callbacks to higher-order functions — ensures the callback has the right signature before it runs
  • Defining event handlers in React — enforce correct event types on onClick, onChange, etc.
  • Building strategy-pattern APIs — sorting, filtering, validation functions passed as config
  • Typing middleware in Express — ensure every middleware matches (req, res, next) => void
  • Documenting function variables — make the expected signature clear to readers and the IDE

Avoid Function Types When…

  • TypeScript can infer the type — adding const fn: (x: number) => number = (x) => x * 2 is redundant; inference handles it
  • You need method overloads in an interface — use interface method syntax instead, which supports overloads
  • For single-use inline callbacks — annotate inline rather than creating a type alias for a one-time callback
  • Tempted to use Function — the bare Function type loses all type information; always specify the signature

What the Compiler Does

TypeScript uses structural typing for functions. When you assign a function to a typed variable, the compiler checks:

  1. Parameter types: each parameter in the implementation must be assignable to the corresponding parameter in the declared type
  2. Return type: the actual return type must be assignable to the declared return type
  3. Parameter count: a function with fewer parameters than the type declares is allowed (because JavaScript ignores extra arguments)

Under --strictFunctionTypes, parameters are checked contravariantly — this prevents unsafe assignments where a handler expecting a subtype receives a supertype. Method signatures in interfaces remain bivariant for backwards compatibility.

All function types are erased at compile time. The output JavaScript has no trace of them.

typescript
// Type alias syntax for a function type
type MathOperation = (a: number, b: number) => number;
//   ^^^^^^^^^^^^^                                      type alias name
//                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^       parameter list with types
//                                             ^^^^^^   return type after =>

// Using the alias — TypeScript infers parameter types from MathOperation
const add: MathOperation = (a, b) => a + b;
const mul: MathOperation = (a, b) => a * b;

// Inline function type (without a separate alias)
const greet: (name: string) => string = (name) => `Hello, ${name}`;

// Generic function type — reusable across types
type Predicate<T> = (item: T) => boolean;
type Transformer<T, U> = (item: T) => U;

// Function type as a parameter
function filter<T>(arr: T[], predicate: Predicate<T>): T[] {
  return arr.filter(predicate);
}

The arrow (=>) in a function type always means "returns" — it is different from the arrow in an arrow function expression, even though they look the same.

2. Colon instead of arrow in type alias
typescript
// WRONG — colon is not valid in a type alias signature
type Op = (a: number, b: number): number; // Syntax Error

// CORRECT — arrow => separates params from return type
type Op = (a: number, b: number) => number;
3. Not realising TypeScript allows fewer parameters
typescript
type Handler = (x: number, y: number) => void;

// VALID — fewer params are OK (JavaScript ignores extra args)
const fn: Handler = (x) => console.log(x);

// INVALID — extra params are NOT OK
const fn2: Handler = (x, y, z) => {}; // Error: too many parameters
  1. Name aliases descriptively — Predicate, Comparator, RequestHandler communicate intent far better than Fn or Callback
  2. Never use the bare Function type — it provides zero safety; always specify the full signature
  3. Use void for callbacks whose return value is discarded — it prevents accidental reliance on the return value
  4. Make function types generic when possible — Predicate<T> is reusable across string, number, and custom types
  5. Prefer type aliases over inline types for reuse — if the same signature appears in 3+ places, create a named alias
  6. Keep aliases close to where they're used — co-locate them in the same module unless they're shared across the whole codebase
  7. Document complex signatures with JSDoc — a one-line comment on the type declaration saves future maintainers from decoding the parameters
Q: What is a function type and how do you declare one? Easy
A function type describes what a function accepts and returns. You declare it with type Name = (param: Type) => ReturnType. This lets you type variables, parameters, and return values that hold functions, and TypeScript will verify any assigned function matches the signature.
Q: What is the difference between void and undefined as return types? Easy
void means "I don't care about the return value" — useful for event handlers and callbacks where the return is ignored. undefined means the function must explicitly return undefined. Use void for callbacks passed to addEventListener or setTimeout; use undefined when the absence of a value is part of the API contract.
Q: Why does TypeScript allow a function with fewer parameters to satisfy a type that has more? Medium
This is "parameter count compatibility." It mirrors how JavaScript works — extra arguments are silently ignored. Array methods pass (item, index, array) to callbacks, but most callbacks only use item. If TypeScript required exact parameter count, array.map(String) would be an error. Fewer params ✓, more params ✗.
Q: What is the difference between a method signature and a function type property in an interface? Medium
Method: { greet(name: string): string }. Function property: { greet: (name: string) => string }. They're nearly equivalent, but method signatures support overloads and behave bivariantly under --strictFunctionTypes. Function type properties are checked contravariantly. Prefer function type properties for strict safety.
Q: What is "contravariance" and how does --strictFunctionTypes relate to it? Hard
Contravariance means: if B extends A, then (b: B) => void is NOT assignable to (a: A) => void. A handler for a specific subtype can't safely receive a more general supertype. --strictFunctionTypes enables this correct check for function type aliases. Method signatures bypass it (remain bivariant) for practical compatibility with common patterns like Array.push.

Optional Parameters Beginner

Simple Explanation

An optional parameter is one that a caller doesn't have to provide. It's like a restaurant order with optional add-ons — the burger arrives without toppings unless you specifically ask for them.

Technical Explanation

You mark a parameter optional by appending ? after its name. Internally, TypeScript treats its type as T | undefined — it receives the value if provided, or undefined if not. Optional parameters must come after all required parameters in the signature.

The JavaScript Problem

In JavaScript you can call any function with fewer arguments than declared. The missing ones silently become undefined. There is no way to tell from the signature whether an argument is intentionally optional or was just forgotten — and accessing properties on undefined crashes at runtime.

javascript
// JavaScript — intent unclear, no safety
function greet(name, title) {
  return `Hello ${title} ${name.toUpperCase()}`;
}
greet("Smith");  // "Hello undefined SMITH" — silent bug
greet();        // TypeError: Cannot read properties of undefined

The TypeScript Fix

typescript
function greet(name: string, title?: string): string {
  return title ? `Hello ${title} ${name}` : `Hello ${name}`;
  //     ^^^^^ TypeScript forces you to handle the undefined case
}
greet("Smith");           // "Hello Smith" — safe
greet("Smith", "Dr.");    // "Hello Dr. Smith"
greet();                  // Error: Expected 1-2 arguments, but got 0
  • Parameters with natural absence — a title prefix, a middleName, or a reason for an action that sometimes exists and sometimes doesn't
  • Configuration toggles — verbose?: boolean on a logging utility that adds extra output only when requested
  • Callback parameters on components — onClick?: () => void in React — the component works with or without a click handler
  • Legacy JS migration — mark arguments that were already optional in JS so callers don't need to change
  • Pagination options — cursor?: string is absent on the first call and present for subsequent pages
  • When a sensible default exists — use a default parameter (limit = 10) instead; it's cleaner and removes the undefined check inside the function body
  • First parameter optional, later ones required — TypeScript forbids this. Restructure to an options object instead
  • Functions with 4+ optional params — more than a couple optional params is a sign you need an options object: fn(options?: Options)
  • Signalling "not yet implemented" — optional params are not a design pattern for conditional features; use explicit union types or function overloads

TypeScript desugars param?: Type into param: Type | undefined internally. The ? is syntactic sugar — there is no runtime difference. In JavaScript, calling a function with fewer arguments simply leaves those parameters as undefined.

What TypeScript adds is forced acknowledgement: inside the function body, the type is T | undefined, so you must narrow it before accessing properties. The compiler refuses to let you call param.toUpperCase() without first checking that param is defined.

Q: What does ? after a parameter name mean in TypeScript? Easy
It marks the parameter as optional — callers may omit it. The parameter's type becomes T | undefined inside the function. TypeScript forces you to handle the undefined case before accessing properties on the parameter.
Q: Can optional parameters come before required parameters? Easy
No. Required parameters must come before optional ones. Placing an optional before a required parameter causes a compile error: "A required parameter cannot follow an optional parameter." Restructure to put all optional params at the end, or use an options object.
Q: What is the difference between param?: string and param: string | undefined? Medium
Both produce the same internal type (string | undefined), but they differ in call semantics. With ?, callers can simply omit the argument. With string | undefined, callers must explicitly pass undefined — they cannot skip the argument. Prefer ? for truly optional arguments.
Q: How do you safely access the value of an optional string parameter? Medium
Three safe patterns: optional chaining param?.toUpperCase(), nullish coalescing param ?? 'default', or an explicit guard if (param !== undefined) { ... }. Avoid the non-null assertion param! unless you have proven the value cannot be undefined.
Q: How do optional parameters interact with function overloads? Hard
If a function behaves fundamentally differently based on whether a param is present, overloads are clearer: function fn(x: string): string; function fn(): number;. For simple "here's a default" cases, ? is sufficient. The implementation signature must be compatible with all declared overloads, so it often needs param?: string to cover both cases.

Default Parameters Beginner

Simple Explanation

A default parameter is a backup value that the function uses when the caller doesn't provide one. It's like a form with pre-filled fields — you can change them, but if you leave them blank, something sensible is used.

Technical Explanation

TypeScript uses the same ES6 default parameter syntax (param: Type = defaultValue) as JavaScript, but adds compile-time verification that the default value's type matches the declared type. Inside the function body, the parameter's type is T, never T | undefined, because TypeScript knows the default covers the absence case.

The Pre-ES6 Problem

Before default parameters, JavaScript developers wrote var x = arg || 'default'. This pattern is broken — it replaces any falsy value (including 0, false, "") with the default, even when those are legitimate inputs.

javascript
// BUG: || replaces 0 and false with default
function setPage(page) {
  page = page || 1; // page=0 becomes 1 — wrong!
}
setPage(0); // silently goes to page 1 instead of 0

The TypeScript Fix

typescript
// Default params only trigger for undefined, never for 0/false/""
function setPage(page: number = 1): void {
  console.log(page);
}
setPage(0);         // 0  — correct, default NOT triggered
setPage();          // 1  — default triggered (undefined)
setPage(undefined); // 1  — default triggered
  • Pagination params — page = 1, limit = 10 are universally sensible defaults
  • Timeout values — timeoutMs = 3000 prevents every caller from having to specify a timeout
  • Sort order — order: 'asc' | 'desc' = 'asc' when ascending is the natural default
  • Eliminating null checks in function bodies — instead of const l = limit ?? 10, make limit = 10 a default
  • Refactoring old || 'default' patterns to correctly handle falsy legitimate values
  • Mutable objects or arrays as defaults — the same reference is shared across calls; use a factory function inside the body instead
  • When absence should trigger different behaviour — use optional params or overloads when undefined means "do something different," not just "use a fallback"
  • Truly required parameters — if missing the argument should be an error, don't add a default just to silence TypeScript
  • Complex expressions as defaults — defaults are eagerly evaluated once at call time in JavaScript; if you need lazy evaluation, compute the default inside the body

At runtime, JavaScript replaces an argument with the default value if and only if the argument is undefined. TypeScript's job is to:

  1. Verify the default value's type is assignable to the declared parameter type
  2. Make the parameter implicitly optional from the caller's perspective (callers can omit it)
  3. Keep the parameter's type as T (not T | undefined) inside the function body — TypeScript knows the default covers the undefined case

Q: What is the key difference between optional (?) and default (= value) parameters? Easy
An optional parameter's type is T | undefined inside the function — you must check for undefined. A default parameter's type is just T — inside the function it is always defined because the default covers the absence case. Use defaults when you have a sensible fallback; use optional when absence should trigger different logic.
Q: Does a default parameter make calling with no argument valid? Easy
Yes. A parameter with a default becomes optional from the caller's perspective — the argument may be omitted. TypeScript automatically infers it as optional. This is different from a parameter typed as T | undefined without a default, where the caller must explicitly pass undefined.
Q: What is the danger of using an object or array literal as a default parameter value? Medium
In TypeScript (and JavaScript), default parameter values are evaluated once per call, but if you mutate the array or object received from the default, subsequent calls share the same mutated reference in some implementations. The safe pattern is to never mutate parameters — always create new values. Use return [...list, newItem] instead of list.push(newItem); return list.
Q: What happens when you pass null to a parameter that has a default value? Medium
The default does NOT apply. Default parameters only trigger for undefined (or an omitted argument). Passing null is an explicit value — the function receives null, not the default. If you need to treat null as "use the default," handle it explicitly: const val = param ?? defaultValue inside the body.

Rest Parameters Intermediate

Simple Explanation

Rest parameters let a function accept any number of arguments and bundle them into an array. Think of it like a "collect everything else" bucket at the end of the parameter list — whatever extra values come in get scooped up there.

Technical Explanation

A rest parameter is declared with ... before the parameter name and a typed array annotation (...args: T[]). It collects all remaining arguments passed to the function into a real, typed array. TypeScript enforces the element type, so every item in the collected array is known to be of type T. The rest parameter must be last and there can only be one per function.

The Problem: arguments

Before rest params, JavaScript used the arguments object — a weird array-like object that isn't a real array, has no type info, doesn't work in arrow functions, and requires Array.from(arguments) to use any array method.

javascript
// Old JavaScript — arguments is an array-like, not a real array
function sum() {
  return Array.from(arguments).reduce((a, b) => a + b, 0);
}

// Arrow functions don't have 'arguments' — this captures outer scope
const sumArrow = () => Array.from(arguments); // WRONG

The Fix: Rest Parameters

typescript
// TypeScript rest params — real typed array, works in arrows
function sum(...nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0); // nums is number[], has all array methods
}

const sumArrow = (...nums: number[]): number =>
  nums.reduce((a, b) => a + b, 0); // works perfectly in arrow functions

sum(1, 2, 3, 4); // 10
  • Variadic utility functions — sum, max, merge, concat where the count of inputs isn't fixed
  • Forwarding arguments to another function — wrapper functions that collect args and spread them forward
  • Logging functions — log(level, ...messages) where messages is a flexible list
  • Event emission — emit(eventName, ...args) where arguments depend on the event type
  • Tagged template literals — the standard signature uses rest params: (strings: TemplateStringsArray, ...values: unknown[])
  • When you know the exact argument count — use explicit named parameters; they're clearer and give better IntelliSense
  • When arguments have different types — rest params give you T[], so all elements must be the same type. Use overloads for heterogeneous args
  • As a lazy substitute for an explicit array param — fn([1, 2, 3]) is often clearer than fn(1, 2, 3) when you already have an array
  • Mixing with arguments — don't use both in the same function; they don't mix well and rest params fully replace arguments

At runtime, JavaScript rest parameters are implemented as Array.from(arguments).slice(n) where n is the number of named parameters before the rest param. TypeScript statically types the resulting array's element type.

TypeScript enforcements:

  1. Only one rest parameter per function
  2. Must be the last parameter in the list
  3. Type must be an array type (T[] or Array<T>) or a tuple type

Tuple rest types ([T, ...T[]]) are a TypeScript-specific extension that lets you require at least one argument while still accepting more — the first element has type T and the remaining elements are T[].

Q: What is a rest parameter and how does it differ from the arguments object? Easy
A rest parameter (...args: T[]) collects remaining function arguments into a real, typed array. Unlike arguments, it supports all Array methods, is properly typed, and works inside arrow functions. arguments is a legacy feature that should be avoided in TypeScript.
Q: Can you have multiple rest parameters in one function? Easy
No. Only one rest parameter is allowed per function, and it must be the last parameter. TypeScript and JavaScript both enforce this at parse time.
Q: How do you require at least one argument with rest params? Medium
Use a tuple rest type: (...args: [T, ...T[]]). The first element is required and typed T; the rest are optional Ts. TypeScript will error if the function is called with no arguments.
Q: How do you forward rest parameters to another function in a type-safe way? Medium
Use Parameters<typeof originalFn> to capture the parameter types as a tuple, then spread: function wrapper(...args: Parameters<typeof original>) { return original(...args); }. This is fully typed and forward-compatible — if original's signature changes, wrapper stays in sync.
Q: Explain the difference between ...args: string[] and ...args: [string, ...number[]]. Hard
string[] means all arguments must be strings. [string, ...number[]] is a heterogeneous tuple rest type: the first argument must be a string, the rest must be numbers. This enables calls like fn('label', 1, 2, 3). TypeScript uses a similar pattern for console.log: (message?: any, ...params: any[]).

Return Types Intermediate

Simple Explanation

A return type tells TypeScript what kind of value a function will hand back. It's like a label on a machine that says "this machine outputs oranges" — TypeScript makes sure you don't accidentally output apples, and callers know exactly what they're going to receive.

Technical Explanation

Return types are type annotations placed after the function's parameter list, following a colon (: Type). TypeScript performs control flow analysis on the function body, verifying that every possible return statement returns a value assignable to the declared type. TypeScript can also infer return types automatically, but explicit annotations create a documented contract and act as a safety net against accidental changes.

The Problem: Silent Type Drift

Without explicit return types, TypeScript infers the return type from the function body. This works well initially, but as the function evolves, a new branch might accidentally return undefined instead of the expected type. The callers silently receive a different type without any warning.

typescript
// Without return type — drift is silent
function getUser(id: number) {
  if (id > 0) {
    return { name: 'Alice', id };
  }
  // Missing return — TypeScript infers: { name: string; id: number } | undefined
  // Callers now get undefined silently — no warning!
}

// With explicit return type — caught immediately
function getUser(id: number): { name: string; id: number } {
  if (id > 0) {
    return { name: 'Alice', id };
  }
  // Error: Function lacks ending return statement and return type
  // does not include 'undefined'
}
  • Public API functions and exported utilities — callers rely on the contract; changing the type should be a deliberate breaking change
  • Async functions — document the resolved type explicitly: async function fn(): Promise<User>
  • Complex functions with multiple branches — explicit types verify all paths return the correct shape
  • Team settings — prevents unintentional return type changes from slipping past code review
  • When inference is too wide — TypeScript might infer string | undefined when you know it's always string
  • Trivial one-liners where inference is obvious — const double = (n: number) => n * 2 doesn't need : number at the end
  • Private internal helpers — let inference do the work; explicit annotations add noise
  • Simple arrow callbacks in array methods — users.map(u => u.id) doesn't benefit from annotating : number
  • Never use any as a return type — this defeats type safety entirely; investigate the root cause instead

TypeScript performs control flow analysis on the function body. It tracks every execution path and verifies each return statement returns a value assignable to the declared return type.

Special return types and what the compiler checks:

  • void — allows any return statement or no return at all; callers should not use the value
  • never — verifies the function never returns normally (always throws or infinite loops); enables exhaustiveness checking in switch statements
  • Promise<T> — enforces that async functions have the correct resolved type; TypeScript auto-wraps any returned value in a Promise
  • Union returns — all branches must return a value in the union; TypeScript errors if any path is missing

All type annotations are erased in the JavaScript output — return types are purely a compile-time construct.

Q: What is the difference between void and never return types? Easy
void means the function returns without a meaningful value — it may return undefined, but callers shouldn't use the value. never means the function never completes normally — it always throws or has an infinite loop. A void function returns; a never function does not.
Q: When should you use Promise<void> versus Promise<undefined>? Medium
Promise<void> signals that the async function performs a side effect and the resolved value should be ignored. Q: How does TypeScript use never for exhaustiveness checking? Medium
When you declare a function function assertNever(v: never): never and call it in the default branch of a switch on a discriminated union, TypeScript verifies that all union members are handled. If you add a new union member without handling it, TypeScript errors: "type 'NewMember' is not assignable to type 'never'."
Q: Can a function's return type be conditional based on the input type? Show an example. Hard

With generic conditionals: function wrap<T>(v: T): T extends string ? number : string. The implementation signature must cover all overload cases. Overloads are simpler for a small fixed set; conditional types are for complex generic scenarios.
