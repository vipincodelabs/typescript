Object Types Beginner ▶

Simple Explanation

An object type tells TypeScript what properties an object must have and what type each value should be. Think of it as a blueprint: you declare "this object needs a name string, an age number, and an email string" — and TypeScript enforces that blueprint everywhere the type is used.

Technical Explanation

Object types are anonymous structural type annotations written as { key: Type; key2: Type2 }. TypeScript uses structural typing (also called duck typing): any object that has at least the declared properties with compatible value types satisfies the annotation — regardless of how it was created or what it is named. The type annotation is erased at compile time; it exists only during static analysis.

The Problem It Solves

In plain JavaScript, accessing a property that doesn't exist returns undefined silently. A typo like user.nme instead of user.name produces a bug at runtime that can be incredibly hard to track down in a large codebase.

javascript (bug)
// JavaScript — no error, silent bug at runtime
function greet(user) {
  return "Hello, " + user.nme; // typo! nme instead of name
}
greet({ name: "Alice", age: 30 });
// Returns: "Hello, undefined" — no error thrown, hard to debug
typescript (fixed)
// TypeScript — caught at compile time, before the code runs
function greet(user: { name: string; age: number }): string {
  return "Hello, " + user.nme;
  // Error: Property 'nme' does not exist on type '{ name: string; age: number }'
  // Did you mean 'name'?
}

TypeScript also catches passing objects that are missing required properties, or passing the wrong type for a property — all before the code ever runs in a browser or on a server.

When Object Types Are The Right Tool

  • Function parameters that receive structured data — type every function parameter that expects an object with specific properties.
  • One-off object shapes used in a single place — if a type is only used once, inline it; there's no need to extract it.
  • API response typing (local) — when you fetch data and immediately destructure it in the same function, an inline object type is clean.
  • Configuration options objects — functions that accept option bags benefit from object type annotations to communicate what's accepted.
  • Return type annotations — document what shape a function returns, especially when the shape is small and self-contained.

When NOT to Use Inline Object Types

  • When the same type appears in more than one place — extract it to a type alias or interface. Duplicating inline object types creates a maintenance nightmare when the shape needs to change.
  • When you need to extend or inherit from the type — inline object types cannot be extends-ed. Use interfaces or extract to a named alias first.
  • When the structure is completely dynamic — use Record<string, unknown> or an index signature instead of a fixed-shape object type.
  • When nesting gets deep — deeply nested inline types like { user: { address: { city: string } } } are unreadable. Give each nested shape its own name.

What TypeScript Actually Does

When you write const user: { name: string; age: number } = { ... }, TypeScript:

  1. Records the object type { name: string; age: number } as the declared type of user.
  2. At each assignment, checks the right-hand side has a name property of type string and an age property of type number.
  3. At each property access (user.x), verifies x is in the declared shape. If not, it reports an error.
  4. Applies an excess property check to fresh object literals — if you write extra properties directly in the literal, TypeScript reports them even though structural typing would normally allow extra properties.
  5. Compiles to plain JavaScript with all type annotations stripped — no runtime cost.

The output JavaScript for const user: { name: string } = { name: "Alice" } is just const user = { name: "Alice" }.

typescript
// ── Variable with inline object type ──────────────────────────────────
const point: { x: number; y: number } = { x: 10, y: 20 };
//           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//           inline object type annotation
//           properties are separated by semicolons (commas also work)

// ── Function parameter typed as object ────────────────────────────────
function printPoint(coord: { x: number; y: number }): void {
//                          ^^^^^^^^^^^^^^^^^^^^^^^^
//                          parameter must match this shape
  console.log(`${coord.x}, ${coord.y}`);
}

// ── Return type annotation ─────────────────────────────────────────────
function createUser(name: string): { id: number; name: string } {
//                               ^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                               return type: the function must return this shape
  return { id: 1, name };
}

// ── Nested object type ────────────────────────────────────────────────
const config: { server: { host: string; port: number } } = {
  server: { host: "localhost", port: 3000 }
};
// Tip: for nested types, extract to named type aliases for readability

Semicolons (;) are the idiomatic separator between properties in TypeScript type annotations. Commas work too but are less common in types (they're more common in plain JavaScript objects).

typescript
// A typed user record system

const user: { id: number; name: string; email: string } = {
  id: 1,
  name: "Alice Johnson",
  email: "alice@example.com",
};

function formatUser(u: { id: number; name: string; email: string }): string {
  return `[${u.id}] ${u.name} <${u.email}>`;
}

console.log(formatUser(user));
// Output: [1] Alice Johnson <alice@example.com>

const partial = { id: 2, name: "Bob" }; // missing 'email'

// Error: Argument of type '{ id: number; name: string; }'
// is not assignable to parameter of type '{ id: number; name: string; email: string; }'
// Property 'email' is missing in type '{ id: number; name: string; }'

// Simulating a DB lookup typed as an inline object type
function getUserById(
  id: number
): { id: number; username: string; role: string } | null {
  const rows = [{ id: 1, username: "admin", role: "admin" }];
  return rows.find(row => row.id === id) ?? null;
}

  console.log(result.username); // OK: TypeScript knows shape after null check
  console.log(result.role);     // OK

  • API request body validation — Type Express handler parameters as inline object types matching the expected JSON body shape. Saves you from accessing fields that don't exist.
  • Database row modeling — Before migrating to Prisma or Drizzle, type raw query results as object types matching table columns to get autocomplete and shape safety.
  • Configuration objects — Libraries like Vite, Jest, and ESLint accept configuration objects; TypeScript types their parameters as inline object types so you can't pass unknown keys.
  • Event handler payloads — Custom event systems pass data objects to handlers; inline object types communicate exactly what each event carries.
  • Prototype typing — When quickly prototyping a component or function, inline object types are faster to write than creating a full interface file.

❌ Mistake 2 — Surprised by excess property checks on literals
typescript
function connect(opts: { host: string; port: number }) { /* ... */ }

// OK: variable with extra property passes (structural typing)
const config = { host: "localhost", port: 3000, debug: true };
connect(config); // ✓ No error — extra properties allowed via variable

// ERROR: fresh object literal with extra property fails (excess property check)

// is not assignable to parameter of type '{ host: string; port: number; }'
// Object literal may only specify known properties

Excess property checks only apply to fresh object literals. When you pass a variable, TypeScript uses structural typing and allows extra properties. This is intentional — literals are often where accidental typos live.

❌ Mistake 3 — Deeply nesting inline types without extraction
typescript — BAD
function processOrder(order: {
  id: number;
  customer: { name: string; address: { street: string; city: string } };
  items: { productId: number; qty: number }[];

// Unreadable, unreusable, hard to maintain

1. Use semicolons to separate properties in type annotations

Semicolons ({ name: string; age: number }) are idiomatic in TypeScript object types. Commas work too but look more like JavaScript object literals and can confuse readers.

2. Extract reused shapes to type aliases or interfaces

If an inline object type appears in more than one place, give it a name. A single source of truth makes refactoring safe — change the type in one place and everything updates.

3. Prefer interfaces for types you plan to extend

Interfaces support extends and declaration merging; inline object types and type aliases do not. If a type will ever need to be extended by other types, start with an interface.

4. Nest inline types at most one level deep

If a property's value is an object with multiple properties, give that nested shape its own named type. Deep nesting in a single type annotation is a readability problem.

5. Avoid using empty object type {}

The empty type {} does not mean "an empty object" — it means "any non-null, non-undefined value." This is almost never what you want. Use Record<string, never> for a truly empty object.

6. Use explicit, descriptive property names

Write { firstName: string; lastName: string } over { fn: string; ln: string }. TypeScript error messages include property names — descriptive names make errors immediately understandable.

Q: What is structural typing in TypeScript? Easy

Structural typing means TypeScript checks compatibility based on the shape of a type — its property names and value types — rather than the type's declared name. If object A has at least the properties declared in type T with compatible value types, A satisfies T, even if A was never explicitly declared as T. This is sometimes called "duck typing" — if it walks like a duck and quacks like a duck, TypeScript treats it as a duck. This contrasts with nominal typing (like Java or C#) where types must explicitly declare their relationships through implements or inheritance.

Q: Why does TypeScript allow passing a variable with extra properties but reject an object literal with extra properties? Medium

This is the excess property check — TypeScript applies it only to fresh object literals assigned to a typed variable or passed directly as a typed argument. When you first assign to a variable and then pass that variable, the check isn't applied because the variable could legitimately be used in other places that expect those extra properties. Object literals are treated as a "fresh" suspicious source where accidental typos are most likely to appear, so the stricter check helps catch mistakes like { diabled: true } instead of { disabled: true }.

Q: What is the difference between an object type and an interface? Medium

Both describe the shape of objects and are mostly interchangeable for basic use cases. Key differences: (1) Interfaces support declaration merging — you can reopen an interface in multiple files and TypeScript merges the definitions. Type aliases cannot be reopened. (2) Interfaces have better error messages in some cases. (3) Type aliases can describe any type — unions, intersections, primitives, function signatures — while interfaces can only describe object shapes. Most TypeScript style guides prefer interfaces for object shapes you plan to extend and type aliases for unions, intersections, and everything else.

Q: What does the empty object type {} mean in TypeScript? Hard

Counterintuitively, {} does NOT mean an empty object. It means "any value that is not null or undefined." This is because TypeScript's structural typing considers any value with at least zero properties to satisfy {}, and every non-null value in JavaScript has at least zero properties. This catches developers off guard when they use {} to mean "an object with no properties" — the actual way to express that is Record<string, never>. The {} type is sometimes used intentionally in type-level programming to mean "any non-nullable value."

Q: How does TypeScript handle { ...a, ...b } object spread types? Hard

TypeScript infers the type of { ...a, ...b } as a merged object type where properties from b override same-named properties from a. The inferred type reflects that later spread properties shadow earlier ones — unlike A & B intersection which would create a conflict for overlapping property names. This means { ...defaults, ...overrides } gives you an accurate type where overrides properties have their own types, not an intersection. This is one of the rare cases where the type of a value-level operation is subtly different from a pure type-level expression.

Type Aliases Beginner ▶

Simple Explanation

A type alias gives a name to any TypeScript type. Instead of writing { name: string; age: number } in every function signature, you define it once as type User = { name: string; age: number } and then use User everywhere. It's like a variable — but for types instead of values.

Technical Explanation

The type keyword creates an alias — another name — for a TypeScript type expression. Type aliases can name any type: primitive types, object types, union types, intersection types, function types, tuple types, and generic types. They are resolved entirely at compile time: the TypeScript compiler substitutes the full definition wherever the alias appears, then strips all type declarations from the output JavaScript.

The Problem It Solves

Without type aliases, you'd repeat complex type expressions in every function that uses them. When the shape needs to change — add a property, rename one — you'd have to hunt down every occurrence in the codebase and update them manually.

typescript — without aliases (bad)
// Repetition creates a maintenance nightmare
function saveUser(u: { id: number; name: string; email: string }): void { }
function updateUser(u: { id: number; name: string; email: string }): void { }
function deleteUser(u: { id: number; name: string; email: string }): void { }
// Adding 'role' requires updating 3 function signatures manually
typescript — with aliases (good)
// Single source of truth — update once, fixes everywhere
type User = { id: number; name: string; email: string };

function saveUser(u: User): void   { }
function updateUser(u: User): void { }
function deleteUser(u: User): void { }
// Add 'role' to User once — all three functions automatically updated

Type aliases are also the only way to name union types, intersection types, and function types — concepts that can't be expressed as interfaces.

When Type Aliases Are the Right Tool

  • Any type used in more than one place — duplicate types are a maintenance risk. Name it.
  • Union types — type Status = "active" | "inactive" | "banned" is unreadable inline; name it.
  • Intersection types — type AdminUser = User & { permissions: string[] } combines two types into one.
  • Function types — type EventHandler = (event: Event) => void is far cleaner than repeating function signatures.
  • Semantic primitive aliases — type UserId = number communicates intent; raw number does not.
  • Generic utility types — type Nullable<T> = T | null creates a reusable pattern for any type T.

When NOT to Use Type Aliases

  • When you need declaration merging — if you're extending a library's types (e.g., adding properties to Express's Request), you need interfaces, not type aliases. Type aliases cannot be reopened or merged.
  • When defining class shapes for OOP — use classes for implementations that combine state and behavior. Type aliases describe shapes, not implementations.
  • Over-aliasing obvious types — creating type MyString = string adds noise without benefit. Alias only when the name communicates something the underlying type does not.
  • When a simple inline type is clearer — function foo(x: string | number) is clearer than introducing type StringOrNumber = string | number for a type used exactly once.

What TypeScript Actually Does

Type aliases are purely a compile-time construct. The TypeScript compiler:

  1. Parses type X = ... and registers X in its type registry with its full definition.
  2. When X appears anywhere in code, substitutes the full definition for type checking purposes.
  3. Checks structural compatibility using the underlying type — not the alias name. Two aliases type A = { x: number } and type B = { x: number } are completely interchangeable.
  4. Emits zero JavaScript for type declarations — they are fully erased.

This means type aliases are cost-free at runtime. They are a developer experience tool, not a runtime mechanism. Because TypeScript uses structural typing, you cannot distinguish two aliases with identical structures — both are just the structure they alias.

typescript
// ── Basic type alias ──────────────────────────────────────────────────
type UserName = string;
//   ^^^^^^^^   ^^^^^^
//   alias name  the type being aliased (can be ANY type expression)

// ── Object type alias ─────────────────────────────────────────────────
type Point = {
  x: number;
  y: number;
};

// ── Union type alias ──────────────────────────────────────────────────
type Direction = "north" | "south" | "east" | "west";
type ID        = string | number;

// ── Intersection type alias ───────────────────────────────────────────
type WithTimestamps = { createdAt: Date; updatedAt: Date };
type User           = { id: number; name: string };
type UserRecord     = User & WithTimestamps;
//                         ^
//                         intersection: UserRecord has ALL properties of both types

// ── Function type alias ───────────────────────────────────────────────
type Comparator<T> = (a: T, b: T) => number;
//               ^^^
//               generic type parameter

// ── Referencing other aliases ─────────────────────────────────────────
type NullableUser = User | null;
//                  ^^^^
//                  references the User alias defined above

The type keyword is always followed by a name (PascalCase by convention), an equals sign, and the type expression. The type expression can be anything TypeScript supports: primitives, objects, unions, intersections, functions, tuples, or references to other type aliases.

typescript
// A typed blog system using type aliases

type PostId     = number;
type AuthorId   = number;
type PostStatus = "draft" | "published" | "archived";

type Author = {
  id: AuthorId;
  name: string;
  bio: string;
};

type Post = {
  id: PostId;
  title: string;
  content: string;
  author: Author;
  status: PostStatus;
  createdAt: Date;
};

// Function using the aliases — clean, readable signatures
function publishPost(post: Post): Post {
  return { ...post, status: "published" };
}

function getPostsByStatus(posts: Post[], status: PostStatus): Post[] {
  return posts.filter(p => p.status === status);
}

// Usage
const draft: Post = {
  id: 1, title: "Hello TypeScript", content: "...",
  author: { id: 10, name: "Alice", bio: "Developer" },
  status: "draft", createdAt: new Date(),
};
const published = publishPost(draft);
console.log(published.status); // "published"

  page: number;
  pageSize: number;

  totalPages: number;

  status: ApiStatus;
  data: T | null;
  error: string | null;

  id: number;
  name: string;
  price: number;
  category: string;

  try {
    const res  = await fetch(`/api/products?page=${page}`);
    const body = await res.json();
    return { status: "success", data: body.products, error: null, meta: body.pagination };
  } catch (err) {
    return { status: "error", data: null, error: String(err), meta: null };

  • Domain modeling — Type aliases like type OrderStatus = "pending" | "processing" | "shipped" | "delivered" make business logic self-documenting and enforce valid state values at the type level.
  • Generic utility types — Libraries define type aliases like type Nullable<T> = T | null that work for any type T, reducing boilerplate across the codebase.
  • React component props — Event handler types like type ClickHandler = React.MouseEventHandler<HTMLButtonElement> are aliased once and reused across all button components.
  • Branded types — type UserId = number & { readonly _brand: "UserId" } prevents accidentally passing a ProductId where a UserId is expected, catching logic errors at compile time.
  • Zod schema types — type UserSchema = z.infer<typeof userSchema> keeps the runtime validation schema and the static type in sync automatically.

1. Use PascalCase for all type aliases

This is the universal TypeScript convention, matching class and interface naming. It signals at a glance that a name refers to a type, not a variable.

2. Name types semantically — convey intent, not structure

type UserRole = "admin" | "user" | "guest" is better than type StringLiteral = "admin" | "user" | "guest". The name should tell you what the type represents, not describe its structure.

3. Prefer type aliases for union and intersection types

Complex types like string | number | null or User & Permissions are much more readable when given a meaningful name. Inline unions spanning more than two options should almost always be named.

4. Prefer interface for public API object shapes

Interfaces generate better error messages in some scenarios and support declaration merging — important when writing libraries or defining contracts that classes will implement.

5. Co-locate type aliases with their primary usage

Define types in the same file or module where they are primarily used. Export them if other modules need them. Avoid creating a single large types.ts file with unrelated types — it becomes a dumping ground.

6. Use type aliases to document intent for primitives

type Milliseconds = number adds no type safety (it's still just number) but documents that a parameter expects a time in milliseconds, not a count or an ID. This is especially useful for function parameter names.

Q: What is the difference between type and interface? Medium

Both describe object shapes and are often interchangeable. Key differences: (1) interface supports declaration merging — you can reopen an interface in multiple files and TypeScript merges the definitions; type aliases cannot be reopened. (2) type can alias any type — unions, intersections, primitives, functions, tuples; interface can only describe object shapes with named properties. (3) Error messages involving interfaces sometimes display the interface name rather than the expanded structure, which can be cleaner. Common style: prefer interface for object shapes and type for everything else.

Q: Are two type aliases with identical structures compatible? Easy

Yes. Because TypeScript uses structural typing, type A = { x: number } and type B = { x: number } are fully compatible and interchangeable — a value of type A can be assigned to a variable of type B and vice versa. The alias names don't matter for compatibility; only the underlying structure does. This is unlike nominal typing where two types with the same structure but different names would be incompatible.

Q: Can a type alias reference itself recursively? Hard

Yes — type aliases can be self-referential for recursive data structures: type Tree<T> = { value: T; children: Tree<T>[] }. TypeScript evaluates this lazily since the recursion is inside an object property (an array). However, direct recursion at the top level is not allowed: type Infinite = Infinite[] is a circular reference error. The key rule is that recursive references must appear inside an object, array, or generic parameter — not directly as the definition itself.

Q: How do you simulate interface extension with type aliases? Medium

Use the intersection operator (&): type Admin = User & { permissions: string[] }. This creates a new type with all properties of User plus permissions, structurally equivalent to extending an interface. The difference is that intersection combines using structural composition rather than named inheritance, and overlapping properties in an intersection must be compatible — if both types define id, their types must be compatible or the intersection becomes never.

Q: When would you always use a type alias instead of an interface? Easy

Always use type aliases for: (1) Union types — type Direction = "north" | "south"; interfaces cannot express unions. (2) Intersection types — type WithId<T> = T & { id: number }. (3) Function types — type Handler = (req: Request, res: Response) => void. (4) Tuple types — type Pair<A, B> = [A, B]. (5) Conditional types and mapped types. For these non-object-shape types, interfaces simply don't support the syntax and type aliases are the only option.

Optional Properties Beginner ▶

Simple Explanation

An optional property is one that might or might not be there. You mark it with a ? after the property name to say "this might exist on the object — but it might not." Objects with or without that property both pass the type check.

Technical Explanation

In TypeScript, the ? modifier after a property name converts the property from required to optional. Internally, TypeScript treats an optional property's type as Type | undefined. With strictNullChecks enabled, accessing an optional property returns a Type | undefined union, and TypeScript requires you to narrow out the undefined case before performing operations that assume a value.

The Problem It Solves

Real-world data is rarely complete. Not every user has a phone number. Not every API response includes all fields. JavaScript lets you create objects with missing properties freely, but without optional properties in the type system, TypeScript would force you to either lie (provide empty strings or fake values) or use any and lose type safety entirely.

typescript — without optional (lying)
type User = { name: string; phone: string }; // phone is "required"
const user: User = { name: "Alice", phone: "" };
// Empty string is a lie — phone is missing, not empty
typescript — with optional (honest)
type User = { name: string; phone?: string }; // phone is optional
const minimalUser: User = { name: "Alice" };           // ✓ valid
const fullUser: User    = { name: "Bob", phone: "555-0100" }; // ✓ also valid

When Optional Properties Are the Right Choice

  • Properties that exist in some cases but not others — middle name, phone extension, secondary email, avatar URL.
  • Options/configuration bags — when functions accept option objects, most options have defaults; mark everything with a default as optional.
  • Partial data — multi-step forms, draft documents, records in progress where not all fields are filled yet.
  • API responses with conditional fields — some REST APIs include certain fields only when the related feature is active.
  • Database columns allowing NULL — columns that accept NULL in your schema should be optional in TypeScript.

When NOT to Use Optional Properties

  • When a property is conceptually required — using ? on a field that's always present misleads readers and forces unnecessary null checks.
  • As a substitute for default values — if a property has a sensible default (false, 0, ""), provide the default in the function body; don't make the property optional on the type.
  • When making everything optional out of laziness — an object type where every property is optional provides almost no type safety. Be intentional about what's genuinely optional.
  • Mutually exclusive properties — if having fieldA means fieldB shouldn't exist, use a discriminated union instead of making both optional.

What TypeScript Actually Does

When TypeScript sees prop?: Type:

  1. Records prop as optional in the object type with effective type Type | undefined.
  2. Allows objects that omit prop entirely to satisfy the type — the property can be absent.
  3. When you access obj.prop, the result type is Type | undefined.
  4. With strictNullChecks: true, TypeScript requires narrowing before treating the value as Type: an if (obj.prop !== undefined) check or optional chaining (obj.prop?.method()) is required before calling methods on it.
  5. Compiles to plain JavaScript — no difference in the output object structure.

The JavaScript runtime doesn't know the property was optional. Absent properties are simply absent in the object — TypeScript's type system is the only place this is tracked.

2. Use optional chaining (?.) and nullish coalescing (??) for ergonomic handling

3. Use Partial<T> for update operations

Instead of manually marking all fields optional for patch/update DTOs, Partial<User> makes all User properties optional at once. This keeps update types in sync with the base type automatically.

4. Document why a property is optional

A comment like // only present for verified accounts tells future readers the invariant, so they know when they can safely skip the undefined check in specific contexts.

5. Use prop?: Type over prop: Type | undefined for object properties

Both are similar but prop?: Type communicates "this property may be absent" while prop: Type | undefined implies "always present but may be undefined." For object properties, ? is idiomatic and more clearly communicates absence.

6. Create separate types for different required/optional profiles

If an entity has different required fields in different contexts (create vs update vs display), define separate types: CreateUserInput, UpdateUserInput, UserView. Don't try to express all cases in one type with everything optional.

Q: What does ? after a property name mean in TypeScript? Easy

The ? marks a property as optional, meaning it may be entirely absent from the object or its value may be undefined. TypeScript treats the property's effective type as Type | undefined. For example, phone?: string means you can create an object without a phone property and it satisfies the type. With strictNullChecks enabled, TypeScript requires you to check for undefined before using the property as a string.

Q: What is the difference between name?: string and name: string | undefined? Medium

They are very similar but have a subtle semantic difference. name?: string means the property can be completely absent — {} satisfies the type. name: string | undefined technically requires the property to be present, though its value can be undefined — so { name: undefined } satisfies it, but {} technically does not. In practice, TypeScript's default behavior treats them almost identically. However, with exactOptionalPropertyTypes enabled, this distinction is strictly enforced, and { name: undefined } would not satisfy { name?: string }.

Q: How do you handle optional properties ergonomically without lots of if checks? Medium

Use optional chaining (?.) to safely access a property or call a method that might not exist: user.address?.city returns undefined instead of throwing. Use nullish coalescing (??) to provide a fallback when a value is null or undefined: user.name ?? "Anonymous". Combine them: user.config?.theme ?? "dark". For more complex logic where you need to do multiple operations on a potentially-undefined value, a guard clause (if (!user.config) return) keeps the rest of the function free of null checks.

Q: When would you use Partial<T> vs manually making properties optional? Medium

Partial<T> makes ALL properties of T optional at once — use it for patch/update operations where any field may change. Manually marking specific properties optional is better when only some fields are genuinely optional by design — it communicates intent more precisely and provides better type safety for the required fields. Creating a Partial<User> type for a PATCH endpoint is idiomatic and keeps the update type automatically in sync with any changes to the base User type.

Q: What is exactOptionalPropertyTypes and when does it matter? Hard

It's a TypeScript compiler option (introduced in 4.4) that makes optional property handling stricter. Without it, { prop: undefined } satisfies { prop?: string }. With exactOptionalPropertyTypes: true, an optional property (prop?: string) can only be absent or set to string — explicitly setting it to undefined is an error. This catches a class of bugs where you think you're "clearing" a property by setting it to undefined, but the type system was silently allowing it. It matters most when spreading objects or using Object.assign to update partial records.

Readonly Properties Beginner ▶

Simple Explanation

A readonly property is one that can be set when an object is created, but cannot be changed afterward. Think of it like writing in concrete while it's wet — once it sets, it's permanent. You can read the value any time, but you can't change it.

Technical Explanation

The readonly modifier in TypeScript marks a property as immutable after initialization. Any attempt to reassign a readonly property — whether by direct assignment (obj.prop = value) or compound assignment (obj.prop += 1) — produces a compile-time error. The compiled JavaScript is unchanged (there's no runtime enforcement); readonly is a purely static type-checking constraint.

The Problem It Solves

JavaScript's const prevents reassigning a variable binding, but it doesn't prevent mutating the object the variable points to. This means an ID, a creation timestamp, or a configuration value set at startup can be accidentally changed by any code that has a reference to the object.

javascript — the problem
const user = { id: 1, name: "Alice" };
user.id = 999; // JavaScript allows this — const only protects the binding!
// id is now corrupted — no error, no warning
typescript — the solution
type User = { readonly id: number; name: string };
const user: User = { id: 1, name: "Alice" };

user.id = 999;   // Error: Cannot assign to 'id' because it is a read-only property
user.name = "Bob"; // OK — 'name' is not readonly

This is especially valuable for entity primary keys, creation timestamps, and configuration values that define the identity of an object — things that should be set once and never touched again.

When Readonly Is the Right Choice

  • Primary keys and IDs — readonly id: number prevents the most dangerous possible mutation: changing a record's identity.
  • Creation timestamps — readonly createdAt: Date set when the record is created should never change.
  • Configuration values — Server port, database URL, API keys loaded at startup are set once and should stay fixed.
  • Computed/derived values — Values calculated from other immutable data and stored for performance should not be changed externally.
  • Function parameters you don't want to mutate — Readonly<Config> on a parameter signals the function reads but doesn't write the config.

When NOT to Use Readonly

  • Properties that legitimately need to change — shopping cart items, user profile fields, counters, status flags — don't make them readonly.
  • When you're implementing immutable updates via object spread — if your pattern is return { ...obj, field: newValue }, readonly helps; but if you need direct mutation (e.g., for performance), it gets in the way.
  • Don't use it to force immutability at runtime — readonly is compile-time only. For true runtime immutability (e.g., protecting shared config from third-party code), use Object.freeze() instead.
  • When it leads to excessive object spreading — if every update requires spreading the entire object just to change one field, reconsider whether the type should be mutable and managed differently.

What TypeScript Actually Does

readonly is a compile-time-only constraint. The TypeScript compiler:

  1. Records which properties are marked readonly in the type.
  2. At every assignment expression (obj.prop = ..., obj.prop += ..., obj.prop++), checks whether prop is readonly on obj's type.
  3. If readonly, emits a compile-time error and refuses to compile.
  4. In the output JavaScript, the property behaves like any regular property — there is no Object.defineProperty with writable: false, no Object.freeze. The restriction exists only in the type checker.

This means a cast to any — (obj as any).id = 999 — bypasses the check at runtime. For genuine runtime immutability, combine readonly (for type safety) with Object.freeze (for runtime enforcement). Note that Object.freeze is also shallow.

Q: What is the difference between const and readonly? Easy

const is a JavaScript keyword that prevents reassigning a variable binding — the variable always points to the same value or reference. It doesn't prevent mutating the object's properties. readonly is a TypeScript type modifier that prevents reassigning a specific property on an object. You need both: const to prevent the variable from pointing to a different object, and readonly to prevent the object's properties from being mutated. const obj = { x: 1 } still allows obj.x = 2, while adding readonly x to the type prevents that.

Q: Does readonly provide runtime immutability? Medium

No — readonly is a compile-time constraint only. TypeScript detects and rejects assignments to readonly properties in source code during type checking, but the compiled JavaScript has no special handling. The property is a regular writable JavaScript property. Someone can bypass it at runtime with (obj as any).id = 999. For actual runtime immutability, use Object.freeze(obj), which prevents property mutation at the JavaScript engine level. A common pattern is combining both: readonly for compile-time safety and Object.freeze for runtime enforcement — but note Object.freeze is also shallow.

Q: What is Readonly<T> and when would you use it? Medium

Readonly<T> is a built-in utility type that takes any type T and makes all its top-level properties readonly. It's equivalent to manually prefixing every property with readonly. Use it when: passing an object to a function that should not mutate it (process(config: Readonly<Config>)), creating an immutable snapshot of a type, or signaling that a returned object is read-only. It does not affect nested objects — Readonly<{ server: { port: number } }> prevents replacing server, but not mutating server.port.

Q: What is as const and how does it relate to readonly? Hard

as const is a const assertion that does two things: (1) makes all properties readonly recursively throughout the object tree, and (2) narrows all values to their most specific literal types. So const x = { port: 3000 } as const gives x the type { readonly port: 3000 } — note 3000 (literal number type) not number. This is more powerful than just readonly alone and is the idiomatic way to create typed constant lookup objects. The literal type narrowing means TypeScript knows exactly what value to expect, not just what primitive type.

Q: How do you make a deeply nested object fully readonly in TypeScript? Hard

The built-in Readonly<T> is shallow — it only makes the top-level properties readonly. For deep readonly, you need a recursive utility type: type DeepReadonly<T> = { readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K] }. This maps over every key K in T, marks it readonly, and recursively applies the same transformation to nested objects. Libraries like type-fest provide this as ReadonlyDeep<T>. For many use cases, the as const assertion achieves deep readonly on literal values, and combining as const with Object.freeze covers most production scenarios.

  • The readonly modifier prevents a property from being reassigned after the object is created.
  • It is compile-time only — the compiled JavaScript has no runtime enforcement of immutability.
  • const and readonly are complementary: const protects the variable binding, readonly protects the property.
  • readonly is shallow — nested objects can still be mutated through a readonly reference unless their properties are also marked readonly.
  • Readonly<T> makes all top-level properties of T readonly at once.
  • as const makes all properties readonly AND narrows values to literal types — ideal for constant lookup objects.
  • For genuine runtime immutability, combine readonly with Object.freeze().
💡 Mental model: readonly is like writing in permanent marker — once the value is set at creation time, you can read it as much as you want, but you can't erase or change it. To "update" a readonly property, you write a whole new object (object spread pattern).
