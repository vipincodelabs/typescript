Arrays and tuples are TypeScript’s primary tools for typed collections. Arrays give you a flexible, homogeneous list where every item is the same type. Tuples give you a fixed-length list where each position has its own type — perfect for returning multiple values from a function. After this module you’ll write type-safe collections, prevent accidental mutation with readonly, model structured data with tuples, and represent grids and matrices with nested arrays.

Arrays
Beginner
Simple: An array in TypeScript is an ordered list where every item must be the same type. Think of it as a typed version of a JavaScript array — you declare upfront what kind of items live in the list, and TypeScript enforces it.
Technical: TypeScript arrays are parameterized over an element type T, written as T[] or Array<T>. The compiler validates every push, assignment, and indexed access against the declared element type. At runtime all type annotations are erased — typed arrays are plain JavaScript arrays.

Plain JavaScript arrays accept anything — you can push a string into a number array and nothing complains until your code breaks at runtime:

javascript — silent bug
const scores = [85, 92, 78];
scores.push("oops");                        // no error!
const total = scores.reduce((a,b) => a+b, 0);
console.log(total); // "85920oops" — NaN catastrophe

TypeScript catches the mistake at compile time, before the code runs:

typescript — caught immediately
const scores: number[] = [85, 92, 78];
scores.push("oops");
// Error: Argument of type 'string' is not assignable
//        to parameter of type 'number'

This matters most in large codebases where array results flow between many functions — TypeScript guarantees the shape is correct all the way through the call chain.

  • Homogeneous lists — any time all items share the same type: User[], string[], number[].
  • API responses — type GET /users as returning User[] so every consumer is type-safe.
  • React props — items: Product[] gives type-checked .map() calls in JSX.
  • Queue / stack operations — push, pop, shift, unshift are all type-checked.
  • Sorted or paginated results — any ordered collection of uniform data.
  • Fixed-length, mixed-type sequences — use a Tuple instead. [string, number] is clearer than (string | number)[] when position matters.
  • Named key-value collections — use an object, Record<K, V>, or Map<K, T> when you access items by key.
  • Unique-item sets — use Set<T> when duplicates are meaningless and you only need has/add/delete.
  • When you write any[] — this disables all element-level type checking. Use a specific type, union, or generic instead.

TypeScript’s array types are compile-time only. The compiler:

  1. Infers the type from the literal: [1, 2, 3] → number[].
  2. Checks assignments: every = validates the right-hand side matches T[].
  3. Checks mutating calls: .push() requires a T argument; .splice() returns T[].
  4. Types return values: .find() returns T | undefined; .map(cb) infers the return type from cb.
  5. Erases everything at compile time — zero runtime overhead.
before compilation
const names: string[] = ["Alice", "Bob"];
names.push("Carol");
after compilation (plain JS)
const names = ["Alice", "Bob"];
names.push("Carol");
typescript
// 1. Shorthand T[] — preferred for simple types
let names: string[] = ["Alice", "Bob", "Carol"];
//          ^^^^^^^^  array-of-strings annotation

// 2. Generic Array<T> — identical to T[]
let scores: Array<number> = [85, 92, 78];

// 3. Type inferred from literal
const flags = [true, false, true]; // inferred: boolean[]

// 4. Empty array MUST be annotated — bare [] infers never[]
const items: string[] = [];
//           ^^^^^^^^  without this, .push("x") errors!

// 5. Array of interfaces / type aliases
interface User { id: number; name: string; }
const users: User[] = [{ id: 1, name: "Alice" }];

// 6. Union-element array (use sparingly — prefer Tuple for positional data)
const mixed: (string | number)[] = ["Alice", 30];

T[] and Array<T> are 100% identical. Use T[] for readability with simple types. Use Array<T> when T itself contains <> (e.g., Array<Map<string, number>>) to avoid nested angle-bracket confusion.

typescript
// Grade statistics — demonstrates typed array operations
function analyzeGrades(grades: number[]): {
  average: number;
  highest: number;
  lowest: number;
  passing: number[];
} {
  if (grades.length === 0) {
    return { average: 0, highest: 0, lowest: 0, passing: [] };
  }
  const sum = grades.reduce((acc, g) => acc + g, 0);
  return {
    average: Math.round((sum / grades.length) * 10) / 10,
    highest: Math.max(...grades),
    lowest:  Math.min(...grades),
    passing: grades.filter(g => g >= 60), // still number[]
  };
}

const classGrades: number[] = [78, 92, 55, 88, 67, 95, 43, 71];
const stats = analyzeGrades(classGrades);

console.log(stats.average);        // 73.6
console.log(stats.highest);        // 95
console.log(stats.lowest);         // 43
console.log(stats.passing.length); // 6

// TypeScript catches this at compile time:
// analyzeGrades(["Alice", "Bob"]);
// Error: Argument of type 'string[]' is not assignable to 'number[]'

❌ Mistake 1 — Using any[] instead of a specific type
bad
function processUsers(users: any[]) {
  users.forEach(u => console.log(u.nme)); // typo — no error!
}
good
function processUsers(users: User[]) {
  users.forEach(u => console.log(u.name)); // typo caught immediately
}
any[] silences all property-access checks on elements — you lose the entire benefit of TypeScript for that array.
❌ Mistake 2 — Not annotating empty arrays
bad
const items = [];      // inferred as never[]
items.push("hello");   // Error: 'string' not assignable to 'never'
good
const items: string[] = [];
items.push("hello");   // OK
TypeScript infers never[] for a bare [] literal — nothing can ever be pushed. Always annotate empty arrays.
❌ Mistake 3 — Mutating a caller’s array with splice
bad
function topThree(arr: number[]): number[] {
  return arr.splice(0, 3); // mutates the original!
}
good
function topThree(arr: readonly number[]): number[] {
  return arr.slice(0, 3); // creates a new array
}
Use readonly on parameters to prevent accidental mutation; prefer non-mutating methods (slice, filter, map) that return new arrays.
  1. Prefer T[] over Array<T> for simple types — it's more concise and idiomatic. Use Array<T> only when T itself contains angle brackets.
  2. Always annotate empty arrays — const items: string[] = []. TypeScript infers never[] from a bare [].
  3. Use readonly T[] for parameters that the function only reads. This also makes the function accept both mutable and readonly arrays as arguments.
  4. Use type predicates for filtered narrowing — plain .filter(x => x != null) does not narrow the element type; you need .filter((x): x is T => x != null).
  5. Never use any[] — use a union type, generic, or unknown[] with type guards instead.
Easy What is the difference between string[] and Array<string>?
They are completely identical. string[] is syntactic sugar for Array<string>. The TypeScript compiler treats them the same. Convention: use string[] for simple types and Array<T> when T itself is a complex generic to avoid nested angle brackets.
Easy What happens when you push a number into a string[]?
TypeScript raises a compile-time error: "Argument of type 'number' is not assignable to parameter of type 'string'". The code won’t compile. This is the core value of typed arrays — catching type mismatches before the code ever runs.
Medium Why does const arr = [] cause a problem with .push()?
TypeScript infers the type of [] as never[] — an array that can hold nothing. Any push fails because no type is assignable to never. Fix: always annotate empty arrays: const arr: string[] = [].
Medium How do you type a function that accepts both string[] and number[]?
Two options: a union (arr: string[] | number[]) or a generic (arr: T[]). The union forces you to narrow with typeof inside the function. The generic preserves the specific type through the function body — use generics when the function works uniformly across element types.
Hard What is the return type of arr.filter(x => x > 0) when arr: (number | null)[]?
Still (number | null)[]. TypeScript doesn’t analyze filter callbacks to infer which elements pass. To get number[], use a type predicate: arr.filter((x): x is number => x !== null && x > 0). The (x): x is number form explicitly tells the compiler the narrowing guarantee.

Readonly Arrays
Beginner
Simple: A readonly array is a typed array you promise not to change. TypeScript removes push, pop, splice, and any other method that modifies the array. You can still read, iterate, and spread it.
Technical: ReadonlyArray<T> (or readonly T[]) is a TypeScript interface that omits all mutating methods and blocks index-assignment (arr[0] = ...). The underlying runtime value is still a plain JavaScript array — readonly is purely a compile-time constraint with zero runtime cost.

Accidental mutation is one of the hardest bugs to track in JavaScript. Passing an array to a function can silently modify it for the caller:

javascript — silent mutation bug
const config = ["debug", "info", "warn"];

function setupLogger(levels) {
  levels.sort();         // mutates the caller's array!
  levels.push("error"); // caller's array now has "error" too!
}

setupLogger(config);
console.log(config); // ["debug","error","info","warn"] — surprise!

With readonly, TypeScript prevents this at the call site:

typescript — compile-time protection
function setupLogger(levels: readonly string[]): void {
  levels.sort();         // Error: 'sort' does not exist on readonly string[]
  levels.push("error"); // Error: 'push' does not exist on readonly string[]
}

This is especially critical in React where mutating a prop array inside a child component bypasses React’s change detection and causes subtle rendering bugs.

  • Function parameters you only read — annotate any array parameter the function doesn’t modify as readonly T[] to document and enforce the contract.
  • React component props — items: readonly Product[] prevents child components from mutating parent state.
  • Configuration constants — allowed origins, supported locales, feature flags — anything that should not change at runtime.
  • Redux / Zustand state — state arrays should never be mutated directly; readonly enforces this at the type level.
  • as const assertions — ["red","green","blue"] as const infers readonly ["red","green","blue"] with literal types per element.
  • Arrays you’re actively building — use a mutable T[] locally while collecting results, then expose it as readonly T[] when returning.
  • APIs that require mutable arrays — some older libraries type their parameters as T[] and won’t accept readonly T[]. Spread into a mutable copy: [...readonlyArr].
  • In-place sort operations — Array.prototype.sort is mutating. Use [...arr].sort() on a copy instead.

ReadonlyArray<T> is a built-in TypeScript interface that includes only non-mutating methods: map, filter, find, forEach, slice, indexOf, includes — but not push, pop, splice, sort, reverse, or index assignment.

At runtime there is no difference between readonly string[] and string[]. Both are plain JavaScript arrays. The constraint lives only in TypeScript’s type checker.

Key assignability rule: a mutable T[] is always assignable to readonly T[] (you’re adding a restriction, which is safe). The reverse is not allowed (you can’t promise immutability and then break it):

typescript
const mutable: string[] = ["a", "b"];
const frozen: readonly string[] = mutable; // OK — narrowing is safe

function needsMutable(arr: string[]) { arr.push("c"); }
needsMutable(frozen);  // Error: ReadonlyArray not assignable to string[]
needsMutable(mutable); // OK
typescript
// 1. readonly modifier — preferred
const levels: readonly string[] = ["debug", "info", "warn"];
//             ^^^^^^^^  removes all mutating methods from the type

// 2. ReadonlyArray<T> — identical to readonly T[]
const scores: ReadonlyArray<number> = [85, 92, 78];

// 3. as const — readonly TUPLE with literal types per element
const DIRS = ["north", "south", "east", "west"] as const;
//                                               ^^^^^^^^
// Inferred: readonly ["north","south","east","west"]
// Each element is a literal type, not just 'string'

// Function parameter — accepts BOTH mutable and readonly arrays
function printAll(items: readonly string[]): void {
  items.forEach(item => console.log(item)); // OK — read only
  items.push("extra"); // Error: 'push' does not exist on readonly
}

printAll(["a", "b"]); // OK — mutable string[] accepted
printAll(DIRS);        // OK — readonly tuple accepted

// Readonly does NOT prevent spreading
const sorted = [...levels].sort(); // OK — spread into a new mutable copy

❌ Mistake 1 — Confusing const with readonly
bad

good

❌ Mistake 2 — Passing readonly array to mutable parameter
bad

When you need to sort or mutate, spread the readonly array into a fresh mutable copy: [...readonlyArr].sort().
  1. Default to readonly T[] for function parameters that only read the array — it widens acceptability (mutable arrays still work) while documenting intent.
  2. Use as const for constant literal arrays — gives a readonly tuple with literal types, enabling exhaustive checks and narrowing.
  3. Remember: const ≠ readonly — const prevents reassignment; readonly prevents mutation. You typically want both.
  4. Spread when you need to sort or mutate — [...readonlyArr].sort() creates a mutable copy without touching the original.
  5. Annotate return types explicitly when returning readonly — otherwise TypeScript may infer the wider mutable type.
Easy What is the difference between const arr = [] and const arr: readonly string[] = []?
const only prevents the variable from being reassigned. The array’s contents can still be mutated with push, pop, etc. readonly string[] additionally prevents any mutation of contents — you cannot call any mutating method or do index assignment. Both together give you a fully immutable array.
Easy Can you pass a mutable string[] to a function expecting readonly string[]?
Yes. A mutable array is always assignable to a readonly array — you’re only adding a restriction. The reverse is not allowed: you cannot pass a readonly string[] to a function expecting string[], because that function might try to mutate it.
Medium How does as const differ from readonly T[]?
readonly T[] keeps element types as wide as T. as const infers the narrowest possible type — a readonly tuple where each element has its literal type. ["a","b"] as const gives readonly ["a","b"], not readonly string[]. Use as const when you need the specific values as types for discriminated unions or exhaustiveness checks.
Medium What’s the right way to sort a readonly string[]?
Spread it into a mutable copy first: [...readonlyArr].sort(). You cannot call .sort() directly on a readonly array because sort is an in-place mutating operation. The spread creates a shallow mutable copy, sort runs on that, and the original readonly array is untouched.
Hard Is there a runtime performance cost to using readonly arrays?
No. readonly is completely erased when TypeScript compiles to JavaScript. The resulting JS has no readonly constraint whatsoever — zero runtime overhead. The only practical cost is that you may need to spread readonly arrays into mutable copies for certain operations, which allocates a new array. That’s a conscious design choice, not a framework tax.

Tuples
Intermediate
Simple: A tuple is an array with a fixed number of slots where each slot has its own specific type. Unlike a regular array where all items are the same type, a tuple says “slot 0 is a string, slot 1 is a number” — and TypeScript holds you to that contract at every access.
Technical: A TypeScript tuple is an array type with a fixed length and per-position element types. The type [string, number, boolean] describes an array of exactly 3 elements where index 0 is string, index 1 is number, and index 2 is boolean. TypeScript 4.0+ supports named tuples: [name: string, age: number] — the labels add documentation without changing runtime behaviour.

Sometimes you want to return multiple values from a function without creating a full object. In JavaScript you return an array and just remember what each position means — which breaks easily:

javascript — fragile convention
function getUser() {
  return ["Alice", 30]; // Is [0] name or age? Only one way to know...
}
const result = getUser();
const age = result[0]; // string! But the dev thought it was number.

TypeScript tuples make position-to-type mapping explicit and enforced:

typescript — explicit and safe
function getUser(): [name: string, age: number] {
  return ["Alice", 30];
}
const [name, age] = getUser();
//     ^^^^  ^^^  — TypeScript knows string and number respectively

React’s useState hook uses exactly this pattern, returning [T, Dispatch<SetStateAction<T>>].

  • Hook return values — [state, setState], [data, loading, error] — React’s built-in hooks all use tuples.
  • Go-style error handling — [result: T | null, error: Error | null] as an explicit error return pattern.
  • Coordinate pairs / ranges — [x: number, y: number], [min: number, max: number].
  • CSV or structured data rows — when a row always has [id, name, email] and the structure is fixed.
  • Promise.all results — await Promise.all([fetchUser(), fetchConfig()]) returns [User, Config].
  • More than 3 elements — use an interface. A 5-element tuple is a maintenance nightmare; no one can remember what index 4 means next month.
  • All elements the same type — use a regular array. [number, number, number] is just a worse number[] with a fixed length.
  • When named access matters — if you'll write .name and .age, use an object. { name: string; age: number } is far more readable.
  • Data models — tuples lack self-documentation. An interface with named fields is always more maintainable than positional slots.

TypeScript compiles tuples to plain JavaScript arrays. What makes them special is how the compiler indexes into the type:

  1. Indexed access: tuple[0] on [string, number] returns string; tuple[1] returns number.
  2. Length literal: [string, number]['length'] is the literal type 2, not number.
  3. Destructuring: const [a, b] = tuple assigns a: string and b: number by position.
  4. Rest elements: [string, ...number[]] — a string followed by any number of numbers.
before / after compilation
// TypeScript
const point: [number, number] = [10, 20];

// JavaScript output (identical — type info is erased)
const point = [10, 20];
typescript
// Basic tuple
let point: [number, number] = [10, 20];
//          ^^^^^^  ^^^^^^  — slot 0 and slot 1 have their own types

// Named tuple (TypeScript 4.0+) — adds IDE documentation
let person: [name: string, age: number] = ["Alice", 30];

// Tuple as function return type
function divide(a: number, b: number): [result: number, remainder: number] {
  return [Math.floor(a / b), a % b];
}

// Optional element (TS 4.0+)
type StringNum = [string, number?]; // length 1 or 2

// Rest element in tuple
type StringAndNums = [string, ...number[]];
const a: StringAndNums = ["hello"];           // OK
const b: StringAndNums = ["hello", 1, 2, 3]; // OK

// Readonly tuple
const RGB: readonly [number, number, number] = [255, 128, 0];

// Go-style error handling with tuples
type Result<T> = [data: T, error: null] | [data: null, error: Error];

function safeParse(json: string): Result<unknown> {
  try {
    return [JSON.parse(json), null];
  } catch (e) {
    return [null, e as Error];
  }
}

const [data1, err1] = safeParse('{"name":"Alice"}');
if (err1 === null) {

  2. Use named tuples for documentation — [name: string, age: number] over bare [string, number]. IDE hover hints show the labels, making destructuring much clearer.
  3. Prefer 2–3 elements max — beyond that, use an interface. Named access (user.name) is almost always clearer than positional access.
  4. Destructure immediately — const [data, err] = result is far clearer than result[0] / result[1].

Easy What is the difference between a tuple and a regular array in TypeScript?
A regular array (T[]) has variable length and every element is the same type. A tuple has a fixed length where each position can have a different type. [string, number] is exactly 2 elements where index 0 is always string and index 1 is always number. At runtime both are plain JavaScript arrays — the distinction is entirely in TypeScript’s type system.
Easy Why doesn’t TypeScript infer a tuple when you return a mixed array?
TypeScript infers the widest type by default. For return ["Alice", 30] it infers (string | number)[] — a variable-length array of either strings or numbers. To get a tuple, annotate the return type explicitly (: [string, number]) or use as const.
Medium What are named tuples in TypeScript 4.0, and why are they useful?
Named tuples let you add labels to each position: [name: string, age: number]. The labels appear in IDE hover hints and error messages but don’t change runtime behaviour. They’re especially useful for hook return types where the consumer chooses their own destructuring names but needs to know what each position means.
Medium How does React’s useState use tuples?
useState<T> is declared as returning [T, Dispatch<SetStateAction<T>>]. This tuple is what enables const [count, setCount] = useState(0). TypeScript infers count: number and setCount: Dispatch<SetStateAction<number>> from the tuple — the consumer can name them however they want.
Hard What are rest elements in tuples, and when would you use them?
Rest elements let you define a tuple with a known prefix and a variable-length suffix: [string, ...number[]] means “a string followed by zero or more numbers.” TypeScript 4.0+ also supports rest elements in the middle or beginning. They’re useful for variadic function signatures and spread-argument patterns that are otherwise hard to type precisely.

Nested Arrays
Intermediate
Simple: A nested array is an array whose elements are themselves arrays. In TypeScript you write this by doubling the notation: number[][] means “an array of arrays of numbers” — like a grid or table where each row is an array.
Technical: T[][] is equivalent to Array<Array<T>>. TypeScript tracks nesting depth in the type, so arr[0] on a number[][] returns number[] and arr[0][0] returns number. The pattern extends to any depth: T[][][] for three dimensions, though two levels is the practical limit for maintainability.

Many real-world structures are inherently two-dimensional. Without proper typing, accessing nested data causes runtime errors that are hard to debug:

javascript — no type safety on nested access
const grid = [[1,2,3],[4,5,6],[7,8,9]];
const cell = grid[1][5]; // undefined — out of bounds, no warning
const sum  = grid[0] + 1; // NaN — you got a row, not a number!

TypeScript with nested array types catches these mistakes at compile time:

typescript — type-safe nested access
const grid: number[][] = [[1,2,3],[4,5,6],[7,8,9]];
const row  = grid[1];     // Type: number[]
const cell = grid[1][1];  // Type: number — value: 5
const sum  = grid[0] + 1; // Error: Operator '+' cannot be applied
                           //        to types 'number[]' and 'number'
  • Grid / board data — game boards, seating charts, spreadsheet cells, image pixel maps.
  • Matrix operations — mathematical matrices, transformation matrices in graphics.
  • CSV / table parsing — rows: string[][] where each row is an array of cell values before transformation.
  • Batch processing results — when an API returns results in batches (T[][]).
  • Arrays of tuples — [number, number][] for lists of coordinate pairs or key-value entries.
  • Irregular / asymmetric structures — if rows have different shapes per type, use discriminated unions or interfaces instead.
  • 3+ levels of nesting — T[][][] is hard to reason about. Consider flattening or using a flat array with index arithmetic.
  • Rows with semantic column names — a TableRow interface is far clearer than string[] when columns have meaning.
  • Recursive/variable-depth structures — use recursive types (type Tree<T> = T | Tree<T>[]) rather than increasing numbers of [].

T[][] is structural shorthand for Array<Array<T>>. TypeScript tracks nesting depth by peeling one layer of array wrapping per index access:

  • arr → number[][]
  • arr[0] → number[]
  • arr[0][0] → number

For arrays of tuples, the compiler tracks the tuple shape per element:

typescript
const points: [number, number][] = [[0,0],[1,2],[3,4]];
const first = points[0];    // Type: [number, number]
const x     = points[0][0]; // Type: number
const y     = points[0][1]; // Type: number
// points[0][2]              // Error: Tuple type '[number,number]' has no element at index 2

At runtime, nested arrays are plain JavaScript arrays of plain arrays — no structural metadata is stored. All type tracking is compile-time only.

function createMatrix(rows: number, cols: number, fill = 0): Matrix {

function transpose(matrix: Matrix): Matrix {
  if (matrix.length === 0) return [];
  const rows = matrix.length;
  const cols = matrix[0].length;
  return Array.from({ length: cols }, (_, col) =>
    Array.from({ length: rows }, (_, row) => matrix[row][col])
  );
}

interface UserImportRow {
  name:  string;
  email: string;
  role:  "admin" | "user";
}

type ValidationError = { row: number; col: number; message: string };

// Raw CSV parsed into string[][] by a CSV library
function parseCSV(csv: string): string[][] {
  return csv.trim().split("\n").map(line => line.split(","));
}

function validateAndTransform(
  rows: string[][]
): { users: UserImportRow[]; errors: ValidationError[] } {
  const users:  UserImportRow[]  = [];
  const errors: ValidationError[] = [];

  rows.slice(1).forEach((row, rowIdx) => {
    const [name, email, role] = row; // destructure each string[] row

    if (!name)              { errors.push({ row: rowIdx+1, col:0, message:"Name required" }); return; }
    if (!email?.includes("@")) { errors.push({ row: rowIdx+1, col:1, message:"Invalid email" }); return; }
    if (role !== "admin" && role !== "user") {
      errors.push({ row: rowIdx+1, col:2, message:"Invalid role" }); return;
    }
    users.push({ name, email, role });
  });

  return { users, errors };
}

const csv = `name,email,role\nAlice,alice@co.com,admin\nBob,not-email,user`;
const { users, errors } = validateAndTransform(parseCSV(csv));
console.log("Users:",  users.length);  // 1
console.log("Errors:", errors.length); // 1

  • Game boards — Cell[][] for chess, checkers, Minesweeper — rows and columns of cell states.
  • Seating charts — Seat[][] for theatres or stadiums — rows and columns of seat availability.
  • Image processing — Pixel[][] for 2D pixel grids in canvas manipulation.
  • Coordinate lists — [number, number][] for GeoJSON polygon rings, SVG path points, or canvas drawing commands.
  • Batch API responses — T[][] where outer is batches and inner is results per batch.

❌ Mistake 2 — Using number[][] instead of [number, number][] for fixed-size pairs
bad

// points[0][5] is typed as 'number' — out of bounds not caught!
good

When each sub-array has a fixed, known length with positional meaning, use an array of tuples for stronger type safety.
  1. Use type aliases for complex nested types — type Matrix = number[][] is far more readable than repeating number[][] everywhere.
  2. Parse raw string[][] into typed objects early — don’t pass raw CSV data deep into your codebase; transform it to a typed interface at the boundary.
  3. Prefer arrays of tuples for fixed-structure rows — [x: number, y: number][] over number[][] for coordinate lists; tuples prevent out-of-bounds access.
  4. Avoid 3+ levels of nesting — T[][][] is hard to debug. Flatten or restructure if you find yourself there.
  5. Use .flat() and .flatMap() — TypeScript types both correctly; .flat() on T[][] returns T[].
Easy What is the type of arr[0] when arr: number[][]?
The type is number[]. Accessing the first index of a number[][] removes one level of array wrapping. Then arr[0][0] would give number. TypeScript tracks this depth automatically.
Easy How do you type an array of x/y coordinate pairs?
Use an array of tuples: [number, number][] or with named elements: [x: number, y: number][]. This is more specific than number[][] because it enforces exactly 2 elements per sub-array and prevents accessing a non-existent third index. Alternatively, use { x: number; y: number }[] if named access is preferred over destructuring.
Medium What does TypeScript infer as the type of [[1,2],[3,4]]?
TypeScript infers number[][] — an array containing arrays of numbers. It does not infer a fixed-size 2×2 type. If you need the 2D structure enforced as a specific size, you need an explicit annotation or a type constraint (which TypeScript cannot natively enforce for rectangular grids at the type level alone).
Medium How does .flat() work with nested array types in TypeScript?
.flat() is typed in TypeScript’s lib to return the flattened type. Calling .flat() on a number[][] returns number[]. Calling .flat() on number[][][] returns number[][]. TypeScript tracks this in the return type so you don’t need a manual annotation. .flatMap() similarly collapses one level of nesting.
Hard How would you type a function that works on any rectangular grid?
Use a generic: function processGrid<T>(grid: T[][]): T[]. For true rectangular enforcement (all rows same length), TypeScript can’t verify it at compile time without complex conditional types. In practice, use T[][] with a runtime length check and a documented precondition. If the exact dimensions are compile-time constants, you can encode them with tuple types in advanced TypeScript.
