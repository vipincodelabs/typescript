Classes are how you bundle data and the behavior that acts on it into a single, reusable blueprint. If you've used class in modern JavaScript, the syntax will look familiar — but TypeScript adds a typed layer on top that catches an entire category of bugs before your code ever runs: missing fields, wrong argument types, calling methods that don't exist. By the end of this module you'll be able to model real-world entities — a BankAccount, a User, a Book — as fully typed classes with constructors, methods, and properties, and you'll understand exactly what TypeScript checks at compile time versus what runs in the browser.

▶Class Basics
Beginner

Simple Explanation

A class is a blueprint for making objects. Think of it like a cookie cutter: the class defines the shape (what data and what actions an object has), and each object you stamp out with new is a real cookie made from that shape. You design the cutter once, then produce as many cookies as you want.

Technical Explanation

A class declares a new type and a constructor function in one statement. The class body lists fields (typed data) and methods (typed behavior). Calling new ClassName() creates an instance — an object whose type is the class itself. TypeScript treats the class name as both a runtime value (the constructor) and a compile-time type (the instance shape), which is why you can write const u: User = new User().

The Problem Without Classes

In plain JavaScript you can build objects with factory functions or object literals, but nothing stops you from forgetting a field, misspelling a property, or calling a method that doesn't exist. The mistake surfaces at runtime — often in production — as undefined is not a function.

javascript
// Plain JS object — no guard rails
function makeUser(name) {
  return { name: name };  // forgot to add greet()
}
const u = makeUser("Ada");
u.greet();  // 💥 runtime crash: u.greet is not a function

The Solution With a TypeScript Class

typescript
class User {
  name: string;
  constructor(name: string) { this.name = name; }
  greet() { return `Hi, ${this.name}`; }
}
const u = new User("Ada");
u.greet();   // ✓ TypeScript knows greet exists
u.greett();  // ✗ Error: Property 'greett' does not exist — caught before running

When to Use Classes

  • When data and behavior belong together — a ShoppingCart holds items and knows how to add/remove/total them.
  • When you need many instances of the same shape — each BankAccount has its own balance but shares the same methods.
  • When you'll use inheritance or interfaces — classes can extends a base class or implements an interface contract.
  • When integrating with class-based libraries — ORMs (TypeORM), NestJS controllers/services, and Angular all expect classes.
  • When you want a stable identity with internal state — a class instance encapsulates mutable state behind methods.

When NOT to Use Classes

  • For plain data with no behavior — a config object or API response is better as an interface / type and a plain object literal.
  • In functional React code — modern React uses function components and hooks; class components are legacy.
  • When a single function will do — don't wrap one pure function in a class just to call new; export the function instead.
  • When you need structural shapes, not instances — if you only need to describe the shape of data flowing through your app, a type alias is lighter and has zero runtime footprint.

What TypeScript Does Under the Hood

A class is one of the few TypeScript features that emits real runtime JavaScript — unlike interfaces or type aliases, which vanish during compilation. Here's the step-by-step:

  1. TypeScript reads the class and registers two things from one name: a value (the constructor function) and a type (the instance shape).
  2. It type-checks every field assignment, method body, and new call against that shape.
  3. It strips all type annotations and emits a standard JavaScript class (or a function + prototype if targeting older ES versions).
  4. At runtime, new User() allocates an object, links it to User.prototype, runs the constructor, and returns the instance.
typescript
// TypeScript source
class User {
  name: string;
  constructor(name: string) { this.name = name; }
}

// Compiled JavaScript (ES2015 target) — types erased
class User {
  constructor(name) { this.name = name; }
}

Fully Annotated Syntax

typescript
class Point {
//    ^^^^^ class name — also becomes a TYPE you can annotate with
  x: number;   // field declaration with a type annotation
  y: number;   // every instance will have x and y of type number

  constructor(x: number, y: number) {
    this.x = x;  // 'this' refers to the instance being created
    this.y = y;
  }

  distanceFromOrigin(): number {
//                       ^^^^^^^^ method return type annotation
    return Math.sqrt(this.x ** 2 + this.y ** 2);
  }
}

const p: Point = new Point(3, 4);
//       ^^^^^         ^^^^^^^^^ 'new' invokes the constructor
//       Point as a TYPE annotation (the instance shape)
console.log(p.distanceFromOrigin()); // 5

The class name does double duty: as a type in annotations and as a value after new. Fields declared at the top of the body must either be initialized or assigned in the constructor, or TypeScript reports them as not definitely assigned (under strictPropertyInitialization).

Practical Code Example

typescript
// A small Timer class — data (state) + behavior (methods) together
class Stopwatch {
  elapsed: number = 0;     // field with an initializer
  running: boolean = false;

  start(): void {
    this.running = true;
  }

  tick(seconds: number): void {
    if (this.running) this.elapsed += seconds;
  }

  stop(): number {
    this.running = false;
    return this.elapsed;
  }
}

const sw = new Stopwatch();
sw.start();
sw.tick(5);
sw.tick(3);
console.log(sw.stop()); // Output: 8
console.log(sw.running); // Output: false

Real-World Example

typescript
// A typed in-memory cache used across a Node service
class TTLCache {
  private store = new Map<string, { value: unknown; expiresAt: number }>();

  set(key: string, value: unknown, ttlMs: number): void {
    this.store.set(key, { value, expiresAt: Date.now() + ttlMs });
  }

  get(key: string): unknown | undefined {
    const hit = this.store.get(key);
    if (!hit) return undefined;
    if (Date.now() > hit.expiresAt) {     // expired
      this.store.delete(key);
      return undefined;
    }
    return hit.value;
  }

  size(): number { return this.store.size; }
}

const cache = new TTLCache();
cache.set("user:1", { id: 1, name: "Ada" }, 60_000);
console.log(cache.get("user:1")); // { id: 1, name: "Ada" }

Real-World Use Cases

  • NestJS services and controllers — the entire framework is class-based; you inject dependencies through typed constructors.
  • TypeORM / Sequelize entities — each database table is modeled as a class with decorated, typed columns.
  • Domain models in DDD — an Order or Invoice class encapsulates business rules so invalid states are impossible.
  • Custom error types — class NotFoundError extends Error gives you typed, catchable errors with extra fields.
  • State containers — a class-based store wraps mutable state behind controlled methods (older MobX, RxJS subjects).
  • Game / simulation entities — a Player or Enemy bundles position, health, and the methods that update them.

Common Mistakes

Mistake 1 — Forgetting new
typescript
// WRONG — calling a class like a function
const u = User("Ada");      // Error: Value of type 'typeof User' is not callable

// CORRECT
const u = new User("Ada");

A class constructor must be invoked with new; calling it directly throws at runtime and TypeScript flags it at compile time.

Mistake 2 — Confusing the type with the instance
typescript
// WRONG — typeof User is the constructor, not an instance
function printName(u: typeof User) {}  // expects the class itself

// CORRECT — use the class name as the instance type
function printName(u: User) { console.log(u.name); }

User is the instance type; typeof User is the constructor type. Mixing them up is a classic beginner error.

Mistake 3 — Uninitialized fields under strict mode
typescript
// WRONG — strictPropertyInitialization complains
class User { name: string; } // Error: no initializer and not assigned in ctor

// CORRECT — initialize, assign in constructor, or mark optional
class User { name: string = ""; }

With strict enabled, every field needs a clear initialization path or TypeScript can't guarantee it's a string rather than undefined.

Best Practices

1
Use PascalCase for class names

Classes are types and constructors, so the convention (BankAccount, not bankAccount) signals "instantiate me with new".

2
Keep classes focused — one responsibility

A class that handles HTTP, parsing, and caching should be split. Smaller classes are easier to test and reuse.

3
Reach for a type/interface when there's no behavior

If your "class" has only fields and no methods, a plain type or interface is lighter and emits no runtime code.

4
Enable strict in tsconfig

It turns on strictPropertyInitialization and strictNullChecks, catching uninitialized fields and null-safety bugs in class code.

5
Prefer composition over deep inheritance

Favor holding instances of other classes as fields over building tall extends chains, which become brittle.

6
Annotate public method return types

Explicit return types make the class's contract obvious and prevent accidental widening when you refactor the body.

Interview Questions

EasyQ: What is the difference between a class and an object in TypeScript?

A class is a blueprint — it defines the shape and behavior. An object (instance) is a concrete value created from that blueprint with new. One class can produce many independent instances, each with its own field values but sharing the same methods on the prototype.

EasyQ: Does a TypeScript class exist at runtime?

Yes. Unlike interfaces and type aliases, which are erased during compilation, a class emits real JavaScript — a constructor function with a prototype. That's why you can use it with new, instanceof, and reflection at runtime.

MediumQ: What's the difference between User and typeof User as types?

User is the instance type — what you get back from new User(). typeof User is the constructor type — the class object itself, including static members and the new (...) => User signature. You use typeof User when you want to pass the class around as a value, e.g. a factory that takes a class and returns an instance.

MediumQ: Can a class be used as an interface?

Yes — a class declaration also creates a type, so another class can implements MyClass and an object can be annotated with it. TypeScript checks structural compatibility, ignoring private/protected members' implementations but requiring matching public shape. It's usually clearer to define a separate interface, but the capability exists.

HardQ: Why does TypeScript use structural typing for classes instead of nominal typing?

TypeScript checks compatibility by shape, not by name — if two classes have the same public members, instances are interchangeable even with no inheritance relationship. This matches JavaScript's duck-typed nature. The exception: private and protected members are tracked by their declaring class, so two structurally identical classes with private fields are not assignable to each other — a deliberate escape hatch toward nominal behavior.

▶Constructors
Beginner

Simple Explanation

A constructor is the setup routine that runs automatically the moment you create an object. It's like the assembly line that fills a new product with its starting parts — you hand it the raw materials (arguments) and it returns a fully prepared instance.

Technical Explanation

The constructor is a special method invoked once by new. It receives typed arguments and is responsible for initializing the instance's fields via this. TypeScript adds parameter properties — a shorthand where prefixing a constructor parameter with an access modifier (public, private, readonly) automatically declares and assigns the field, eliminating boilerplate.

The Problem Without a Typed Constructor

In JavaScript a constructor accepts anything. Pass the wrong type or forget an argument, and the object is silently half-built — the bug only appears later when something reads the missing field.

javascript
// Plain JS — nothing validates the arguments
class Account {
  constructor(balance) { this.balance = balance; }
}
const a = new Account("100");  // oops, a string
a.balance - 10;                  // "100" - 10 = 90 by luck, or NaN elsewhere

The Solution With TypeScript

typescript
class Account {
  constructor(public balance: number) {}  // parameter property
}
const a = new Account("100");  // ✗ Error: string not assignable to number
const b = new Account(100);    // ✓

When to Use Constructors

  • When an instance needs starting data — pass required values in so the object is valid the instant it exists.
  • When you want to enforce invariants on creation — validate inputs and throw before an invalid object escapes.
  • Use parameter properties when the argument maps directly to a stored field — it removes repetitive this.x = x lines.
  • For dependency injection — frameworks like NestJS and Angular read constructor parameter types to supply dependencies.
  • When defaulting values — give parameters defaults so callers can omit them.

When NOT to Use a Constructor (or Heavy Logic in One)

  • For async setup — constructors can't be async; use a static create() factory that returns a Promise instead.
  • For complex multi-step building — prefer a Builder or a static factory method when construction has many optional steps.
  • When there's no state to initialize — if every field has an initializer, you may not need an explicit constructor at all.
  • Avoid side effects — don't fire network calls or start timers in a constructor; it makes the class hard to test and surprising to instantiate.

How Constructors Work Internally

When you write new Account(100), the runtime: (1) creates a fresh empty object, (2) links it to Account.prototype, (3) runs the constructor body with this bound to that object, and (4) returns the object. Parameter properties are pure TypeScript syntax — the compiler expands them into a field declaration plus an assignment.

typescript
// TypeScript source — parameter property shorthand
class Account {
  constructor(public balance: number) {}
}

// Compiled JavaScript — expanded to field + assignment
class Account {
  constructor(balance) {
    this.balance = balance;  // the compiler generated this line
  }
}

If you don't declare a constructor, TypeScript provides an implicit empty one. In a subclass you must call super(...) before touching this.

Fully Annotated Syntax

typescript
class User {
  readonly id: string;          // declared here, assigned in ctor

  constructor(
    id: string,                  // plain parameter — must assign manually
    public name: string,           // parameter property: declares + assigns this.name
    private email: string,         // parameter property, private field
    role: string = "user"          // default value — caller may omit
  ) {
    this.id = id;                    // manual assignment for the plain parameter
    // this.name and this.email already assigned by the shorthand
  }
}

const u = new User("u1", "Ada", "a@b.com");
console.log(u.name); // "Ada"  (public)
// u.email -> Error: 'email' is private

Mixing plain parameters and parameter properties in the same constructor is allowed. Order doesn't matter to TypeScript, but keep required params before optional/defaulted ones.

Practical Code Example

typescript
// Constructor that validates an invariant before the object exists
class Temperature {
  constructor(public readonly celsius: number) {
    if (celsius < -273.15) {
      throw new Error("Below absolute zero is impossible");
    }
  }

  get fahrenheit(): number {
    return this.celsius * 9 / 5 + 32;
  }
}

const t = new Temperature(25);
console.log(t.fahrenheit); // Output: 77

// const bad = new Temperature(-300); // throws at construction time

Real-World Use Cases

  • Dependency injection — NestJS/Angular read constructor parameter types to wire services automatically.
  • Value objects — a Money or Email class validates input in the constructor so invalid values never exist.
  • Entity hydration — ORMs call constructors (or skip them) to turn DB rows into typed model instances.
  • Configuration objects — a HttpClient takes base URL, headers, and timeout via the constructor.
  • Custom errors — super(message) in a subclass constructor sets the error message while adding typed fields.
  • Immutable records — combine readonly parameter properties to build instances that can't change after creation.

Common Mistakes

Mistake 1 — Using this before super() in a subclass
typescript
// WRONG
class Admin extends User {
  constructor(name: string) {
    this.level = 10;   // Error: 'super' must be called before 'this'
    super(name);
  }
}

// CORRECT
class Admin extends User {
  level = 10;
  constructor(name: string) { super(name); }
}

The base constructor must finish initializing before the subclass touches this.

Mistake 2 — Making the constructor async
typescript
// WRONG — constructors cannot be async / return a Promise
class Db { async constructor() {} } // syntax error

// CORRECT — use a static async factory
class Db {
  private constructor(public conn: string) {}
  static async connect(): Promise<Db> {
    const conn = await openConnection();
    return new Db(conn);
  }
}
Mistake 3 — Double declaring a parameter property
typescript
// WRONG — declares the field twice
class User {
  name: string;
  constructor(public name: string) {} // Error: duplicate
}

// CORRECT — pick ONE: either the field OR the parameter property
class User {
  constructor(public name: string) {}
}

Best Practices

1
Use parameter properties for simple field assignment

constructor(private name: string) is cleaner than declaring the field and assigning it separately.

2
Validate invariants in the constructor and throw early

Reject impossible state at creation so the rest of your code can trust the instance is valid.

3
Keep constructors free of side effects

No network calls, no timers. A constructor should set up state, not start doing work — that keeps instantiation predictable and testable.

4
Use a static factory for async or complex creation

Since constructors can't be async, expose static async create() when setup requires awaiting something.

5
Order parameters: required first, defaulted last

Defaulted and optional parameters must follow required ones so callers can omit them naturally.

6
Combine readonly with parameter properties for immutable inputs

constructor(public readonly id: string) guarantees the field can't be reassigned after construction.

Interview Questions

EasyQ: What is a parameter property in TypeScript?

It's a shorthand where adding an access modifier (public, private, protected, or readonly) to a constructor parameter automatically declares a class field and assigns the argument to it. So constructor(private name: string) replaces a separate field declaration plus this.name = name.

EasyQ: Can a class have more than one constructor?

No — TypeScript classes have a single implementation constructor. You can declare multiple constructor overload signatures for typing purposes, but there must be exactly one implementation body that handles all cases. For multiple creation paths, use static factory methods instead.

MediumQ: Why can't a constructor be async?

Because new must synchronously return the constructed instance, not a Promise. An async constructor would return a Promise, breaking the contract. The standard workaround is a private constructor plus a static async create() method that awaits setup and returns the finished instance.

MediumQ: When must you call super() and what happens if you don't?

In a subclass that declares its own constructor, you must call super(...) before accessing this or returning. It runs the parent constructor so inherited fields are initialized. Omitting it (when extending a class) is a compile-time error; accessing this before it is also an error.

HardQ: What's the order of field initialization relative to the constructor body?

For a base class: field initializers run first (in declaration order) as if at the top of the constructor, then the constructor body executes. For a subclass: super() runs first (initializing parent fields), then the subclass's own field initializers run, then the rest of the subclass constructor body. This is why a subclass field initializer can't observe values the parent constructor expected to set via a virtual method call — a subtle source of bugs.

▶Methods
Intermediate

Simple Explanation

A method is a function that lives inside a class and can act on that object's own data. If the class is a microwave, the methods are its buttons — "start", "stop", "addThirtySeconds" — each one does something using the microwave's current state.

Technical Explanation

A method is a function defined as a member of a class. It has typed parameters and a typed return value, and inside its body this refers to the instance it was called on, giving access to that instance's fields and other methods. Methods are stored once on the class prototype and shared by all instances, unlike arrow-function fields which are created per instance.

The Problem Without Typed Methods

Free-floating functions that take an object as their first argument force callers to remember which function pairs with which data, and nothing checks that you passed the right shape. Methods bind behavior to the data and let TypeScript verify both the arguments and the return value.

javascript
// Loose functions — no link between data and behavior
function deposit(account, amount) { account.balance += amount; }
deposit({ blance: 0 }, "50"); // typo + wrong type, silently wrong

The Solution With a Method

typescript
class Account {
  balance = 0;
  deposit(amount: number): void {
    this.balance += amount;   // 'this' is the account, fully typed
  }
}
new Account().deposit("50"); // ✗ Error: string not assignable to number

When to Use Methods

  • When behavior depends on instance state — a method reads/updates this, which a standalone function can't do cleanly.
  • When the operation conceptually belongs to the object — order.cancel() reads better than cancelOrder(order).
  • When you want polymorphism — subclasses can override a method to change behavior while keeping the same call site.
  • When exposing a controlled API — methods are the public surface that guards private fields.
  • Use method overloads when one method legitimately accepts several distinct argument shapes with different return types.

When NOT to Use Methods

  • For pure, stateless logic — if a function doesn't touch this, a standalone utility function is more reusable and tree-shakeable.
  • When you'll detach the method from its instance — passing obj.method as a callback loses this; either bind it, use an arrow field, or pass () => obj.method().
  • Avoid arrow-function fields for everything — they create a new function per instance (memory cost) and can't be overridden via the prototype.
  • Don't overload when a union parameter is clearer — overloads add complexity; reach for them only when return types differ by input.

How Methods Work Internally

A normal method is defined once on ClassName.prototype. Every instance shares that single function; when you call instance.method(), JavaScript sets this to instance for that call. This is why detaching a method (const f = obj.method) loses the binding — this is decided at call time, not definition time.

typescript
// Prototype method — shared by all instances
class Greeter {
  greeting = "Hi";
  greet() { return this.greeting; } // on Greeter.prototype
}

// Arrow-function field — one copy per instance, 'this' bound at creation
class Greeter2 {
  greeting = "Hi";
  greet = () => this.greeting; // own property of each instance
}

TypeScript also supports a special this parameter — a fake first parameter named this — to constrain what context a method may be called in. It's erased at compile time.

Fully Annotated Syntax

typescript
class Calculator {
  add(a: number, b: number): number {
//   ^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^ return type
//   |    typed parameters
//   method name
    return a + b;
  }

  // Method OVERLOADS — multiple signatures, one implementation
  format(value: number): string;
  format(value: Date): string;
  format(value: number | Date): string {  // implementation signature
    return typeof value === "number"
      ? value.toFixed(2)
      : value.toISOString();
  }

  // 'this' parameter — restricts valid call context, erased at runtime
  describe(this: Calculator): string {
    return "a calculator";
  }
}

Overload signatures have no body and are not callable themselves; only the final implementation signature runs. The implementation signature must be compatible with every overload but is hidden from callers.

Practical Code Example

typescript
// Fluent (chainable) methods by returning 'this'
class QueryBuilder {
  private parts: string[] = [];

  select(cols: string): this {
    this.parts.push(`SELECT ${cols}`);
    return this;          // enables chaining
  }
  from(table: string): this {
    this.parts.push(`FROM ${table}`);
    return this;
  }
  where(cond: string): this {
    this.parts.push(`WHERE ${cond}`);
    return this;
  }
  build(): string {
    return this.parts.join(" ") + ";";
  }
}

const sql = new QueryBuilder()
  .select("id, name")
  .from("users")
  .where("age > 18")
  .build();
console.log(sql); // Output: SELECT id, name FROM users WHERE age > 18;

Real-World Example

typescript
// A domain model where methods enforce business rules
type OrderStatus = "pending" | "paid" | "shipped" | "cancelled";

class Order {
  private status: OrderStatus = "pending";
  constructor(public readonly id: string, private total: number) {}

  pay(): void {
    if (this.status !== "pending")
      throw new Error(`Cannot pay an order that is ${this.status}`);
    this.status = "paid";
  }

  ship(): void {
    if (this.status !== "paid")
      throw new Error("Only paid orders can ship");
    this.status = "shipped";
  }

  cancel(): void {
    if (this.status === "shipped")
      throw new Error("Shipped orders cannot be cancelled");
    this.status = "cancelled";
  }

  getStatus(): OrderStatus { return this.status; }
}

const o = new Order("ord_1", 99);
o.pay();
o.ship();
console.log(o.getStatus()); // "shipped"

Real-World Use Cases

  • Fluent builders — query builders (Knex), validation chains, and config builders return this for chaining.
  • State machines — methods like order.pay() guard valid transitions and throw on illegal ones.
  • Service layers — NestJS service methods encapsulate business logic and are unit-tested in isolation.
  • Custom collections — a typed Stack<T> exposes push/pop/peek methods over private storage.
  • React class components (legacy) — lifecycle methods (componentDidMount) and event handlers were methods.
  • Method overloads in SDKs — a query() that returns different types based on whether you pass a string or an options object.

Common Mistakes

Mistake 1 — Losing this when passing a method as a callback
typescript
// WRONG — 'this' is undefined when called by setTimeout

// CORRECT — preserve the binding
setTimeout(() => counter.increment(), 1000);
// or define increment as an arrow field, or use .bind(counter)

this is bound at call time. Detaching a method drops the link to its instance.

Mistake 2 — Calling an overload's implementation signature directly
typescript
// The implementation signature is NOT visible to callers
format(v: number): string;
format(v: number | Date): string { /*...*/ }

obj.format(true); // ✗ Error: no overload matches boolean — even though impl is wider

Only the listed overload signatures are callable; the implementation signature is internal.

Mistake 3 — Forgetting the return type, getting unexpected widening
typescript
// WRONG — inferred return is string, refactor could break callers silently
getRole() { return "admin"; }

// CORRECT — explicit contract
getRole(): "admin" | "user" { return "admin"; }

Best Practices

1
Annotate return types on public methods

It documents the contract and prevents silent type changes when you edit the body later.

2
Use prototype methods by default; arrow fields only when you need bound this

Prototype methods are memory-efficient and overridable; reserve arrow fields for callbacks that get detached.

3
Return this for fluent APIs

Using the return type this (not the class name) keeps chaining correct across subclasses.

4
Keep methods small and single-purpose

A method that does one thing is easier to test, name, and override.

5
Use overloads only when return type depends on input type

If a union parameter and a single return type express it cleanly, prefer that over overloads.

6
Use a this parameter to guard call context

When a method must only be called on a specific type, declare method(this: MyClass) to catch misuse at compile time.

Interview Questions

EasyQ: What does this refer to inside a class method?

It refers to the instance the method was called on. account.deposit(10) sets this to account for that call, giving the method access to that instance's fields and other methods.

MediumQ: What's the difference between a prototype method and an arrow-function class field?

A prototype method is defined once on the class prototype and shared by all instances; its this is determined at call time. An arrow-function field is created per instance and captures this lexically at construction, so it stays bound even when detached. Arrow fields cost more memory and can't be overridden through the prototype, but they're convenient as event handlers.

MediumQ: How do method overloads work in TypeScript?

You declare multiple bodiless signatures followed by one implementation signature with a body. Callers see only the overload signatures; the implementation must be compatible with all of them but isn't directly callable. Inside the body you narrow the union (e.g. with typeof) to handle each case.

MediumQ: What is a this parameter and when is it useful?

It's a special fake first parameter named this that types the expected context without being a real argument. It's useful for callback-style functions or to ensure a method is only called on instances of a certain type — TypeScript errors if this would be the wrong type. It's erased at compile time.

HardQ: Why does returning this (the type) differ from returning the class name in a fluent API?

Returning the literal type this is polymorphic — in a subclass, the method's return type becomes the subclass, preserving the chain's specific type. Returning the concrete class name would downcast to the base class, so chained calls on a subclass would lose access to subclass methods. this types keep fluent builders correct under inheritance.

▶Properties
Intermediate

Simple Explanation

Properties are the labeled compartments inside an object that hold its data. If a class is a form, the properties are the fields on it — name, age, email — each one typed so you can't accidentally write a number where text belongs.

Technical Explanation

A property (or field) is a typed data member declared in the class body. It can have an initializer, be marked optional (?), readonly, or use definite-assignment (!) when initialized outside the constructor. TypeScript also supports accessors — get/set pairs that look like properties from the outside but run code, letting you compute or validate on read/write.

The Problem Without Typed Properties

In plain JavaScript objects accrete properties dynamically — a typo creates a brand-new field instead of an error, and reading a never-set property returns undefined with no warning.

javascript
class Profile {}
const p = new Profile();
p.usernmae = "ada";   // typo silently creates a junk property
console.log(p.username); // undefined — bug ships to production

The Solution With Declared Properties

typescript
class Profile {
  username: string = "";
}
const p = new Profile();
p.usernmae = "ada";   // ✗ Error: 'usernmae' does not exist on Profile
p.username = "ada";   // ✓

When to Use Properties (and Their Variants)

  • Plain fields — for any mutable instance data the object owns.
  • readonly — for values set once at construction that must never change (IDs, config).
  • Optional (?) — for data that legitimately may be absent (a middleName).
  • Definite assignment (!) — when a framework or lifecycle hook assigns the field after construction (Angular @Input, dependency injection).
  • Getters/setters — when reading or writing should compute a value or validate input rather than just store it.

When NOT to Use Certain Property Features

  • Don't overuse ! definite assignment — it silences the compiler's safety check; only use it when you truly guarantee initialization elsewhere.
  • Don't add a getter/setter that does nothing — a pass-through accessor over a public field is pure boilerplate; just expose the field.
  • Avoid heavy logic in getters — getters look like cheap property reads; doing expensive work in them surprises callers. Use a method named compute...() instead.
  • Don't mark a field readonly if it legitimately changes — that just forces ugly workarounds.

How Properties Work Internally

Plain fields and readonly become normal own properties on the instance at runtime — readonly is a compile-time-only guard with no runtime enforcement. Optional (?) and definite-assignment (!) are also purely type-level; the emitted JavaScript is identical. Accessors compile to real Object.defineProperty getter/setter descriptors on the prototype.

typescript
// TypeScript source
class Box {
  readonly id = "x1";
  get label() { return `Box ${this.id}`; }
}

// Compiled JS — readonly erased; getter becomes a real accessor
class Box {
  id = "x1";             // nothing stops reassignment at runtime
  get label() { return `Box ${this.id}`; }
}

Because readonly is erased, it protects you in your typed code but not against untyped JavaScript at runtime — use #private fields or Object.freeze if you need true runtime immutability.

Fully Annotated Syntax

typescript
class Account {
  balance: number = 0;         // field with initializer
  readonly id: string;            // readonly: assign once (in ctor)
  nickname?: string;              // optional: may be undefined
  loadedUser!: string;            // '!' definite assignment: "trust me, set later"

  constructor(id: string) {
    this.id = id;                  // only place readonly can be set
  }

  // Getter: looks like a property read, runs code
  get isOverdrawn(): boolean {
    return this.balance < 0;
  }

  // Setter: validates on assignment
  set deposit(amount: number) {
    if (amount < 0) throw new Error("No negative deposits");
    this.balance += amount;
  }
}

const a = new Account("acc_1");
a.deposit = 100;        // calls the setter
console.log(a.isOverdrawn); // false — calls the getter (no parens)
// a.id = "other";        // ✗ Error: id is readonly

Getters and setters are accessed without parentheses, exactly like fields. A property with only a getter is effectively read-only from outside.

Real-World Use Cases

  • Entity IDs — readonly id guarantees a database key can't be reassigned after the entity is created.
  • Computed view data — a getter like fullName derives from firstName + lastName without storing a stale copy.
  • Validation on write — setters reject bad input (negative prices, out-of-range values) at the point of assignment.
  • Angular component inputs — @Input() data!: Data uses definite assignment because the framework sets it after construction.
  • Config objects — optional properties model settings that may or may not be provided by the user.
  • Encapsulated state — a private backing field plus a public getter exposes data read-only while keeping writes internal.

Common Mistakes

Mistake 1 — Calling a getter like a method

Mistake 2 — Overusing definite assignment !

Mistake 3 — Expecting readonly to protect at runtime

Best Practices

1
Mark fields readonly when they shouldn't change after construction

It documents intent and catches accidental reassignment in typed code (IDs, injected dependencies).

2
Initialize fields with sensible defaults

An initializer satisfies strictPropertyInitialization and means callers don't have to set everything.

3
Use getters for derived values, not stored duplicates

Computing fullName on read avoids stale data that a stored copy would suffer from.

4
Validate in setters, keep getters cheap

Setters are the right place for write-time checks; getters should be fast since callers treat them like field reads.

5
Reserve ! for framework-assigned fields only

Definite assignment is a promise to the compiler — use it where a lifecycle hook or DI truly assigns the value.

6
Use a private backing field with a public getter for read-only exposure

It lets external code read state while keeping all writes funneled through controlled methods.

Interview Questions

EasyQ: What's the difference between a property with a getter and a regular method?

A getter is accessed like a field — obj.area, no parentheses — and is meant to feel like reading data. A method is called with parentheses — obj.computeArea(). Use a getter for cheap, side-effect-free derived values; use a method when work is involved or it takes arguments.

EasyQ: What does the ! definite assignment assertion do?

It tells TypeScript "this field will be assigned before it's used, even though I'm not initializing it here or in the constructor," suppressing the strict-property-initialization error. It's a promise you make to the compiler — if the field is actually never set, you'll get a runtime undefined with no warning.

MediumQ: Is readonly enforced at runtime?

No. readonly is a compile-time-only modifier; it's erased in the emitted JavaScript. It prevents reassignment in type-checked code but offers no protection against untyped JS or a cast to any. For real runtime immutability use #private fields, Object.freeze, or closures.

MediumQ: What's the difference between an optional property (?) and one typed | undefined?

An optional property name?: string can be entirely omitted from an object literal and its type is string | undefined. A required property typed name: string | undefined must be present — you have to explicitly set it to undefined. With exactOptionalPropertyTypes the distinction tightens further: optional means "may be absent," not "may be present-but-undefined."

HardQ: How do TypeScript readonly fields and JavaScript #private fields differ?

readonly is a TypeScript-only, compile-time restriction on reassignment — the field is still publicly readable and is erased at runtime. #private is a real ECMAScript feature: the field is genuinely inaccessible outside the class at runtime (accessing it throws), enforced by the JS engine. They solve different problems: readonly prevents writes; #private prevents external access entirely. You can even combine concepts — a #private backing field exposed through a public getter.
