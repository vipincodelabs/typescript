Interfaces Beginner ▶

Simple Explanation

An interface is a contract that says "any object claiming to be this type must have exactly these properties with exactly these types." Think of it like a form — if a function expects a User interface, you must fill out all the required fields before passing it in.

Technical Explanation

An interface in TypeScript defines the structural shape of an object type at compile time. It specifies property names, their types, optionality (?), and mutability (readonly). TypeScript uses structural typing (duck typing), meaning any object that satisfies an interface's shape is considered to implement it — no explicit declaration needed. Interfaces exist only at compile time and are completely erased from the compiled JavaScript output.

The Problem Without Interfaces

In JavaScript, you can pass any object to any function. There's no way to know at a glance what shape an object must have, and mistakes only surface at runtime — often in production.

javascript
// JavaScript — no protection
function displayUser(user) {
  return `Hello, ${user.name}!`; // crashes if user has no `name`
}

displayUser({ username: 'alice' }); // Output: "Hello, undefined!" — silent bug

The Fix With Interfaces

Interfaces catch shape mismatches at compile time, before you ever run the code. The TypeScript compiler reads your interface, checks every usage site, and shows an error if the object is missing required fields or has the wrong types.

typescript
interface User {
  name: string;
  email: string;
}

function displayUser(user: User): string {
  return `Hello, ${user.name}!`;
}

displayUser({ username: 'alice' });
// TS ERROR: Object literal may only specify known properties,
// and 'username' does not exist in type 'User'.
// Did you mean to write 'name'?

The compiler caught the typo (username instead of name) before the code ran. This is the core value of interfaces: errors at build time, not at runtime.

Use interfaces when…

  • Typing API request/response objects — interfaces precisely model JSON shapes coming from a REST API or GraphQL endpoint.
  • Defining data models — User, Product, Order entities that map to database rows or domain objects benefit from the clarity of an interface.
  • Typing function parameters that are objects — rather than listing five separate parameters, accept one typed object so callers get autocomplete and typo protection.
  • When you want declaration merging — augmenting third-party library types (Express Request, global Window) requires interfaces, not type aliases.
  • When a class will implement the contract — class UserService implements IUserService is idiomatic and makes the contract explicit.
  • When other developers will consume your types — interfaces produce cleaner error messages and are the idiomatic TypeScript choice for public APIs.

Don't reach for interface when…

  • You need a union type. Interfaces cannot represent string | number — use type instead.
  • You need a tuple or primitive alias. interface only works for object shapes. type Point = [number, number] or type ID = string require type.
  • You need computed/mapped types. type Readonly<T> or mapped types like { [K in keyof T]: boolean } require type, not interface.
  • You need conditional types. type IsString<T> = T extends string ? true : false — interfaces can't do this at all.
  • The shape is one-off and internal. For a tiny local object used once, an inline type annotation ({ id: number; name: string }) is cleaner than a named interface you'll never reuse.

Compile-Time Only

Interfaces are a purely compile-time construct. When TypeScript compiles your code to JavaScript, every interface is completely removed. There is no interface keyword in the output, no runtime object, no prototype — nothing. This means interfaces have zero runtime cost.

Structural Typing

TypeScript checks interfaces using structural typing: it compares the shape of the object against the interface, property by property. An object doesn't need to explicitly say implements User — if it has all the required properties with the correct types, TypeScript accepts it.

typescript
interface Greetable {
  name: string;
}

function greet(g: Greetable) { return `Hi ${g.name}`; }

const cat = { name: 'Whiskers', lives: 9 };
greet(cat); // OK — cat has `name`, extra `lives` is allowed

What Gets Erased

interface Point { x: number; y: number; }
const p: Point = { x: 10, y: 20 };
javascript (output)
// interface Point is completely gone
const p = { x: 10, y: 20 };
typescript
interface Product {
// ^^^^^^^^^  keyword that starts an interface declaration
//           ^^^^^^^  name (PascalCase by convention)

  id: number;
// ^^  property name
//    ^^^^^^  type annotation — this property MUST be a number

  name: string;        // required string property

  price: number;       // required number property

  description?: string;
//           ^  the `?` makes this property OPTIONAL
//              callers may omit it; its type is string | undefined

  readonly createdAt: Date;
// ^^^^^^^^  cannot be reassigned after the object is created
//           attempting to write `product.createdAt = x` is a TS error

  tags: string[];     // array type — array of strings

  metadata: {          // nested inline object type
    sku: string;
    weight: number;
  };
}

1. Prefixing interface names with "I"

typescript
// BAD — Hungarian notation, not idiomatic TypeScript
interface IUser { name: string; }

// GOOD — plain PascalCase
interface User { name: string; }

The TypeScript team and community style guides (Airbnb, Google) explicitly recommend against the I prefix. It's legacy C# convention; TypeScript has better tooling to distinguish types from values.

2. Using interface for non-object types

typescript
// BAD — interface can't represent a union
interface Status = 'active' | 'inactive'; // SYNTAX ERROR

// GOOD — use type for unions, primitives, tuples
type Status = 'active' | 'inactive';

3. Forgetting optional marker on nullable fields

typescript
// BAD — bio is required but might not exist in real data
interface User {
  name: string;
  bio: string; // callers MUST provide this — unexpected
}

// GOOD — mark genuinely optional fields
interface User {
  name: string;
  bio?: string; // callers can omit it; type is string | undefined
}

4. Defining method signatures with wrong syntax

typescript
// Confusing but valid — two ways to type a method in an interface
interface Formatter {
  format(s: string): string;         // method shorthand (preferred)
  format: (s: string) => string;    // property with function type
}
// They're almost equivalent, but method shorthand is more readable.
// Stick to method shorthand for interface method signatures.
  1. Use PascalCase for interface names. User, ProductResponse, CartItem — consistent with classes and TypeScript's own built-in types.
  2. Mark fields readonly if they shouldn't change after creation. IDs, timestamps, and slugs are natural candidates. This prevents accidental mutation and makes intent clear: readonly id: string.
  3. Prefer interface over inline object types for reusable shapes. If you write the same object shape in two places, extract it to a named interface. It's easier to document, refactor, and reuse.
  4. Keep interfaces focused. An interface for "a user" shouldn't also carry "the user's shopping cart." Split by concern, then compose with extension or intersection.
  5. Use optional ? honestly. Don't mark a field optional just to avoid specifying it — optional means callers can legitimately omit it. If a field is always present, keep it required.
  6. Export interfaces from a central types.ts module. Shared types that cross module boundaries should live in one place, not scattered across implementation files.
  7. Separate request and response interfaces. CreateUserRequest ≠ UserResponse. The input shape rarely equals the output shape (IDs and timestamps are server-generated).
Q: What is an interface in TypeScript, and how is it different from a plain JavaScript object?Easy
An interface is a compile-time contract that defines the required shape of an object. Unlike a plain JavaScript object, an interface exists only in TypeScript source code — it's completely erased when compiled to JavaScript. Its job is to let the type checker verify that any object assigned to that type actually has the right properties and types, catching mistakes before the code runs.
Q: What does "structural typing" mean, and how does it relate to interfaces?Medium
Structural typing means TypeScript checks compatibility based on shape (the properties and their types), not on explicit inheritance or declaration. An object satisfies an interface simply by having the right properties — it doesn't need to say implements User. This is in contrast to nominal typing (C#, Java) where you must explicitly declare a class to implement an interface. In TypeScript: if it looks like a User, it is a User.
Q: What's the difference between an optional property (?) and a property typed as string | undefined?Medium
They're almost the same but have a subtle distinction. bio?: string means the key can be completely absent from the object. bio: string | undefined means the key must be present, but its value can be undefined. In practice, when using exactOptionalPropertyTypes in your tsconfig, TypeScript enforces this distinction strictly — { bio: undefined } would not satisfy bio?: string.
Q: Can a class implement multiple interfaces? How?Easy
Yes. A class can implement multiple interfaces by separating them with commas: class PayPalService implements PaymentService, Loggable. The class must provide all properties and methods defined in every interface it implements, or TypeScript will report an error.
Q: If interfaces are erased at compile time, why use them instead of just writing code and hoping for the best?Hard
Interfaces let the TypeScript compiler verify correctness across the entire codebase without any runtime overhead. When a function expects a CreateOrderRequest interface, the compiler checks every call site — if an API shape changes and a caller doesn't update, it's a compile error, not a 3am production incident. The value isn't runtime enforcement; it's the confidence that refactoring one file doesn't silently break five others.

Interface Extension Beginner ▶

Simple Explanation

Interface extension is like inheritance for object shapes. You take an existing interface and say "I want everything in that one, plus these extra properties." The child interface automatically has all of the parent's properties without you having to copy them.

Technical Explanation

Using the extends keyword, a child interface inherits all members of one or more parent interfaces and can add new members or (with compatible types) override them. The resulting type is the union of all inherited properties plus the new ones. An interface can extend multiple interfaces simultaneously by separating them with commas: interface C extends A, B.

The Problem Without Extension

Without extension, you'd copy fields across every interface that shares a common base, leading to duplication that drifts out of sync over time.

typescript
// Without extension — id/createdAt/updatedAt duplicated everywhere
interface User {
  id: string;
  createdAt: Date;
  updatedAt: Date;
  name: string;
  email: string;
}
interface Product {
  id: string;            // copy-pasted
  createdAt: Date;       // copy-pasted
  updatedAt: Date;       // copy-pasted
  name: string;
  price: number;
}
// If you add `deletedAt` to the base, you must update every interface manually

Fix With Extension

typescript
interface BaseEntity {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

interface User extends BaseEntity {
  name: string;
  email: string;
}

interface Product extends BaseEntity {
  name: string;
  price: number;
}
// Adding `deletedAt` to BaseEntity automatically updates both User and Product
  • Building layered data models — BaseEntity → TimestampedEntity → SoftDeletableEntity → User: each layer adds a concern without duplicating earlier ones.
  • Specializing a general interface — Animal → Dog, Vehicle → Car → ElectricCar: when a specific type is a strict superset of the general type.
  • Extending third-party types — Add custom fields to a library's interface without modifying its source (though for third-party, declaration merging is more idiomatic — see next topic).
  • Separating concerns — interface Timestamped, interface SoftDeletable, interface Auditable; then interface Order extends Timestamped, SoftDeletable, Auditable.
  • When implementing classes — If both an AdminUser class and a RegularUser class should implement the base User interface, extending avoids duplicate method signatures.
  • When the relationship is compositional, not hierarchical. If Order has a User (not IS a user), use a property, not extension: interface Order { customer: User; }
  • When you need to override a property with an incompatible type. You can narrow a type (string → 'active' | 'inactive') but can't widen it (string → string | number). TypeScript will error. Use intersection types or a new separate interface instead.
  • When combining unrelated shapes. If you're merging two completely unrelated interfaces, an intersection type (type AB = A & B) expresses the intent more clearly than forced extension.
  • For deeply nested hierarchies. More than 2–3 levels of extension makes the type system hard to follow. Prefer composition (nested interface properties) over deep inheritance chains.

How TypeScript Resolves Extended Interfaces

When you write interface Child extends Parent, TypeScript creates a new type that contains all of Parent's members plus Child's own members. This resolution happens entirely at compile time — the compiler flattens the inheritance chain when checking types.

Property conflict rules: If Child redeclares a property from Parent with the same name, the Child type must be assignable to the Parent type (i.e., a narrower or equal type). You can restrict string to 'admin' | 'user', but you cannot change string to number.

typescript
interface Animal {
  name: string;
  sound(): string;
}

interface Dog extends Animal {
  breed: string;
}

// TypeScript sees Dog as equivalent to:
// { name: string; sound(): string; breed: string; }

const rex: Dog = {
  name: 'Rex',
  breed: 'Labrador',
  sound() { return 'Woof'; },
};

Multi-inheritance: interface C extends A, B — TypeScript merges all members from A and B into C. If A and B both declare the same property with incompatible types, it's a compile error.

typescript
// Single extension
interface Child extends Parent {
//         ^^^^^  new interface name
//                ^^^^^^^ keyword
//                        ^^^^^^  parent interface
  extraProp: string;  // new properties added by Child
}

// Multiple extension — merge A and B into C
interface C extends A, B {
//                   ^  ^  comma-separated parent interfaces
  ownProp: number;
}

// Narrowing a parent property (valid)
interface AdminUser extends User {
  role: 'admin';    // narrows User's role: string to the literal 'admin'
}

// Attempting to widen a parent property (ERROR)
interface BadChild extends Parent {
  name: number; // ERROR: Property 'name' in type 'BadChild' is not assignable
                // to the same property in base type 'Parent'.
}

1. Trying to widen a property type

typescript
interface Base { id: string; }

// WRONG — can't change id from string to number
interface Child extends Base {
  id: number; // ERROR: number is not assignable to string
}

// If you genuinely need a different type, create a new interface
interface ChildWithNumericId {
  id: number;
  // copy the other Base properties manually or use intersection
}

2. Confusing extension with interface merging

typescript
// These are DIFFERENT things:

// EXTENSION — Child is a new interface that inherits from Parent
interface Child extends Parent { extra: string; }

// MERGING — both declarations combine into one interface named Parent
interface Parent { extra: string; }

Extension creates a new named type; declaration merging modifies the original interface. Mixing them up leads to accidentally augmenting a type you meant to specialize.

3. Forgetting that multi-extend conflicts cause errors

typescript
interface A { value: string; }
interface B { value: number; }

// WRONG — 'value' can't be both string and number
interface C extends A, B { } // ERROR: Named property 'value' of types 'A' and 'B' are not identical

// CORRECT — rename one of the conflicting properties
interface C extends A { numericValue: number; }
  1. Create a BaseEntity interface for database tables. Put id, createdAt, updatedAt there once. Every entity interface extends it. Add deletedAt once and everything inherits it.
  2. Keep inheritance shallow (max 3 levels). Deep hierarchies become hard to reason about. If you need more than 3 levels, reconsider whether composition (nested properties) wouldn't be clearer.
  3. Use multiple extension for orthogonal concerns. interface Order extends Timestamped, SoftDeletable is cleaner than a single fat base that tries to do everything.
  4. Prefer extends over copy-paste. If you notice two interfaces share three or more properties, extract a base interface and have both extend it.
  5. Name base interfaces by their concern, not by who uses them. Timestamped and SoftDeletable are better than BaseModel, because the name tells you exactly what they contribute.
Q: What does the extends keyword do in an interface declaration?Easy
It makes the new interface inherit all properties and method signatures from the parent interface(s). The resulting type contains all members from every parent plus any new members defined in the child. An object assigned to the child type must satisfy every property requirement from all parents.
Q: Can an interface extend multiple interfaces at once? Show the syntax.Easy
Yes. interface Order extends Timestamped, SoftDeletable, Auditable { ... } — list parent interfaces separated by commas after the extends keyword. The resulting interface inherits all members from every parent. If two parents declare the same property with incompatible types, TypeScript reports an error.
Q: Can you override a parent interface property in the child? What are the rules?Medium
You can re-declare a property in the child only if the child's type is assignable to (i.e., a subtype of) the parent's type. You can narrow string to 'admin' | 'user', but you cannot change string to number. This preserves substitutability: anything that accepts the parent interface must also be able to handle the child.
Q: What is the difference between interface extension and type intersection?Medium
Both combine types, but they behave differently with conflicts. Interface extension errors at declaration time if two parents have the same property with incompatible types. Type intersection (type C = A & B) silently creates a never-typed property when types conflict, which can cause subtle bugs. Interface extension also creates a named, re-openable type; intersections are aliases and cannot be merged.
Q: How does interface extension relate to the Liskov Substitution Principle?Hard
Interface extension enforces LSP structurally: since the child type must be assignable to the parent, any function expecting the parent interface will also accept the child. TypeScript enforces this by requiring that re-declared properties in the child are subtypes of the parent's version. This means you can safely use a child interface wherever a parent is expected, which is the core guarantee of LSP.

Declaration Merging Intermediate ▶

Simple Explanation

If you write two interfaces with the same name in TypeScript, they don't conflict — TypeScript automatically combines them into a single interface that has all the properties from both. It's as if you wrote one big interface from the start.

Technical Explanation

Declaration merging is the TypeScript compiler's behavior of combining multiple declarations sharing the same identifier into a single definition. It applies to interfaces (and namespaces, but not type aliases or classes). When two interface declarations with the same name exist in the same scope, their members are merged. Later declarations of the same property must be compatible; method signatures stack into an overloaded function type, with later declarations having higher priority in resolution.

The Problem It Solves

TypeScript was designed to work alongside existing JavaScript and third-party libraries. Those libraries expose types in their own declaration files (.d.ts). Without declaration merging, users would have no way to extend those types without modifying the library's source — which isn't an option for node_modules packages.

Consider Express: its Request type doesn't know about your JWT-authenticated user. Declaration merging lets you add a user property to Express's Request interface in your own project without touching Express's code.

typescript
// express.d.ts (inside node_modules) — you can't edit this
interface Request {
  body: any;
  params: Record<string, string>;
}

// Your project's custom.d.ts — merges with Express's declaration
declare namespace Express {
  interface Request {
    user?: AuthenticatedUser; // added by your JWT middleware
  }
}
// Now req.user is typed everywhere — no 'any' needed
  • Augmenting Express's Request or Response — Add custom properties like user, tenant, or requestId that your middleware attaches.
  • Extending the global Window object — Add browser globals your script adds: window.analytics, window.gtag.
  • Augmenting module types — Add missing properties to a poorly-typed third-party package via module augmentation.
  • Incrementally building large interface definitions — Spread interface members across multiple files that logically own different concerns (rare in application code, but common in library code).
  • Environment-specific additions — Different parts of your codebase add to ProcessEnv to type their specific environment variables.
  • For regular application code. Splitting one logical interface across multiple declarations in your own codebase is confusing. Use extends or just define it in one place.
  • When you mean to extend, not merge. If you want a new type that builds on an existing one, use extends. Merging modifies the original interface for everyone — that's usually not what you want in application code.
  • When using type aliases. type aliases cannot be merged. If you try to re-declare a type, TypeScript errors with "Duplicate identifier."
  • When the property is already defined with a conflicting type. You cannot use merging to change an existing property's type — only to add new ones.

How the Compiler Merges

When the TypeScript compiler encounters two interface declarations with the same name in the same scope, it treats them as one combined declaration. The merged interface has the union of all properties from both declarations. Rules:

  1. Non-function members: Must be the same type in all declarations. If one says name: string and another says name: number, it's an error.
  2. Function members (method signatures): Stack into overloads. Later declarations appear first in the overload list (higher priority in resolution). This lets you add specialized overloads in your augmentation file.
  3. Order matters for methods: The last-declared interface's signatures resolve first — useful when you want a more specific signature to win.

Q: What is declaration merging in TypeScript?Easy
When two or more interface declarations in TypeScript share the same name in the same scope, the compiler automatically combines them into a single interface containing all members from every declaration. This is called declaration merging. It works for interfaces (and namespaces) but not for type aliases.
Q: Why can't you use declaration merging with type aliases?Medium
Type aliases are opaque references — they create a new name for an existing type and cannot be re-opened after declaration. Attempting to re-declare a type alias with the same name is a "Duplicate identifier" error. Interfaces, by design, are open-ended and meant to be augmented, which is why only they support merging.
Q: How do you augment a third-party module's types using declaration merging?Medium
Use module augmentation: create a .d.ts file with import (to make it a module) and a declare module 'package-name' block containing the augmented interface. For global augmentation (like extending Window or ProcessEnv), use declare global { ... }. The file must be included in your TypeScript compilation for the augmentation to take effect.
Q: What happens when two merged interface declarations both define the same method signature?Hard
Method signatures (functions) stack into overloads. The declaration that appears later in the file (or in a file loaded later) takes precedence — its signature is placed first in the overload list. This is intentional: augmentations added after the original declaration are treated as more specific and get tried first during overload resolution.
Q: Give a concrete example where declaration merging is the only practical solution.Hard
Express's Request type doesn't know about your authentication middleware's user property. You can't modify Express's source or its declaration files in node_modules. Declaration merging via declare global { namespace Express { interface Request { user?: User } } } is the only way to add a typed req.user everywhere in your app without casting to any.

Interface vs Type Intermediate ▶

Simple Explanation

Both interface and type let you give a name to a shape or a type. Think of interface as a specialist for object shapes, and type as a generalist that can describe anything — unions, primitives, tuples, computed types — but with fewer object-shape superpowers.

Technical Explanation

An interface declaration creates a named object type that supports extends for structural inheritance and declaration merging for augmentation. A type alias assigns a name to any TypeScript type expression — including primitives, union types (A | B), intersection types (A & B), tuples, mapped types, conditional types, and template literal types. Type aliases cannot be re-opened after declaration; interfaces can. Both are fully erased from compiled JavaScript.

Why Both Exist

interface predates type aliases in TypeScript. It was the original way to describe object shapes and class contracts. As TypeScript grew more expressive, type aliases were added to handle the complex type manipulations (unions, mapped types, conditional types) that interfaces couldn't express. Today they overlap significantly for object shapes, which is the source of the "interface or type?" confusion.

typescript
// These two are functionally equivalent for object shapes:
interface UserI { name: string; age: number; }
type UserT = { name: string; age: number; };

// But only type can do these:
type ID = string | number;        // union
type Pair = [string, number];      // tuple
type Callback = () => void;       // function alias
type Keys = keyof UserT;           // computed type

// And only interface can do this:
interface UserI { premium: boolean; }  // declaration merging — adds to UserI

Use interface when…

  • Defining object shapes that others will implement or extend — interface IRepository implemented by classes is idiomatic TypeScript.
  • You need declaration merging — Augmenting third-party types requires interfaces.
  • Modeling domain entities — User, Product, Order benefit from the structural clarity and extensibility of interfaces.
  • React component props — Many React codebases use interface ButtonProps because it's easy to extend with extends React.ButtonHTMLAttributes<HTMLButtonElement>.

Use type when…

  • Union types — type Status = 'active' | 'inactive' | 'pending'
  • Intersection types — type AdminUser = User & AdminPrivileges
  • Tuple types — type Point = [number, number]
  • Conditional types — type IsArray<T> = T extends unknown[] ? true : false
  • Mapped types — type Nullable<T> = { [K in keyof T]: T[K] | null }
  • Template literal types — type EventName = \`on${string}\`
  • Utility type compositions — type UpdateUser = Partial<Omit<User, 'id'>>
  • Don't use interface for unions. interface Status can't represent 'active' | 'inactive'. That's literally a syntax error.
  • Don't use type when you need merging. If you'll augment the type later (or let others augment it), it must be an interface.
  • Don't force a choice based on dogma. Neither is universally "correct." Pick based on what you need: merging + extends → interface; union/mapped/conditional → type.
  • Don't mix them randomly in the same codebase. Pick a convention and document it. Inconsistency confuses contributors.

3. Assuming intersection equals extension

typescript
interface A { x: number; }
interface B { x: string; }

// Intersection of conflicting types creates `never` for the property
type AB = A & B;
// AB.x is `never` — you can never satisfy it
// Interface extension would have caught this at declaration time
interface AB2 extends A, B {} // ERROR at declaration — safer

Intersection silently creates unusable never types for conflicting properties; interface extension errors loudly at the declaration site.

4. Cargo-culting one over the other

Some teams pick "always interface" or "always type" without understanding why. The result is either interfaces used for unions (syntax errors) or types used for everything that loses error message quality and merging capability. Pick based on need, not habit.

  1. Default to interface for object shapes. The TypeScript team recommends interface for objects because it produces better error messages and supports merging. Reserve type for what interfaces can't do.
  2. Use type for unions, intersections, tuples, and utility type compositions. These are non-negotiable — interfaces can't express them.
  3. Pick a convention for your team and document it in the style guide. Inconsistency is more costly than either choice. Many teams use: interface for public API shapes; type for internal computed types.
  4. Prefer interface extends over type & for structural inheritance. Extension errors at declaration time; intersection silently creates never on conflicts.
  5. Don't refactor working code just to switch between them. If existing code uses type for object shapes and it works, leave it. The difference rarely matters enough to justify a refactor.
  6. Use type for inferred types from Zod/Prisma/tRPC. type CreateInput = z.infer<typeof schema> — the type is computed, not authored.
Q: What is the main difference between interface and type in TypeScript?Easy
The key differences are: interfaces support declaration merging (you can add properties by re-declaring the interface) while type aliases cannot be re-declared; interfaces use extends for inheritance while types use & for intersection; and type aliases can represent any type expression (unions, tuples, primitives, conditional types) while interfaces are restricted to object shapes. For object shapes, they are functionally equivalent in most cases.
Q: Can a class implement a type alias? Can it implement a union type?Medium
A class can implement a type alias if that alias describes an object shape (not a union). class Foo implements Bar works whether Bar is an interface or an object type alias. However, a class cannot implement a union type — class Foo implements A | B is a compile error, because the class would have to satisfy all possible branches simultaneously, which is undefined behavior.
Q: When would you choose type over interface for an object shape?Medium
Choose type for an object shape when: (1) you derived the type using utility types (Partial<User>, Omit<User, 'id'>) — these are type expressions, not independent declarations; (2) you infer the type from a Zod schema or ORM query — type T = z.infer<...>; or (3) you want to create an intersection of existing types. In all other cases, interface is the community-recommended default for object shapes.
Q: Why do type intersections with conflicting properties produce never while interface extension errors at declaration?Hard
Interface extension validates the constraint at the declaration site — it's a structural rule check that runs when you write the type definition. Type intersection is evaluated at the usage site — the resulting type for a conflicting property is the intersection of the two types (e.g., string & number), which is never since no value can be both. This means intersection type bugs can hide in your code until you try to assign a value, whereas interface extension surfaces them immediately.
Q: The TypeScript official docs recommend interface over type. Do you agree? When might you disagree?Hard
The recommendation makes sense as a default because interfaces produce cleaner error messages, support augmentation, and signal "this is a public contract." However, I'd disagree in these cases: when using utility type compositions (Partial, Pick, Omit) you must use type; when working with discriminated unions or state machines, type is the only option; and when inferring types from schema validators or ORMs, type is natural. The real answer is: use the right tool for the shape of the problem, not a blanket rule.
