Union Types Beginner ▶

Definition

Simple: A union type lets you say "this value can be one of these types." Instead of committing to a single type, you list the options separated by |, like a menu of valid choices.
Technical: Union types are denoted with the | operator and represent the set-theoretic union of all member types. A value of union type A | B is assignable when it satisfies at least one member. The type checker requires you to narrow to a specific member before accessing type-specific properties that don't exist on all members.

Why It Exists / What Problem It Solves

In JavaScript, functions routinely return null on failure or a value on success. There's no mechanism to force callers to handle the null case — they forget, and the app crashes.

javascript
// JavaScript — nothing stops you from forgetting null
function findUser(id) {
  return database.find(id); // might return null!
}
const user = findUser(42);
console.log(user.name); // 💥 TypeError if user is null — crashes in production

TypeScript's union types force the caller to acknowledge all possible return values:

typescript
function findUser(id: number): User | null {
  return database.find(id) ?? null;
}

const user = findUser(42);
console.log(user.name);   // ❌ Error: Object is possibly 'null'
console.log(user?.name);  // ✅ Safe — optional chaining

The compiler becomes your safety net: every place you might forget a null check becomes a compile error instead of a runtime crash.

When to Use Union Types

  • Optional / nullable values — use string | null when a value might be absent; forces callers to handle the null case
  • Multi-form state — use 'loading' | 'success' | 'error' to model UI state that transitions through distinct phases
  • Flexible function inputs — use string | number when a function can legitimately accept either, like a lookup by UUID or integer ID
  • API responses — use SuccessResponse | ErrorResponse to model the two possible shapes from an endpoint
  • Event payloads — when different events carry different data shapes, union them to create a type-safe event bus
  • Database queries — when a query can return a found record or undefined, encoding that in the return type prevents silent nil access

When NOT to Use Union Types

Don't create a "catch-all" union that's just any in disguise

string | number | boolean | object | null | undefined covers almost everything — you've recreated any with more syntax. Use unknown instead and require explicit narrowing.

Don't union types that should share a common interface

If Cat | Dog | Bird all have a name: string property you always need, they should implement a shared Animal interface. Use union only when the shapes genuinely differ.

Don't use unions to paper over bad API design

If an API returns { data: User } | { data: Product }, consider whether the endpoint itself is poorly designed. A single endpoint returning fundamentally different resource types is an API smell, not a TypeScript problem to solve with unions.

Don't nest unions deeply without type aliases

(A | B) | (C | D | E) is hard to read and maintain. Flatten with named aliases: type AB = A | B; type CDE = C | D | E; type All = AB | CDE;

How It Works Internally

Union types are a purely compile-time concept — they produce no JavaScript output. The TypeScript compiler tracks them through three key mechanisms:

  1. Assignability: A value is assignable to A | B if it satisfies at least one member. A plain string is assignable to string | number.
  2. Property access: When you access a property on a union type, TypeScript only allows it if the property exists on ALL members. Accessing .toUpperCase() on string | number is an error because number doesn't have it.
  3. Control flow narrowing: When you write if (typeof x === 'string'), TypeScript updates its internal type for x inside that branch to just string, discarding the number possibility. This is called Control Flow Analysis (CFA).

At runtime, after TypeScript compiles to JavaScript, all union type annotations are stripped completely. There is zero runtime overhead — unions exist only during the compilation phase.

Syntax Explanation

typescript
// 1. Basic union — value is either string or number
type StringOrNumber = string | number;
//                            ^ the pipe | means "or"

// 2. Nullable type — value can be string, null, or undefined
type MaybeString = string | null | undefined;

// 3. In a function parameter — accepts both types at call site
function printId(id: string | number): void {
  console.log(id);
}

// 4. In a return type — callers must check which variant they got
function search(query: string): User | null { /* ... */ }

// 5. Object shape union — most common in practice
type ApiResult = SuccessPayload | ErrorPayload;

// 6. Discriminated union — add a shared "tag" property
//    so TypeScript can narrow with a simple === check
type Shape =
  | { kind: 'circle';    radius: number }
  | { kind: 'square';    side: number }
  | { kind: 'rectangle'; width: number; height: number };

Convention: put each union member on its own line, leading with |, for readability. Use a kind / type / tag discriminant property whenever members share context — it makes narrowing trivial.

Practical Code Example

typescript
type UserId = string | number;

// typeof narrows the union inside each branch
function formatUserId(id: UserId): string {
  if (typeof id === 'string') {
    return `UUID: ${id.toUpperCase()}`; // id: string here
  }
  return `INT: ${id.toFixed(0)}`; // id: number here
}

console.log(formatUserId('abc-123')); // Output: UUID: ABC-123
console.log(formatUserId(42));       // Output: INT: 42

// Discriminated union for loading state
type LoadState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error';   error: string };

function renderState<T>(state: LoadState<T>): string {
  switch (state.status) {
    case 'idle':    return 'Ready';
    case 'loading': return 'Loading...';
    case 'success': return `Got data: ${JSON.stringify(state.data)}`;
    case 'error':   return `Error: ${state.error}`;
  }
}
// TypeScript knows state.data only exists in the 'success' branch

// Express route — API response typed as discriminated union

type ApiSuccess<T> = { ok: true;  data: T };
type ApiError      = { ok: false; message: string; code: number };
type ApiResponse<T> = ApiSuccess<T> | ApiError;

interface User { id: number; name: string; email: string; }

  }
}

const result = await getUser(1);

}

Real-World Use Cases

  • React query states: Model 'loading' | 'success' | 'error' | 'idle' for data-fetching components — eliminates impossible states like having both data and error at once.
  • Form validation results: Return { valid: true; value: T } | { valid: false; errors: string[] } from validators so callers always handle the error path.
  • Webhook event routing: Type incoming webhook bodies as a union of known event shapes; switch on the event type to route to the correct handler with full type safety.
  • Command pattern: In Redux or Zustand, action types are unions of action shapes; the reducer switches on action.type and gets narrowed props automatically.
  • Database optional columns: string | null for nullable DB columns ensures you can't use the value without a null-check.
  • Multi-provider auth: GoogleUser | GithubUser | EmailUser — each provider returns slightly different profile data modelled as distinct union members.

Common Mistakes and How to Avoid Them

1. Accessing union properties without narrowing first
typescript
// WRONG
function bad(x: string | number) {
  return x.toUpperCase(); // ❌ Error: number has no toUpperCase
}

// CORRECT
function good(x: string | number) {
  if (typeof x === 'string') return x.toUpperCase(); // ✅
  return x.toString();
}

Property access on a union only compiles if the property exists on every member. Narrow first using typeof, instanceof, or a discriminant check.

2. Confusing | (union) with & (intersection)
typescript
// WRONG — & means value must be BOTH, which is impossible for primitives
type Bad = string & number; // type: never — nothing can satisfy both

// CORRECT — | means value can be EITHER
type Good = string | number; // can be a string or a number

| is OR (union), & is AND (intersection). They look similar but have opposite semantics. Intersecting incompatible primitive types creates never.

3. Creating a union so wide it defeats the purpose
typescript
// WRONG — this is basically just any
type Anything = string | number | boolean | object | null;

// CORRECT — use unknown for truly dynamic input
function process(input: unknown): string {
  // must narrow before using
}

Wide unions that cover almost every type lose the precision benefit. Use unknown and require narrowing at the point of use.

4. Forgetting to handle all union members in a switch
typescript
// WRONG — missing 'error' case silently falls through
function handle(s: 'loading' | 'success' | 'error') {
  switch (s) {
    case 'loading': return '...';
    case 'success': return 'Done';
    // 'error' case missing — no compile warning by default
  }
}

// CORRECT — add exhaustiveness check with never
function handle(s: 'loading' | 'success' | 'error'): string {
  switch (s) {
    case 'loading': return '...';
    case 'success': return 'Done';
    case 'error':   return 'Failed';
    default: const _: never = s; return _;
  }
}

Best Practices

1
Add a discriminant property to object unions. A shared kind, type, or status property with a literal type makes narrowing trivial — one switch statement handles all members without custom logic.
2
Use exhaustiveness checks in switch statements. Add a default: const _: never = x clause so TypeScript reports a compile error when you add a new union member but forget to handle it.
3
Name your union types. type ApiResponse = Success | Failure is far more readable and reusable than inlining the union at every usage site.
4
Keep union members focused and small. Each member should represent one coherent state. If a member has 10 optional properties, it's probably doing too much — split it further or use a nested type.
5
Prefer unknown over wide unions. If you truly don't know the type at the point of declaration, unknown is honest and forces narrowing at usage. A wide union gives false confidence.
6
Use | on new lines for long unions. Format multi-member unions with leading | per line for readability — this is the TypeScript community standard.

Interview Questions

EasyQ: What is a union type and how do you declare one?
A union type allows a variable to hold a value of one of several specified types, declared using the | operator. For example, string | number means the variable can be either a string or a number. You can use them in variable declarations, function parameters, return types, and type aliases. TypeScript requires you to narrow down to a specific member before using type-specific methods.
EasyQ: What is the difference between string | null and just string?
With string, TypeScript guarantees the value will always be a string — you can call string methods on it directly. With string | null, TypeScript knows the value might be null, so it forces you to check for null before using string methods. This is the basis of TypeScript's null safety: in strict mode, null is not assignable to string, so you must explicitly opt in to nullable types with a union.
MediumQ: Why can't you access .length on a string | number[] union?
Actually you can in this case, because both string and number[] have a length property. TypeScript only allows property access on a union if the property exists on ALL members. If you had string | number, you couldn't access .length because number doesn't have it. The general rule: union type property access is the intersection of the members' properties.
MediumQ: What is a discriminated union and why is it useful?
A discriminated union is a union where each member has a shared property (the "discriminant") with a unique literal type value. For example, { type: 'circle'; radius: number } | { type: 'square'; side: number } — the type property discriminates between members. This is useful because TypeScript can narrow to the exact member type using a simple switch (shape.type) statement, without needing typeof, instanceof, or custom type guards. It's the most maintainable pattern for union types in real code.
HardQ: How does TypeScript determine the type inside a conditional branch? What is Control Flow Analysis?
TypeScript's compiler performs Control Flow Analysis (CFA): it statically simulates execution paths through your code and tracks which types are possible at each point. When it encounters a type guard (like typeof x === 'string'), it splits the flow into two branches — one where x is narrowed to string, and one where string is excluded from the union. CFA handles if/else, switch, ternaries, early returns, and even assignments. The narrowed type is computed per-statement, not per-function — so reassigning a variable resets the narrowing, and accessing through a closure may not preserve it.

Key Takeaways

  • Union types use | and mean "this value is one of these types" — it's the OR operator of the type system.
  • You must narrow to a specific member before accessing type-specific properties — TypeScript won't let you pretend a string | null is always a string.
  • Discriminated unions add a shared literal-typed "tag" property that makes narrowing trivial with a single switch statement.
  • Exhaustiveness checking with never ensures your switch handles every union member — adding a new member creates a compile error until you handle it.
  • Union types are erased at compile time — no runtime overhead, no JS output, purely a compile-time contract.
  • Prefer narrow, focused unions with a discriminant over wide, flat unions with many optional properties.
Mental model: A union type is like a multiple-choice field in a form — the value must be exactly one of the listed options, and you have to check which option it is before acting on it.
Intersection Types Intermediate ▶

Definition

Simple: An intersection type combines multiple types into one that has ALL the properties from ALL the types. If union is "A OR B", intersection is "A AND B" — the resulting value must satisfy every member simultaneously.
Technical: Intersection types are declared with the & operator. A value of type A & B must be assignable to both A and B. The resulting type's property set is the union of all properties from all members. If a property exists in multiple members with different types, those types are themselves intersected for the property's type.

Why It Exists / What Problem It Solves

You have two separate types that model distinct concerns, and you need a third type that combines both. Without intersection types, you'd either duplicate properties or flatten everything into one big interface.

typescript
// Without intersection — manual duplication, fragile
interface User { id: number; name: string }
interface HasTimestamps { createdAt: Date; updatedAt: Date }

// You have to manually copy — if User changes, this gets out of sync
interface AuditedUser {
  id: number; name: string;
  createdAt: Date; updatedAt: Date;
}
typescript
// With intersection — compose once, stay in sync automatically
type AuditedUser = User & HasTimestamps;
// AuditedUser now has: id, name, createdAt, updatedAt
// If User or HasTimestamps changes, AuditedUser updates automatically

Intersection types are especially powerful for mixin patterns — adding capabilities to an existing type without modifying the original type definition.

When to Use Intersection Types

  • Mixin composition: Combine multiple capability interfaces — Serializable & Cacheable & Loggable — to declare that an object implements all of them
  • Adding metadata to a base type: User & { sessionId: string } — add request-scoped data to an existing model without modifying it
  • Extending third-party types: When you can't modify a library's type, intersect it with your additions
  • HOC patterns in React: A higher-order component injects props; type the wrapped component's props as OwnProps & InjectedProps
  • Combining Drizzle ORM schema with domain types: Intersect a schema type with validation results or computed fields

When NOT to Use Intersection Types

Don't intersect incompatible primitive types

string & number produces never — no value can be both a string and a number. This is rarely useful and almost always a mistake. If you intended a union, use | instead.

Don't use & when interface extends is cleaner

For simple object type inheritance, interface Admin extends User { role: string } is clearer than type Admin = User & { role: string }. Use extends for single-parent hierarchies; use & for multi-source composition.

Don't use intersection to "merge" mutually exclusive states

LoadingState & SuccessState makes no conceptual sense — a request can't be both loading and succeeded. Use a union for mutually exclusive states.

Watch out for conflicting property types

If A has id: string and B has id: number, then A & B gives id: string & number — which is never. No object can ever satisfy this type. TypeScript won't warn you directly; you'll only notice when you can't construct a value.

How It Works Internally

When TypeScript evaluates A & B, it creates a new structural type whose property set is the union of all properties from A and B. For each property that appears in both, the property types are themselves intersected:

  • If A.x: string and B.x: string, then (A & B).x = string & string = string
  • If A.x: string and B.x: number, then (A & B).x = string & number = never
  • If only A has property y, then (A & B).y is just A.y's type

Like unions, intersection types are erased at compile time — they produce no JavaScript output. Intersecting function types creates an overloaded function type. Intersecting class instance types works for structural typing but not actual class inheritance.

typescript
// TypeScript resolves properties at compile time
type A = { x: string; y: number };
type B = { y: number; z: boolean };
type AB = A & B;
// AB is: { x: string; y: number & number; z: boolean }
//      → { x: string; y: number; z: boolean }

Syntax Explanation

typescript
// 1. Basic intersection — result has ALL properties from both
type WithId         = { id: string };
type WithTimestamps = { createdAt: Date; updatedAt: Date };

type DbRecord = WithId & WithTimestamps;
//   DbRecord has: id, createdAt, updatedAt

// 2. Inline intersection — common for one-off augmentations
type AdminUser = User & { role: 'admin'; permissions: string[] };

// 3. Multiple members — A & B & C, all properties required
type AuditedAdmin = User & HasTimestamps & { role: 'admin' };

// 4. In function parameter — accepts any object with BOTH shapes
function save(record: WithId & WithTimestamps): void {
  console.log(record.id, record.createdAt); // both available
}

// 5. Conflicting property — results in never
type Impossible = { x: string } & { x: number };
// Impossible.x is string & number = never
// You cannot construct a valid Impossible object

Common Mistakes and How to Avoid Them

1. Intersecting types with conflicting property types
typescript
// WRONG — id: string in A conflicts with id: number in B
type A = { id: string; name: string };
type B = { id: number; role: string };
type Bad = A & B; // Bad.id = string & number = never!
const x: Bad = { id: ???, name: '', role: '' }; // impossible to construct

// CORRECT — ensure shared properties have compatible types
type A = { id: string; name: string };
type B = { role: string }; // no conflicting id
type Good = A & B;
2. Using & when you mean | (wrong operator)
typescript
// WRONG — & means value must be BOTH types at once
function handle(value: string & number) {} // never callable!

// CORRECT — | means value can be either type
function handle(value: string | number) {}
3. Using intersection when interface extends is cleaner
typescript
// WORKS but harder to read for simple hierarchy
type Admin = User & { role: 'admin' };

// BETTER for single-parent object inheritance
interface Admin extends User { role: 'admin' }

Best Practices

1
Use intersection for composition, not inheritance. When you're combining multiple independent capabilities into one type, intersection is correct. For a parent→child hierarchy, use extends.
2
Always name the resulting intersection type. type AuthRequest = Request & { user: User } is far more readable than inlining Request & { user: User } at every function signature.
3
Audit for never properties. When intersecting third-party types you don't control, check that shared property names have compatible types. A never property makes the type impossible to satisfy.
4
Keep mixin types focused on one concern. WithTimestamps should only have timestamp fields. WithId should only have an id. Combining multiple concerns into one mixin defeats the composition benefit.
5
Prefer interface extends for interfaces, & for type aliases. The two are mostly equivalent for objects, but extends gives better error messages and hover information in editors.

Interview Questions

EasyQ: What does A & B mean in TypeScript? How is it different from A | B?
A & B is an intersection type — a value must satisfy both A and B simultaneously, so it has all properties from both. A | B is a union type — a value satisfies either A or B, but you can only safely access properties that exist on both. Think of & as "AND" (value must be this AND that) and | as "OR" (value can be this OR that).
EasyQ: What happens when you intersect two object types that have the same property name?
The property's type becomes the intersection of both property types. If both have x: string, the result is x: string. If one has x: string and the other has x: number, the result is x: string & number, which resolves to never — making the type impossible to construct. This is a common gotcha when intersecting types from different libraries.
MediumQ: When would you prefer intersection types over interface extension?
Use intersection when combining types from multiple unrelated sources — especially when you don't own one or both of the types. For example, augmenting an Express Request with auth data: type AuthRequest = Request & { user: User }. Use interface extends for single-source hierarchies where you own the types and want better IDE error messages. Intersection also allows mixing type aliases with interface types, which extends on an interface can't always do.
MediumQ: What is a mixin type pattern and how do intersections enable it?
A mixin is a small, focused type that contributes a specific capability. You compose complex types by intersecting mixins: type Product = DbEntity & Searchable & Cacheable. Each mixin is defined once and reused across many domain types. Intersections enable this because the result type gets ALL properties from all mixins — it's additive composition. This is the TypeScript equivalent of multiple interface implementation in other languages.
HardQ: How do function intersection types work? What is the resulting type when you intersect two function types?
Intersecting two function types creates an overloaded function type — a function that can be called with the arguments of either member. For example, ((x: string) => void) & ((x: number) => void) creates a function that must handle both string and number arguments. This is different from union — a union function type can only be called with arguments that satisfy ALL members (the intersection of parameter types), while an intersection function type creates overloads. This subtlety catches many developers off guard because function variance is contravariant for parameters.

  • The result type has the property-set union of all members — every property from every member is present.
  • Conflicting property types (e.g., string & number) produce never — making the type impossible to construct.
  • Best used for mixin/composition patterns: combining multiple focused capability types into one rich type.
  • For simple single-parent hierarchies, prefer interface extends — better error messages and readability.
  • Like unions, intersections are erased at compile time — no JavaScript output, zero runtime cost.
Mental model: An intersection type is like a job that requires multiple certifications — the candidate must hold ALL of them, so the final type is the combination of everything each certification requires.
Literal Types Beginner ▶

Definition

Simple: Instead of saying "this is a string," you say "this is exactly the string 'success'." A literal type pins a value to one specific, exact value — not just any string, but that particular string.
Technical: A literal type is a type whose domain contains exactly one value. TypeScript supports string, number, boolean, and bigint literal types. Literal types are subtypes of their base types ("hello" is a subtype of string). They're the foundational building blocks for discriminated unions, const assertions, and template literal types.

Why It Exists / What Problem It Solves

You have a status field that should only ever be "pending", "active", or "closed". Using string allows any value — typos and invalid states compile and deploy silently.

typescript
// Without literal types — typos are invisible
interface Account { status: string }
const a: Account = { status: 'actve' }; // typo: no error, ships to prod

// With literal types — compile-time enforcement
interface Account { status: 'pending' | 'active' | 'closed' }
const a: Account = { status: 'actve' }; // ❌ Error: not assignable
const b: Account = { status: 'active' }; // ✅

Literal types are also the key enabler for discriminated unions — without them, you can't have a kind: "circle" discriminant field that TypeScript can narrow on.

When to Use Literal Types

  • Status/state enumerations: Any field with a fixed set of valid string values — order status, user role, environment name, HTTP method
  • Direction/orientation constants: "left" | "right" | "top" | "bottom" for layout or navigation values
  • Configuration keys: When a configuration object must use one of a fixed set of keys or values
  • Discriminant properties in union types: The kind or type field that TypeScript uses to narrow which union member you have
  • React prop constraints: Button variants, sizes, color schemes — anywhere the UI component only supports a fixed set of options
  • Compile-time constant tables: Use as const on arrays/objects to preserve all literal types for deriving union types

When NOT to Use Literal Types

Don't use for truly open-ended string values

User names, email addresses, URLs, and free-text fields should be string. Literal types only make sense when the complete set of valid values is known at design time and changes rarely.

Don't use when the value set comes from an external data source

If valid values come from a database, config file, or API, you can't encode them as literal types — they're not known at compile time. Use string plus runtime validation (e.g., Zod) instead.

Don't add explicit literal annotations on const declarations
typescript
// REDUNDANT — TypeScript already infers the literal type from const
const x: 'hello' = 'hello';

// BETTER — let TypeScript infer it
const x = 'hello'; // type is already "hello"
Don't replace enums with literal types when the enum has numeric values you need

If you need to compare against numeric codes (HttpStatus.OK === 200) or iterate over values, numeric enums are clearer. Literal types are better for string-based, human-readable values.

How It Works Internally

Literal types are subtypes of their base types in TypeScript's type hierarchy:

  • "hello" is a subtype of string — so "hello" is assignable to string
  • string is NOT a subtype of "hello" — a general string is not assignable to a literal

Literal widening: TypeScript uses two inference modes. With const, the type is inferred as the literal. With let, the literal is "widened" to its base type because the variable can be reassigned.

typescript
const a = 'north'; // type: "north" (literal, can't change)
let   b = 'north'; // type: string (widened, might be reassigned)

// as const forces literal inference on object/array literals
const config = { env: 'production' };
// config.env: string (widened because object is mutable)

const config2 = { env: 'production' } as const;
// config2.env: "production" (literal preserved)

Like all types, literal types are erased at compile time. 'pending' as a type constraint produces no runtime output — only the string value itself remains.

EasyQ: What is a literal type? How does it differ from its base type?
A literal type constrains a value to one specific exact value — "success" is only that string, whereas string is any string. Literal types are subtypes of their base type: "success" is assignable to string, but string is NOT assignable to "success". They're used for values from a finite, known set — status fields, HTTP methods, directions, button variants — anywhere a generic base type would be too permissive.
EasyQ: Why does let x = "hello" give type string but const x = "hello" give type "hello"?
TypeScript uses "literal widening" — for let variables, it widens the inferred type to the base type because the variable could be reassigned to any other string. For const, reassignment is impossible, so TypeScript keeps the exact literal type. This is called "narrowing by constness." The practical impact: if you want a literal type in a variable you might reassign, you must annotate it explicitly: let x: "hello" | "world" = "hello".
MediumQ: What does as const do and when do you need it?

On a string, it's equivalent to a literal type annotation. On objects and arrays, it's essential: { env: 'production' } normally infers env: string, but { env: 'production' } as const infers env: "production". This is powerful for generating typed event names, CSS class names, or path patterns without manual enumeration.

Type Narrowing Intermediate ▶

Definition

Simple: Type narrowing is TypeScript's ability to look at your if statements and automatically figure out which specific type you're working with inside each branch. You do the check; TypeScript does the deduction.
Technical: Narrowing is driven by Control Flow Analysis (CFA) — the TypeScript compiler statically simulates program execution paths and maintains a "narrowed type" for each variable at every statement. Type guards (built-in or user-defined) update the narrowed type at branch points; the compiler tracks these updates through if/else, switch, ternaries, early returns, and assignments.

Why It Exists / What Problem It Solves

Union types are essential for correctness, but they create a problem: you can't call type-specific methods without first checking which variant you have. Narrowing is the mechanism that makes union types actually usable.

typescript
// Without narrowing — TypeScript correctly stops you
function bad(value: string | null) {
  console.log(value.toUpperCase()); // ❌ Object is possibly 'null'
}
typescript
// With narrowing — TypeScript tracks what you proved
function good(value: string | null) {
  if (value !== null) {
    console.log(value.toUpperCase()); // ✅ TypeScript knows: value is string
  }
}

Without narrowing, you'd need to cast with as everywhere — which is unsafe because it bypasses TypeScript's checks. Narrowing gives you safety AND convenience: write the check once, get fully typed access for the rest of the branch.

When to Use Type Narrowing

  • After null/undefined checks: Any time you check if (value != null), TypeScript narrows out null/undefined in the true branch
  • Handling union type members: When you have Cat | Dog | Fish and need to call animal-specific methods
  • Working with unknown: You must narrow before using any value typed as unknown — narrowing is mandatory, not optional
  • Switch on discriminants: The most ergonomic narrowing — one switch (shape.kind) narrows to the exact union member in each case
  • Error handling: Narrow catch (err) (which is unknown in strict mode) before accessing err.message
  • After array checks: if (Array.isArray(value)) narrows string | string[] to string[]

When NOT to Use Narrowing (or how not to misuse it)

Don't use type assertions (as) instead of narrowing

value as string bypasses all checks and shifts responsibility for correctness entirely to you. If value is actually null, you get a runtime crash with no TypeScript warning. Always narrow instead of casting.

Don't rely on narrowing through closures without re-checking

TypeScript can't guarantee a variable's type won't change between when you checked it and when a callback runs. A variable narrowed to string before a setTimeout callback may have been reassigned to null by the time the callback fires. Re-capture the narrowed value into a const.

Don't add redundant checks TypeScript already knows about

If TypeScript's CFA has already proven a value is non-null (e.g., after an early return for the null case), adding another null check is noise. Trust the compiler.

How It Works Internally

TypeScript's Control Flow Analysis (CFA) builds a data-flow graph of your program. At each node in the graph, every variable has a "narrowed type" which starts as its declared type and is refined by type guards:

  1. typeof checks: typeof x === 'string' narrows x to string in the true branch and removes string from the union in the false branch
  2. instanceof: x instanceof Error narrows x to Error (and subclasses) in the true branch
  3. Truthiness: if (x) removes null | undefined | false | 0 | "" from x's type in the true branch
  4. Equality: x === 'circle' narrows x to "circle" (or removes it from the union in the false branch)
  5. in operator: 'radius' in shape narrows to union members that have a radius property
  6. Assignment: After x = "hello", TypeScript narrows x to string (or the literal) for the rest of the block

The analysis is intra-procedural — it doesn't track types across function call boundaries unless you use user-defined type guards (covered next topic).

Syntax Explanation — Narrowing Patterns

typescript
// 1. typeof narrowing — for primitives
function pad(x: string | number) {
  if (typeof x === 'string') return x.padStart(10); // x: string
  return x.toFixed(2);                               // x: number
}

// 2. Truthiness narrowing — removes falsy types
function greet(name: string | null | undefined) {
  if (name) return `Hi, ${name}`; // name: string (null/undefined removed)
  return 'Hi!';
}

// 3. Equality / discriminant narrowing
type Shape = { kind: 'circle'; r: number }
           | { kind: 'square'; s: number };

function area(sh: Shape): number {
  if (sh.kind === 'circle') return Math.PI * sh.r ** 2; // sh: circle
  return sh.s ** 2; // sh: square
}

// 4. instanceof narrowing — for class instances
function handle(err: Error | string) {
  if (err instanceof Error) return err.message; // err: Error
  return err; // err: string
}

// 5. in operator narrowing — checks property existence
type Cat = { purr: () => void };
type Dog = { bark: () => void };
function sound(pet: Cat | Dog) {
  if ('purr' in pet) pet.purr(); // pet: Cat
  else              pet.bark(); // pet: Dog
}

// 6. Exhaustiveness check with never
function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${x}`);
}

Best Practices

1
Design discriminated unions to make narrowing trivial. A single kind/type/status property with distinct literals on each member enables one-liner switch-based narrowing — no complex guards needed.
2

3
Use early returns to reduce nesting. Instead of if (x) { ... long block ... }, use if (!x) return; at the top. TypeScript narrows x for the rest of the function body without indentation.
4

Interview Questions

EasyQ: What is type narrowing in TypeScript?
Type narrowing is TypeScript's ability to refine the type of a variable within a conditional block based on runtime checks. When you write if (typeof x === 'string'), TypeScript tracks that check and narrows x's type to string inside the if block. This makes union types practical — you can have a string | null variable, prove at each usage point which variant you have, and get full type-safe access to the appropriate methods.
EasyQ: What are the different ways TypeScript narrows a type?
TypeScript narrows using: typeof checks (for primitives), instanceof (for class instances), truthiness checks (removes null/undefined/false/0/""), equality checks including === on discriminant properties, the in operator (checks property existence), Array.isArray(), and user-defined type guard functions that return a type predicate (x is Type). Each of these updates the compiler's narrowed type for the checked variable in the appropriate branch.
MediumQ: What is exhaustiveness checking and how do you implement it?
Exhaustiveness checking ensures your switch statement handles every member of a union type. You implement it by adding a default case that assigns the switched variable to never: default: const _: never = x;. When all union members are handled, x in the default case has been narrowed to never (nothing left), so the assignment is valid. If you add a new union member but don't add a case for it, the default case sees that member's type instead of never, causing a compile error. This is the TypeScript equivalent of "total function" guarantees.
MediumQ: Why does TypeScript sometimes not narrow through closures?
TypeScript's CFA is intra-procedural — it analyzes one function body at a time. When you create a closure (callback, event handler, setTimeout), the compiler can't guarantee that a let variable won't be reassigned between when you checked it and when the callback runs. So it doesn't maintain the narrowed type inside closures for mutable variables. The fix: re-capture the narrowed value into a const before creating the closure — const can't be reassigned, so TypeScript maintains its narrowed type inside the closure.
HardQ: What is Control Flow Analysis and what are its limitations?
CFA is TypeScript's static simulation of execution paths. It builds a flow graph where each edge represents a possible execution path, and it tracks the narrowed type of each variable at each node. Its key limitations: (1) it's intra-procedural — it can't track type changes across function calls unless you use type guards; (2) it's conservative with mutable variables in closures; (3) it doesn't analyze runtime mutations to object properties — if obj.x is string | null and you check if (obj.x), TypeScript may not narrow obj.x inside the branch because another reference to obj could mutate it; (4) complex conditions with multiple variables can confuse the analysis. For these cases, user-defined type guards and const re-captures are the escape hatches.

Type Guards Advanced ▶

Definition

Simple: A type guard is a function you write that comes with a special promise to the TypeScript compiler: "if this function returns true, I guarantee the argument is this specific type." Built-in narrowing handles primitives; type guards handle everything else.
Technical: A user-defined type guard is a function whose return type is a type predicate — arg is Type. When such a function returns true, TypeScript narrows the parameter to Type in the true branch and applies Exclude<Original, Type> in the false branch. The runtime check is entirely your responsibility — TypeScript trusts the predicate unconditionally. Assertion functions (asserts arg is Type) are a variant that throw instead of returning false.

Why It Exists / What Problem It Solves

Built-in type guards (typeof, instanceof) only handle primitives and class instances. When you have complex object shapes from external sources — JSON from an API, user input, dynamic imports — you need to write custom logic to validate the shape, and you need TypeScript to understand that logic.

typescript
// Problem: JSON.parse gives unknown — you can't access any property
const body: unknown = JSON.parse(rawJson);
console.log(body.name); // ❌ 'body' is of type 'unknown'

// typeof doesn't help — it just says "object"
// instanceof doesn't help — no class to check against
typescript
// Solution: user-defined type guard teaches TypeScript the shape
interface User { id: number; name: string }

function isUser(v: unknown): v is User {
  return (
    typeof v === 'object' && v !== null &&
    'id' in v && 'name' in v
  );
}

if (isUser(body)) {
  console.log(body.name); // ✅ body: User — safe access
}

When to Use Type Guards

  • Validating external data: API responses, JSON.parse results, form inputs — any data whose shape you can't guarantee at compile time
  • Working with unknown: You must narrow before using unknown, and built-in guards may not be sufficient for complex shapes
  • Array.filter() with typed results: arr.filter(isUser) returns User[] if isUser is a type guard — otherwise it returns the original element type
  • Union discrimination without a discriminant: When union members don't have a shared tag field, a type guard can inspect the shape structurally
  • Library code: When writing utilities that accept polymorphic inputs and need to route to type-specific logic
  • Error type narrowing: In catch blocks, narrow unknown errors to check if they're specific error types before accessing properties

When NOT to Use Type Guards

Don't use type guards when discriminated unions work

If your types have discriminant properties (kind, type, status), a switch statement narrows without any custom guard. Guards are for when you don't control the data shape — if you design the types yourself, design them to be narrowable with built-ins.

Don't skip the actual runtime check inside the guard

The whole point of a type guard is to prove something at runtime. A guard that returns true unconditionally is lying to the compiler — TypeScript will believe it and let you access properties that might not exist. This is worse than no type check at all because you've created a false sense of safety.

Don't use type guards as a performance-critical path

Guards that deeply validate large objects (checking every property of a 50-field type) can be slow if called in hot loops. For performance-critical paths with large payloads, consider Zod's parse-once-validate approach or lean on TypeScript-only validation where you trust the source.

Don't hand-roll guards for complex types — use Zod or similar

For production API validation, Zod schemas parse and validate in one step, returning typed results automatically. Hand-rolled type guards for 10+ field types are tedious and error-prone. Use guards for simple/structural checks; use Zod for full schema validation.

How It Works Internally

When TypeScript sees a call to a function with a param is Type return type annotation, it treats that call site as a narrowing point — exactly like a built-in type guard.

  1. True branch: TypeScript narrows the parameter's type to Type
  2. False branch: TypeScript narrows to Exclude<OriginalType, Type> — removes Type from the union
  3. Trust: TypeScript does NOT verify that your guard implementation is correct. If you return true for something that isn't a User, TypeScript will happily let you access User properties, which may not exist at runtime.

Assertion functions (asserts arg is Type) work slightly differently — they narrow the type for the rest of the calling scope if they don't throw, rather than narrowing in an if branch. They're useful for "validate or die" scenarios.

typescript
// TypeScript's view of a type guard call site:
// - if isUser(x) returns true  → x is narrowed to User
// - if isUser(x) returns false → x is narrowed to Exclude<original, User>
const data: unknown = getData();
if (isUser(data)) {
  data.name; // data: User — compiler trusts isUser's predicate
} else {
  // data: unknown (Exclude<unknown, User> is still unknown)
}

Syntax Explanation

//                              ^^^^^^^^^
//                              type predicate: if true, v is string
  return typeof v === 'string';
}

// 2. Object shape guard — checks all required properties
function isUser(v: unknown): v is User {
  return (
    typeof v === 'object' &&  // must be an object

    'id' in v &&              // id property exists

const clean = [1, null, 2, undefined].filter(isNonNull);

// 4. Assertion function — narrows or throws (no if needed)
function assertIsString(v: unknown): asserts v is string {
//                                    ^^^^^^^^^^^^^^^^

  if (typeof v !== 'string') throw new TypeError(`Expected string`);

Common Mistakes and How to Avoid Them

1. Lying to the compiler — returning true without checking
typescript
// WRONG — this "guard" proves nothing; it's just a cast in disguise
function isUser(v: unknown): v is User {
  return true; // ❌ TypeScript trusts this — silent runtime crashes
}

// CORRECT — actually validate the shape
function isUser(v: unknown): v is User {
  return (
    typeof v === 'object' && v !== null &&
    typeof (v as User).id   === 'number' &&
    typeof (v as User).name === 'string'
  );
}
2. Not checking for null before object property access in the guard
typescript
// WRONG — typeof null === 'object', so this crashes on null input
function isUser(v: unknown): v is User {
  return typeof v === 'object' && 'id' in v; // ❌ in null throws
}

// CORRECT — always check v !== null when checking object type
function isUser(v: unknown): v is User {
  return typeof v === 'object' && v !== null && 'id' in v;
}
3. Using guards for discriminated unions that don't need them
typescript
// OVER-ENGINEERED — discriminant property already works
function isCircle(s: Shape): s is Circle { return s.kind === 'circle'; }

// SIMPLER — just use the discriminant directly
if (shape.kind === 'circle') { /* TypeScript already narrows here */ }
4. Not validating array elements in array guards
typescript
// WRONG — only checks if it's an array, not what's in it
function isUserArray(v: unknown): v is User[] {
  return Array.isArray(v); // ❌ items could be anything
}

// CORRECT — validate each element
function isUserArray(v: unknown): v is User[] {
  return Array.isArray(v) && v.every(isUser); // ✅ check each element
}

Best Practices

1
Make guards thorough — check every required property. A guard that only checks some fields will let malformed data slip through. Validate every field that you'll access after narrowing. For complex types, use Zod instead of writing guards by hand.
2
Name guards isSomething or hasSomething. The naming convention signals to readers that the function is a predicate with a type narrowing effect, not a regular boolean function.
3
Use assertion functions for "validate or throw" scenarios. assertIsUser(x) is cleaner than if (!isUser(x)) throw new Error(...) when you always want to throw on invalid input. Assertion functions narrow the type for the rest of the calling scope.
4
Export reusable guards as standalone functions. A guard like isNonNull or isProduct should live in its own file and be imported wherever needed — don't inline the predicate in every filter call.
5
Consider Zod for production API validation. Zod generates TypeScript types from schemas and provides a safe .safeParse() that returns a discriminated union you can narrow. The resulting type is guaranteed correct — no hand-rolled guard needed.
6
Test your guards with invalid inputs. Unlike TypeScript type checks, guards are runtime code and can have bugs. Unit-test each guard with valid, missing-field, wrong-type, and null inputs.

Interview Questions

EasyQ: What is a user-defined type guard and what syntax does it use?
A user-defined type guard is a function that returns a type predicate — a special return type annotation of the form param is Type. When this function returns true, TypeScript narrows the parameter to Type in the true branch. Example: function isString(v: unknown): v is string { return typeof v === 'string'; }. The predicate syntax tells the compiler "trust me, if this function returns true, the argument is of that type." Without the is syntax, the function is just a regular boolean predicate with no narrowing effect.
EasyQ: How does TypeScript handle the false branch of a type guard?
In the false branch, TypeScript applies Exclude<OriginalType, GuardedType> — it removes the guarded type from the union. For example, if the argument is User | Admin and isUser(arg) returns false, the false branch narrows arg to Admin (assuming those are the only two members). If the argument is unknown, the false branch is still unknown because there's no union to narrow against. This bidirectional narrowing makes type guards useful for exhaustively handling union members without a switch statement.
MediumQ: What is an assertion function and how does it differ from a type predicate?
An assertion function uses the syntax function assert(v: unknown): asserts v is Type. Instead of returning a boolean, it either throws (if the check fails) or returns normally. When it returns normally, TypeScript narrows the type for the rest of the calling scope — not just inside an if branch. This is useful for "validate or crash" scenarios: assertIsUser(x); x.name; // x is User from here on. Type predicates narrow inside a conditional; assertion functions narrow from that point forward in the function body.
MediumQ: Can TypeScript verify that your type guard implementation is actually correct?
No — TypeScript takes your type predicate on faith. If your guard function has the signature v is User but the implementation returns true unconditionally, TypeScript will treat every value as a User without complaint. This is a fundamental limitation: type guards are a bridge between runtime behavior and compile-time types, and the compiler can't verify runtime behavior statically. The responsibility for correctness is entirely yours. This is why libraries like Zod are valuable — their types are derived from the schema, so the runtime validation and compile-time type are guaranteed to stay in sync.
HardQ: How would you write a generic type guard for a Zod schema to avoid writing guards by hand?
Use Zod's z.infer to derive the TypeScript type and .safeParse() to validate: function makeGuard<T>(schema: z.ZodType<T>) { return (v: unknown): v is T => schema.safeParse(v).success; }. Then: const isUser = makeGuard(userSchema); const isProduct = makeGuard(productSchema);. This pattern generates fully correct, schema-driven type guards without hand-rolling property checks. The guard is guaranteed to be accurate because it's derived from the same schema that defines the type — any drift is impossible. This is the production pattern for API response validation.
