Enums are one of TypeScript's most distinctive features — they don't exist in vanilla JavaScript at all. An enum defines a closed set of named constants, replacing magic numbers and disconnected string literals with self-documenting, type-safe names. This module covers all three flavors: numeric enums that map names to auto-incrementing integers (with bidirectional lookup), string enums that serialize to human-readable text, and const enums that vanish entirely at compile time for zero-overhead constants. You'll learn exactly when to reach for each kind, and when a simple union type might serve you better.

Numeric Enums Intermediate ▶

Simple Explanation

A numeric enum is like a numbered list where TypeScript automatically assigns a number to each label. If you define Up, Down, Left, Right, TypeScript quietly assigns 0, 1, 2, 3 behind the scenes. You write the name; TypeScript handles the number.

Technical Explanation

A numeric enum maps string identifiers to integer values at compile time. The compiler starts at 0 (or a custom initializer) and auto-increments for each subsequent member. Crucially, it also generates a reverse mapping in the compiled JavaScript — so you can look up a member's name by its number: Direction[0] === "Up". The enum becomes a real JavaScript object with entries in both directions.

The Problem It Solves

In JavaScript, fixed value sets are typically loose constants or magic numbers. When someone writes if (status === 2), you have no idea what 2 means without reading the entire codebase. There's no grouping, no autocomplete, and no protection against passing 99 where only 0–4 is valid.

javascript
// Without enums — magic numbers everywhere
function processOrder(status) {
  if (status === 2) {        // What does 2 mean? Shipped? Cancelled?
    console.log("Shipped!");
  }
}
processOrder(2);   // Works, but is 2 correct?
processOrder(99);  // No error! Silently wrong.
typescript
// With numeric enum — intent is self-documenting
enum OrderStatus { Pending, Processing, Shipped, Delivered, Cancelled }

function processOrder(status: OrderStatus): void {
  if (status === OrderStatus.Shipped) {
    console.log("Shipped!");
  }
}

processOrder(OrderStatus.Shipped);  // ✓ clear intent
// processOrder(99);  // ✗ Error: '99' not assignable to type 'OrderStatus'

When Numeric Enums Are the Right Choice

  • State machines with ordering: Order status, workflow stages — when you need to compare states: if (status <= OrderStatus.Processing).
  • Role hierarchies: enum Role { Guest, User, Moderator, Admin } — numeric ordering lets you do if (role >= Role.Moderator) for tiered checks.
  • Bit flag permissions: Read = 1, Write = 2, Execute = 4 — combine with |, test with &. Numeric values are required for bitwise logic.
  • Reverse lookup needed: When you receive a numeric code from a database or API and need to show a human-readable label: OrderStatus[code].
  • Exhaustive switch statements: TypeScript's exhaustiveness checking works perfectly with enums in switch blocks.

When to Avoid Numeric Enums

  • Serialization boundaries: JSON.stringify({ status: OrderStatus.Shipped }) produces {"status":2} — meaningless to API consumers or DBA reviewing the database. Use string enums instead.
  • Simple boolean toggles: Two states (active/inactive, on/off) — a boolean is cleaner and more obvious.
  • Open-ended sets: If new values will be added by external parties, a union type type Status = "pending" | "shipped" is easier to extend safely.
  • Library tree-shaking: Numeric enums generate real JS objects bundlers can't eliminate. Prefer const enum or as const objects in published libraries.

What TypeScript Compiles to

TypeScript compiles numeric enums into an IIFE that builds a bidirectional object. The trick: JavaScript assignment expressions evaluate to their assigned value, so TypeScript exploits this to run two assignments in one statement.

typescript
enum Direction { Up, Down, Left, Right }
javascript
var Direction;
(function (Direction) {
  Direction[Direction["Up"] = 0] = "Up";
  // Direction["Up"] = 0  →  evaluates to 0
  // Direction[0] = "Up"  →  runs as the outer assignment
  Direction[Direction["Down"] = 1] = "Down";
  Direction[Direction["Left"] = 2] = "Left";
  Direction[Direction["Right"] = 3] = "Right";
})(Direction || (Direction = {}));

// Resulting object has BOTH directions:
// { Up:0, Down:1, Left:2, Right:3, 0:"Up", 1:"Down", 2:"Left", 3:"Right" }

The IIFE pattern (Direction || (Direction = {})) supports declaration merging — running it multiple times extends the same object. This bidirectional object enables both Direction.Up === 0 and Direction[0] === "Up".

typescript
enum Direction {         // 'enum' keyword, then PascalCase name
  Up,                    // auto-assigned: 0
  Down,                  // auto-assigned: 1
  Left,                  // auto-assigned: 2
  Right                  // auto-assigned: 3
}

enum StatusCode {
  OK          = 200,     // explicit initializer — overrides auto-increment
  Created     = 201,     // subsequent members continue from here
  BadRequest  = 400,     // can jump to any integer
  NotFound    = 404,
  ServerError = 500
}

enum Permission {
  None    = 0,
  Read    = 1 << 0,     // bit shift: evaluates to 1
  Write   = 1 << 1,     // bit shift: evaluates to 2
  Execute = 1 << 2,     // bit shift: evaluates to 4
  All     = Read | Write | Execute  // references to other members: 7
}

const dir: Direction = Direction.Up;   // type uses the enum name
console.log(dir);           // Output: 0  (the numeric value)
console.log(Direction[0]);  // Output: "Up"  (reverse lookup)

const perms = Permission.Read | Permission.Write;  // combine: 3
const canRead = (perms & Permission.Read) !== 0;   // check: true

Enum names and members use PascalCase by convention. Custom initializers can be integer literals, bit-shift expressions, or arithmetic on earlier member references.

// Express route handler — order status update with role authorization

enum OrderStatus { Pending=0, Processing=1, Shipped=2, Delivered=3, Cancelled=4 }
enum UserRole    { Guest=0, Customer=1, Support=2, Admin=3 }

interface Order {
  id:        string;
  userId:    string;
  status:    OrderStatus;
  updatedAt: Date;
}

interface AuthUser {
  id:   string;
  role: UserRole;
}

// Business rule: only Support+ can cancel after shipping
function canTransition(
  order: Order, newStatus: OrderStatus, actor: AuthUser
): boolean {
  if (newStatus === OrderStatus.Cancelled) {
    if (order.status >= OrderStatus.Shipped) return actor.role >= UserRole.Support;
    return order.status <= OrderStatus.Processing; // customer can cancel early
  }
  return true; // other transitions are unrestricted here
}

async function handleStatusUpdate(
  req: { body: { orderId: string; status: number }; user: AuthUser },
  res: { json: (v: unknown) => void; status: (n: number) => any }
): Promise<void> {
  const newStatus = req.body.status as OrderStatus;

  // Validate: is this a real enum value?
  if (typeof newStatus !== "number" || !(newStatus in OrderStatus)) {
    res.status(400).json({ error: "Invalid status code" });
    return;
  }

  // Reverse lookup for logging — shows "Shipped" not "2"
  console.log(`Transition request: → ${OrderStatus[newStatus]}`);
  res.json({ status: newStatus, label: OrderStatus[newStatus] });

  • Role-based access: Numeric ordering lets you write if (role >= Role.Admin) for tiered permissions — impossible with string enums.
  • Game state machines: enum GameState { MainMenu, Loading, Playing, Paused, GameOver } — typed transitions between a closed set of states.
  • WebSocket opcodes: RFC 6455 defines numeric opcodes (1=TEXT, 2=BINARY, 8=CLOSE, 9=PING) — numeric enums map these directly to meaningful names.
  • Permission bit flags: Combining Read | Write produces a number you can store in a single database integer column, then decompose later.
  • Sort direction: enum SortOrder { Asc=1, Desc=-1 } — the numeric value doubles as the sort multiplier in query builders.

1. Assuming TypeScript rejects all invalid numbers

typescript
// WRONG assumption
enum Color { Red, Green, Blue }
const c: Color = 100;  // TypeScript ALLOWS this — no error!
// Intentional: enables bit-flag combinations (Read | Write = 3, not a single member)

// CORRECT: validate at runtime for data from external sources
function setColor(c: Color): void {
  if (!(c in Color)) throw new Error(`Invalid color: ${c}`);
}

2. Using numeric enums in JSON responses

typescript
// WRONG — API consumers see numbers, not names
enum Status { Active, Inactive }
JSON.stringify({ status: Status.Active });  // '{"status":0}' — meaningless

// CORRECT — use string enum for anything serialized
enum Status { Active = "ACTIVE", Inactive = "INACTIVE" }
JSON.stringify({ status: Status.Active });  // '{"status":"ACTIVE"}'

3. Expecting reverse lookup on string enums

typescript
// WRONG — carrying numeric habit to string enums
enum Dir { Up = "UP" }
(Dir as any)["UP"];  // undefined — string enums have NO reverse mapping

// CORRECT — reverse lookup only exists for numeric enums
enum NumDir { Up = 0 }
NumDir[NumDir.Up];   // "Up" ✓

4. Heterogeneous enums (mixing types)

typescript
// BAD — TypeScript allows but it's confusing and almost never useful
enum Mixed { A = 1, B = "hello" }

// GOOD — pick one type consistently
enum Directions { Up = "UP", Down = "DOWN" }  // all string
enum Priority   { Low = 1, Medium = 2, High = 3 }  // all numeric
  1. PascalCase for names and members. enum OrderStatus { Pending, Shipped } — the TypeScript community standard. Not ORDER_STATUS or orderStatus.
  2. Assign explicit values when the number is meaningful. If your database stores 0=pending, write Pending = 0 explicitly. Reserve auto-increment only when relative ordering is all that matters.
  3. Switch to string enums at serialization boundaries. The moment a value appears in JSON, a log file, or a database column, numeric values become opaque. Use string enums there.
  4. Use const enum when you never need to iterate. If Object.values() is never called on it, const enum is more efficient (zero runtime object).
  5. Validate incoming numbers with Zod. Use z.nativeEnum(MyEnum) at API/external boundaries — TypeScript's types can't protect you from runtime data.
  6. Document bit-flag enums clearly. Bitwise operations are non-obvious to readers who haven't used them — a short JSDoc comment on the enum is worth it.
  7. Consider union types for small, simple sets. type Dir = "up" | "down" has no overhead and is equally type-safe when you don't need runtime iteration or reverse lookup.
EasyWhat are numeric enums, and what are their default values?
A numeric enum maps named constants to integer values. By default the first member is 0 and each subsequent member auto-increments by 1. You can override the start: enum Foo { A = 5, B, C } gives A=5, B=6, C=7. TypeScript also generates a reverse mapping so Foo[5] returns "A".
EasyWhat is the difference between numeric and string enums?
Numeric enums generate bidirectional mappings (name→number AND number→name) and auto-increment values. String enums generate only a one-way mapping and require every member to have an explicit string value. Numeric enums support reverse lookup and numeric comparison; string enums are safe for serialization to JSON or databases.
MediumWhat JavaScript does TypeScript generate for a numeric enum?
TypeScript generates an IIFE that mutates an object to create bidirectional mappings. For enum Dir { Up } it emits: var Dir; (function(Dir){ Dir[Dir["Up"]=0]="Up"; })(Dir||(Dir={}));. The trick Dir[Dir["Up"]=0]="Up" simultaneously sets Dir.Up=0 and Dir[0]="Up".
MediumWhen would you choose a union type over a numeric enum?
Use a union type when the values are strings for serialization, when tree-shaking matters (unions compile to nothing), when the set may be extended externally, or when you want purely structural compatibility. Use numeric enums when you need the runtime object for iteration or reverse lookup, for bit-flag patterns, or when numeric comparison is needed.
HardTypeScript allows assigning arbitrary numbers to numeric enum variables. Why, and how do you protect against it at runtime?
TypeScript intentionally allows this to support bit-flag patterns — combining Flags.Read | Flags.Write produces 3, which isn't any single member value. To protect against truly invalid values at runtime, validate incoming data at system boundaries using Object.values(MyEnum).includes(val) or Zod's z.nativeEnum(MyEnum).

String Enums Intermediate ▶

Simple Explanation

A string enum is like a numeric enum but each member's value is a meaningful string you set explicitly. Instead of Status.Shipped === 2, you get Status.Shipped === "SHIPPED". The value speaks for itself wherever it shows up — in JSON, database columns, log files, or DevTools.

Technical Explanation

Every string enum member requires an explicit string literal initializer — there is no auto-incrementing. TypeScript compiles a string enum to a one-way mapping object (name→value only), with no reverse mapping. String enums are also nominally typed: two different enums that happen to share identical string values are still distinct, incompatible types at the TypeScript level.

The Problem It Solves

Numeric enums become opaque the moment they leave your TypeScript process. JSON.stringify({ status: OrderStatus.Shipped }) produces {"status":2}. Your API consumers see 2. Your DBA sees 2 in the database. Your logs show 2. Nobody knows what 2 means without a lookup table. String enums eliminate this "decoder ring" problem entirely.

javascript
// Problem: data becomes opaque at serialization boundaries
const order = { status: 2 };
JSON.stringify(order);  // '{"status":2}' — what does 2 mean?
// SELECT * FROM orders WHERE status = 2  — DBA needs a lookup table
typescript
// Solution: string enum values are self-documenting everywhere
enum OrderStatus {
  Pending   = "PENDING",
  Shipped   = "SHIPPED",
  Delivered = "DELIVERED"
}

JSON.stringify({ status: OrderStatus.Shipped });
// '{"status":"SHIPPED"}' — clear to any consumer, no decoder ring needed
// Database: SELECT * FROM orders WHERE status = 'SHIPPED'  — readable

When String Enums Are the Right Choice

  • API payloads: Any enum value that appears in a JSON request or response body — string values are readable without documentation.
  • Database columns: Stored as plain text — readable in SQL queries, migration files, and database admin tools without a reference table.
  • Log messages: [INFO] User created is far more useful in logs than [1] User created.
  • Redux action types: String values appear in Redux DevTools — "posts/FETCH" is informative while 0 is not.
  • Config keys that must match external systems: When enum values must exactly match string keys used by a feature-flag service, i18n system, or remote config.

When to Avoid String Enums

  • Bit-flag patterns: You need numeric values for bitwise | and & operations — string enums can't be combined that way.
  • Reverse lookup needed: Enum["VALUE"] returns undefined for string enums — no reverse mapping is generated. Build a manual helper if needed.
  • Auto-incrementing sequences: If the specific numeric value matters (database ID, HTTP status code), numeric enums with explicit values are more appropriate.
  • Boolean pairs: enum Enabled { Yes = "YES", No = "NO" } is over-engineering — use a boolean.

Compiled JavaScript Output

String enums compile to a simpler object than numeric enums — just forward assignments, no reverse-mapping lines.

typescript
enum Direction { Up = "UP", Down = "DOWN", Left = "LEFT", Right = "RIGHT" }
javascript
var Direction;
(function (Direction) {
  Direction["Up"]    = "UP";    // only forward mapping
  Direction["Down"]  = "DOWN";  // no Direction["UP"] = "Up" generated
  Direction["Left"]  = "LEFT";
  Direction["Right"] = "RIGHT";
})(Direction || (Direction = {}));

// Resulting object: { Up:"UP", Down:"DOWN", Left:"LEFT", Right:"RIGHT" }
// Direction["UP"] → undefined  (no reverse mapping for string enums)

Why no reverse mapping? TypeScript can't guarantee string values won't collide with member names — using the string value as an object key risks overwriting a forward-mapping entry. Numeric enums use integer keys which are safe; string enums use string keys which might conflict. TypeScript chose the safe path: no reverse mapping.

Nominal typing in practice: Even if enum A { X = "X" } and enum B { X = "X" } have identical string values, TypeScript treats them as distinct types. A function accepting A rejects a B — intentional domain separation.

  name:   z.string().min(1).max(100),
  email:  z.string().email(),
  role:   z.nativeEnum(UserRole).default(UserRole.Customer),
  status: z.nativeEnum(AccountStatus).default(AccountStatus.Active)
});

async function handleCreateUser(req: Request, res: Response): Promise<void> {
  const result = createUserSchema.safeParse(req.body);
  if (!result.success) {
    res.status(400).json({ errors: result.error.flatten() });
    return;
  }
  const { name, email, role, status } = result.data;

  // role is now definitely UserRole — "CUSTOMER", "ADMIN", etc.
  // Database INSERT stores "CUSTOMER" → readable in SQL without a lookup table
  console.log(`Creating ${role} user: ${name} (${status})`);

  res.status(201).json({ name, email, role, status });
}

2. Expecting reverse lookup to work

typescript
// WRONG — string enums have NO reverse mapping
enum Color { Red = "RED" }
(Color as any)["RED"];  // undefined — doesn't exist in the compiled object

// CORRECT: build a helper when value→key lookup is needed
function findKey<T extends Record<string, string>>(
  enumObj: T, value: string
): keyof T | undefined {
  return Object.entries(enumObj).find(([, v]) => v === value)?.[0] as keyof T;
}
findKey(Color, "RED");  // "Red"

3. Missing initializers

typescript
// WRONG — every string enum member must have an explicit value
enum Broken { A = "hello", B }  // ✗ Error: must have initializer

// CORRECT
enum Fixed { A = "hello", B = "world" }
  1. Use UPPER_SNAKE_CASE for string values. Active = "ACTIVE" matches REST API conventions and stands out in JSON output and database queries.
  2. The value IS the API contract. If your API docs say status: "SHIPPED", your enum value must be "SHIPPED" — keep them in sync.
  3. Always validate incoming string values. Use z.nativeEnum(MyEnum) at API and database-read boundaries — TypeScript can't protect you from external data at runtime.
  4. Prefer string enums over numeric for any cross-process data. Serialization, database storage, logs, external APIs — all benefit from readable string values.
  5. Keep member names and values semantically aligned. Email = "EMAIL" is clear; Email = "xyz" is confusing — both name and value should describe the same concept.
  6. Use string enums in Redux for DevTools. Action type strings appear directly in the Redux DevTools time-travel debugger — descriptive values are invaluable there.
  7. Document string enum values in OpenAPI specs. The values in your enum are the wire-format contract — include them as the enum constraint on the relevant schema field.
EasyWhat must you provide for every string enum member, and why?
Every string enum member requires an explicit string literal initializer. Unlike numeric enums, there is no auto-incrementing for strings. TypeScript errors if any member lacks a value. This ensures each member maps to a predictable, documented string rather than an auto-generated integer.
EasyDo string enums support reverse mapping like numeric enums?
No. String enums generate only a forward mapping (name→value). Direction["UP"] returns undefined because no reverse-mapping line is emitted. TypeScript chose not to generate reverse mappings for string enums because string values could collide with member names in the compiled object.
MediumHow do you safely parse an unknown string into a string enum at runtime?
The safest approach is Zod: z.nativeEnum(MyEnum).parse(rawValue) — throws with a descriptive error for invalid values. Without Zod, use a type guard: function isMyEnum(v: string): v is MyEnum { return Object.values(MyEnum).includes(v as MyEnum); }. Never use val as MyEnum without validation — it bypasses type safety.
MediumWhen would you choose a string enum over a union type like "ACTIVE" | "INACTIVE"?
Choose a string enum when you need a runtime object (to iterate with Object.values() or use with z.nativeEnum()), when you want nominal typing to prevent mixing same-valued enums from different domains, or when exposing typed constants in a library. Choose a union type when you want lighter output, better tree-shaking, or structural compatibility across modules.
HardExplain how string enums and union types behave differently when they have the same values.
String enums are nominally typed — enum A { X = "X" } and enum B { X = "X" } are distinct types even though both contain the string "X". A function expecting A rejects a B value. Union types are structurally typed — type A = "X" and type B = "X" are identical and interchangeable. This matters when two domain concepts share string values: string enums enforce domain separation that union types cannot provide.

Const Enums Advanced ▶

Simple Explanation

A const enum is a "phantom" enum — it exists only while TypeScript compiles your code. By the time JavaScript runs, every reference to a const enum member has been replaced with its literal value, and the enum itself has been completely removed. Think of it as a find-and-replace operation at compile time.

Technical Explanation

A const enum triggers compile-time inlining. The TypeScript compiler replaces every reference to a const enum member with its literal value (e.g., Direction.Up becomes 0) and discards the enum declaration entirely. No JavaScript object is emitted, no IIFE runs, and no memory is allocated for the enum at runtime. The result is zero overhead — equivalent to writing the literal values by hand, but with full type safety and autocomplete while coding.

The Performance Problem

Regular enums generate JavaScript objects and every member access is a property lookup at runtime. In performance-critical code — game loops running at 60fps, Canvas rendering, signal processors — this overhead accumulates. A const enum inlines the literal value at the usage site: zero property lookups, zero object allocation, zero memory footprint for the enum.

typescript
// Regular enum — generates JS object, each use is a property lookup
enum Direction { Up = 0, Down = 1 }
const x = Direction.Up;
// Compiled: const x = Direction.Up;  (runtime object access)

// Const enum — no JS object, each use becomes a literal
const enum Direction { Up = 0, Down = 1 }
const x = Direction.Up;
// Compiled: const x = 0;  (literal — no object at all)
javascript
// Regular enum compiled output:
var Direction;
(function (Direction) {
  Direction[Direction["Up"] = 0] = "Up";
  Direction[Direction["Down"] = 1] = "Down";
})(Direction || (Direction = {}));
const x = Direction.Up;  // runtime property lookup

// Const enum compiled output:
const x = 0 /* Direction.Up */;  // literal inlined — nothing else emitted

Const enums are also useful for library authors who don't want to ship a runtime enum object — consumers get type safety and autocomplete with zero dependency on a runtime object.

When Const Enums Are the Right Choice

  • Performance-critical hot paths: Game loops, Canvas/WebGL rendering, audio processing — any code called thousands of times per second where property lookups matter.
  • Library authoring: Ship typed constants to consumers with zero bundle-size impact — no runtime object is included in the consumer's bundle.
  • Pure compile-time constants: Key codes, GL constants, HTTP codes that you reference by name for readability but will never iterate at runtime.
  • Declaration files (.d.ts): Ambient const enums let consuming TypeScript code inline values at compile time without importing any runtime module.
  • Bundle size optimization: When every byte matters, const enums avoid emitting the IIFE boilerplate that regular enums generate.

When to Avoid Const Enums

  • When iteration is needed: Object.values(Direction), Object.keys(Direction) — the object doesn't exist at runtime; calling these throws a ReferenceError.
  • Reverse lookup: Direction[0] fails at runtime for the same reason — no object to index into.
  • With isolatedModules builds (Vite, esbuild, Babel, swc): These tools compile each file independently and cannot inline const enum values from other files. Cross-file exported const enums will break with these bundlers.
  • In declaration files consumed by JavaScript: JS consumers can't benefit from TypeScript's inlining and will encounter ReferenceErrors.
  • When values might change in large monorepos: Changing a const enum value forces recompilation of every file that uses it — regular enums only require recompiling the definition file.

Compile-Time Inlining

When TypeScript sees a const enum declaration, it stores the member values internally during compilation. Every reference to a member is replaced with the literal, and an explanatory comment is optionally added.

typescript
const enum HttpStatus { OK=200, NotFound=404, ServerError=500 }

function handleStatus(status: HttpStatus): string {
  switch (status) {
    case HttpStatus.OK:          return "Success";
    case HttpStatus.NotFound:    return "Not found";
    case HttpStatus.ServerError: return "Server error";
    default: return "Unknown";
  }
}
javascript
// Compiled output — enum declaration is gone, values are inlined
function handleStatus(status) {
  switch (status) {
    case 200 /* HttpStatus.OK */:          return "Success";
    case 404 /* HttpStatus.NotFound */:    return "Not found";
    case 500 /* HttpStatus.ServerError */: return "Server error";
    default: return "Unknown";
  }
}
// No 'var HttpStatus = ...' anywhere — the object was never emitted

The /* EnumName.Member */ comments are added by default for readability. They can be stripped with "removeComments": true in tsconfig. Setting "preserveConstEnums": true makes TypeScript additionally emit the enum object (for debugging) while still inlining all references.

  2. Add "isolatedModules": true to tsconfig to catch issues early. This flag makes tsc itself flag const enum cross-file usage problems before your bundler does.
  3. Use "preserveConstEnums": true in development. Emits the enum object alongside inlined values so you can inspect it in DevTools — no production behavior change.
  4. Document inlined values in comments when the source isn't obvious. case 0x0404: is hard to read in compiled output without context — a comment helps.
  5. Use const enums only for constants you'll never iterate. Simple rule: if you'll never call Object.values() on it, const enum is fine.

  7. Prefer const enums for internal hot-path constants. Key codes, GL constants, bitmasks — high-frequency references in tight loops are the sweet spot for const enums.
EasyWhat is the key difference between a regular enum and a const enum?
A regular enum generates a JavaScript object at runtime. A const enum is erased entirely at compile time — every reference is replaced with the literal value. Direction.Up in a regular enum is a runtime object property lookup; in a const enum it compiles directly to 0. No object, no lookup, no memory footprint.
MediumWhat is the isolatedModules problem with const enums?
The isolatedModules flag (used by esbuild, Babel, Vite, swc) compiles each file independently without reading other files. Const enum values from external files can't be inlined during per-file compilation because those values aren't available. The fix is to use regular enums, or restrict const enums to within the same file where they're defined.
MediumCan you use reverse lookup with a const enum? Why or why not?
No. Since const enums don't generate a runtime object, Direction[0] throws a ReferenceError — Direction doesn't exist as a variable. Reverse lookup requires a runtime object, which const enums deliberately don't create. Use a regular enum if reverse lookup is needed.
HardHow does preserveConstEnums in tsconfig affect compilation?
With "preserveConstEnums": true, TypeScript still inlines all const enum references at usage sites (no behavior change for the compiled logic) but additionally emits the enum object declaration in the output. This lets you inspect the enum in DevTools during development without affecting production runtime behavior. It's a debugging convenience — not a semantic change.
HardDescribe a portable alternative to const enums that achieves similar type safety with no build-tool limitations.
Use an as const object with a derived type: const Direction = { Up: 0, Down: 1 } as const; type Direction = typeof Direction[keyof typeof Direction];. The type only accepts 0 or 1, the runtime object is a plain object (tree-shakeable), there are no isolatedModules issues, and iteration works normally with Object.values(Direction). The tradeoff is more boilerplate — you define the object and derive the type separately.
