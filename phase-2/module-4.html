Generics are the feature that separates intermediate TypeScript from beginner TypeScript. They let you write functions, interfaces, and types that work with any type while maintaining complete type safety — no any, no casting, no guessing. Think of generics as a rubber stamp that preserves whatever shape you pour through it. By the end of this module you'll write reusable, type-safe utilities that feel as flexible as JavaScript but as safe as fully typed code.

▶Generic Functions
Beginner

Simple Explanation

A generic function is like a mold you can pour any material into — the shape it produces is always consistent, but it adapts to whatever you put in. You write the function logic once and TypeScript automatically figures out the specific type each time you call it.

Technical Explanation

A generic function declares one or more type parameters (written between <angle brackets>) alongside its regular parameters. These type parameters act as placeholders that TypeScript resolves — through explicit annotation or automatic inference — at each call site. The key guarantee: type information flows through the function without being lost, unlike with any.

The Problem Without Generics

Without generics you face a painful trade-off: write one overload per type, or surrender type safety with any.

typescript
// Without generics — loses the specific type
function identity(arg: any): any { return arg; }

const result = identity("hello");
result.toUpperCase();  // no autocomplete, no safety
result.doesNotExist(); // TypeScript won't catch this bug!

The Solution With Generics

typescript
// With generics — type information is preserved
function identity<T>(arg: T): T { return arg; }

const result = identity("hello"); // result: string
result.toUpperCase();  // ✓
result.doesNotExist(); // ✗ Error caught at compile time

When Generic Functions Are the Right Tool

  • The return type mirrors the input type — if you return what you receive, the output type should match the input.
  • Writing array or collection utilities — first, last, chunk, zip work on any element type.
  • Building API fetch wrappers — the response shape changes per endpoint: get<User>('/api/user').
  • Writing transformation wrappers — caching, retry, debounce utilities work generically without caring about the inner type.
  • Avoiding near-duplicate functions — if you're writing processString, processNumber, processUser, that's a generic waiting to be written.

When NOT to Use Generic Functions

  • When the function only ever works with one type — just type it directly; don't add a pointless <T>.
  • When a union type is simpler — if a function accepts string or number, string | number is cleaner than a constrained generic.
  • When you have 4+ type parameters — design smell; break it into smaller composable pieces.
  • When T only appears in one position (input OR output, not both) — generics add value when the type relationship flows end-to-end. If T appears only once, use unknown instead.

What TypeScript Does Under the Hood

Generics are a purely compile-time feature. Here's what happens step by step:

  1. You write function identity<T>(arg: T): T — TypeScript stores this as a template with a free variable T.
  2. At each call site, TypeScript performs type argument inference. When you write identity("hello") it sees the argument is string and sets T = string.
  3. TypeScript then validates the function body with T replaced by string, verifying all constraints hold.
  4. At compilation, all type annotations are erased completely — zero runtime cost.
typescript
// TypeScript source
function identity<T>(arg: T): T { return arg; }

// Compiled JavaScript — generics are completely erased
function identity(arg) { return arg; }

Fully Annotated Syntax

typescript
// Basic generic function declaration
function identity<T>(arg: T): T {
//              ^^^  ^^^^^  ^
//              |    |      return type — T flows through
//              |    parameter type — placeholder resolved at call site
//              type parameter declaration
  return arg;
}

// Arrow function generic
const identity = <T>(arg: T): T => arg;

// Multiple type parameters
function pair<A, B>(first: A, second: B): [A, B] {
  return [first, second];
}

// Explicit type arg (usually unnecessary — TypeScript infers)
const r1 = identity<string>("hello"); // explicit
const r2 = identity("hello");          // inferred — prefer this

// In .tsx files, trailing comma disambiguates from JSX
const fn = <T,>(arg: T): T => arg;

Practical Code Example

typescript
// Generic array utilities — write once, works for any element type

function getFirst<T>(arr: T[]): T | undefined {
  return arr[0];
}

function getLast<T>(arr: T[]): T | undefined {
  return arr[arr.length - 1];
}

function swap<A, B>(pair: [A, B]): [B, A] {
  return [pair[1], pair[0]];
}

function chunk<T>(arr: T[], size: number): T[][] {
  const result: T[][] = [];
  for (let i = 0; i < arr.length; i += size) result.push(arr.slice(i, i + size));
  return result;
}

const nums = [1, 2, 3, 4, 5];
const first = getFirst(nums);    // Type: number | undefined
const parts = chunk(nums, 2);   // Type: number[][]

const strs = ["a", "b", "c"];
const firstStr = getFirst(strs); // Type: string | undefined

const swapped = swap([42, "hello"]); // Type: [string, number]
// Output: ["hello", 42]

Real-World Example

typescript
// Typed API fetch wrapper — used across an Express + React app

interface ApiError { message: string; code: number; }

async function apiFetch<T>(
  url: string,
  options?: RequestInit
): Promise<T> {
  const res = await fetch(url, options);
  if (!res.ok) {
    const err: ApiError = await res.json();
    throw new Error(err.message);
  }
  return res.json() as Promise<T>;
}

interface User    { id: number; name: string; email: string; }
interface Product { id: number; title: string; price: number; }

// Each call site gets the exact type — no casting needed
const user    = await apiFetch<User>('/api/users/1');
console.log(user.email);          // ✓ string

const products = await apiFetch<Product[]>('/api/products');
console.log(products[0].price);  // ✓ number

Real-World Use Cases

  • React's useState hook — useState<User | null>(null) types state precisely without runtime checks everywhere.
  • React Query's useQuery — useQuery<User[], Error> types both data and error so components get full autocomplete.
  • Axios/fetch wrappers — every team's internal HTTP client uses generics so each endpoint call returns the right type without casting.
  • Lodash utilities — _.chunk<T>, _.groupBy<T> preserve the element type through each transformation.
  • Async retry/timeout wrappers — a withRetry<T> function wraps any async operation without losing its return type.
  • Promise combinators — Promise.all<[A, B, C]> is itself generic so destructured results have the right types.

Common Mistakes

Mistake 1 — Using any inside the generic body
typescript
// WRONG — defeats the purpose entirely
function wrap<T>(val: T): { value: any } { return { value: val }; }

// CORRECT — T flows all the way through
function wrap<T>(val: T): { value: T } { return { value: val }; }

Once you use any in the return type, callers lose all type information.

Mistake 2 — Unnecessary explicit type arguments
typescript
// WRONG — verbose, TypeScript can infer this
const r = identity<string>("hello");

// CORRECT — let inference do the work
const r = identity("hello");
Mistake 3 — Generic where T appears only once
typescript
// WRONG — T only in input, return is void; generic adds nothing
function log<T>(val: T): void { console.log(val); }

// CORRECT — unknown or any is more honest here
function log(val: unknown): void { console.log(val); }

Best Practices

1
Use conventional single-letter names: T (primary), K (key), V (value), E (element), R (return)

This is established convention. Longer names like TItem are considered noise.

2
Let TypeScript infer type arguments — only specify them when inference would be wrong

Type argument inference is one of TypeScript's best features. Forcing explicit args everywhere adds noise.

3
Constrain type parameters when you access their properties

If you access arg.length inside a generic, add T extends { length: number }. Without it TypeScript can't verify T has that property.

4
Keep generic functions focused — one concern per type parameter

If you reach fn<A, B, C, D>, the function is doing too much. Split into smaller generic functions that compose cleanly.

5
Prefer T[] over Array<T> for simple arrays

Both work. Most style guides prefer T[] for simple cases; Array<T> for nested arrays where T[][] is confusing.

Interview Questions

EasyQ: What is a generic function and why use it over any?

A generic function uses type parameters to write one function that works with multiple types while preserving type safety. Unlike any, a generic maintains the relationship between input and output types — if you pass a string, you get a string back. identity<T>(arg: T): T guarantees the return matches the input; identity(arg: any): any throws that information away.

MediumQ: How does TypeScript infer type arguments for generic functions?

TypeScript uses type argument inference — it examines the types of arguments at the call site and unifies them with the type parameter. When you call identity("hello"), TypeScript sees the argument is string and sets T = string. Inference flows from argument types, not from how the return value is used. You can override it with an explicit type argument: identity<string>("hello").

MediumQ: How do you write a generic arrow function in a .tsx file?

The parser sees <T> and thinks it's JSX, causing a parse error. Fix it with a trailing comma — <T,> — which signals "this is a type parameter, not JSX". Alternatively use <T extends unknown>. Most teams prefer the trailing comma: const fn = <T,>(arg: T): T => arg.

HardQ: What's the difference between a generic function and a function overload?

A generic function expresses that the function works uniformly across types — the same logic handles all cases. Overloads express that a function has different behaviors for different input types. Use generics when logic is truly the same regardless of type (utilities, wrappers). Use overloads when the function does something fundamentally different based on what it receives — e.g., returning a string when given a string and a number when given a number can't be expressed as a single generic.

HardQ: Can TypeScript infer a generic's type from the return context rather than the argument?

No — TypeScript only infers type parameters from argument types, not from how the return value is used. Writing const x: string = identity() hoping TypeScript infers T = string won't work. This is why JSON.parse returns any — there's no argument to infer the return type from, so a generic would require explicit annotation at every call site, which is worse ergonomics.

Key Takeaways

  • Generic functions use <T> to write one function that works safely with any type.
  • TypeScript infers type parameters from call-site arguments — you rarely need to specify them explicitly.
  • Generics are erased at compile time — compiled JavaScript looks exactly like untyped JavaScript.
  • The key benefit over any: the relationship between input and output types is preserved and verified.
  • Conventional names: T primary, K key, V value, E element, R return.
  • When T appears in only one position (not bridging input to output), prefer unknown instead.
Mental model: A generic function is a type-preserving pipe — whatever shape goes in comes out the other end with the same shape, no matter what you pour through it.
▶Generic Interfaces
Intermediate

Simple Explanation

A generic interface is a blueprint that describes the same structure for different kinds of data. Like a shipping box template — the template (lid, sides, label slots) is always the same, but you specify whether it holds books, electronics, or food when you use it.

Technical Explanation

A generic interface declares type parameters between angle brackets after the interface name. Properties, method signatures, and index signatures throughout the interface can reference those parameters. When you use the interface you supply concrete types — Box<string>, Box<number> — and TypeScript enforces the resulting shape. Generic interfaces are entirely compile-time; no JavaScript is emitted.

The Problem Without Generic Interfaces

Without them you'd write a separate interface for every variation of the same shape — UserApiResponse, PostApiResponse, OrderApiResponse — all with identical structure except the data type.

typescript
// Without generic interfaces — explosion of near-duplicate code
interface UserApiResponse  { data: User;  status: number; ok: boolean; }
interface PostApiResponse  { data: Post;  status: number; ok: boolean; }
interface OrderApiResponse { data: Order; status: number; ok: boolean; }

With Generic Interfaces

typescript
// One generic interface handles all cases
interface ApiResponse<T> { data: T; status: number; ok: boolean; }

const userResp: ApiResponse<User>  = { data: user,  status: 200, ok: true };
const postResp: ApiResponse<Post>  = { data: post,  status: 200, ok: true };
const errResp:  ApiResponse<null>  = { data: null, status: 404, ok: false };

When to Use Generic Interfaces

  • API response shapes — the wrapper structure (status, error, pagination) is always the same; only the payload type changes.
  • Repository / data-access patterns — a Repository<T> interface defines findById, save, delete for any entity type.
  • Event systems — EventHandler<T> types callback functions where T is the event payload.
  • Paginated lists — PaginatedResult<T> wraps any collection with page metadata.
  • Form state — FormState<T> holds values, errors, and dirty fields where T is the form data shape.

When NOT to Use Generic Interfaces

  • When used with only one concrete type — if UserRepository is the only implementation, skip the generic.
  • When the type parameter never appears in any property — a generic interface where T is unused is pointless indirection.
  • When a union type is more precise — sometimes { result: User } | { result: Error } is clearer because it encodes semantics the generic can't.
  • When over-abstraction hides intent — a concrete, named interface sometimes communicates more than a generic one.

How Generic Interfaces Work Internally

Generic interfaces are entirely a TypeScript compile-time concept. When you write ApiResponse<User>, TypeScript creates a virtual type where every occurrence of T is substituted with User. This virtual type is then used for all structural checks — never materialized in memory or emitted as JavaScript.

TypeScript uses structural subtyping for interface checks. An object satisfies ApiResponse<User> if it has all the required properties with the right types — TypeScript doesn't care how the object was declared, only that it has the right shape.

typescript
// Plain object satisfies ApiResponse<User> structurally — no class needed
const response = { data: { id: 1, name: "Alice", email: "a@b.com" }, status: 200, ok: true };
const typed: ApiResponse<User> = response; // ✓

Fully Annotated Syntax

typescript
// Basic generic interface
interface Container<T> {
//         ^^^^^^^^^  ^^^
//         |          type parameter used throughout the body
//         interface name
  value: T;
  transform: (fn: (v: T) => T) => Container<T>;
}

// Multiple type parameters
interface KeyValue<K, V> {
  key: K;
  value: V;
  toString(): string;
}

// Default type parameter (TypeScript 4.7+)
interface Result<T = unknown> {
  data: T;
  error: string | null;
}

// Usage
const pair: KeyValue<string, number> = { key: "age", value: 30, toString: () => "age:30" };

// Class implementing a generic interface
class UserRepo implements Repository<User> { /* ... */ }

Practical Code Example

typescript
// Generic Repository interface — classic data access pattern

interface Repository<T, ID = number> {
  findById(id: ID): Promise<T | null>;
  findAll(): Promise<T[]>;
  save(entity: T): Promise<T>;
  delete(id: ID): Promise<void>;
}

interface User    { id: number; name: string; email: string; }
interface Product { id: number; title: string; price: number; }

class UserRepository implements Repository<User> {
  async findById(id: number): Promise<User | null> { return null; }
  async findAll(): Promise<User[]> { return []; }
  async save(user: User): Promise<User> { return user; }
  async delete(id: number): Promise<void> {}
}

class ProductRepository implements Repository<Product> {
  async findById(id: number): Promise<Product | null> { return null; }
  async findAll(): Promise<Product[]> { return []; }
  async save(p: Product): Promise<Product> { return p; }
  async delete(id: number): Promise<void> {}
}

Real-World Example

typescript
// Paginated API response — common REST pattern

interface PaginatedResponse<T> {
  data: T[];
  pagination: { page: number; pageSize: number; total: number; totalPages: number; };
}

interface ApiSuccess<T> { ok: true; data: T; }
interface ApiFailure     { ok: false; error: { message: string; code: string }; }
type ApiResult<T> = ApiSuccess<T> | ApiFailure;

interface User { id: number; name: string; }

// Express route handler — clean, fully typed response
async function getUsersHandler(req: Request, res: Response) {
  const page = Number(req.query.page) || 1;
  const users: User[] = await userRepo.findAll();
  const payload: ApiResult<PaginatedResponse<User>> = {
    ok: true,
    data: { data: users, pagination: { page, pageSize: 20, total: users.length, totalPages: 1 } }
  };
  res.json(payload);
}

Real-World Use Cases

  • Repository pattern in NestJS/Express — a single Repository<T> interface contracts all data-access objects consistently, making them swappable in tests.
  • React Query — UseQueryResult<T> is a generic interface that types data, error, isLoading per query.
  • Event bus systems — EventBus<EventMap> interfaces type-safely route events to handlers based on event name.
  • React Hook Form — UseFormReturn<T> holds all form state for a specific data shape.
  • Zod schemas — internally use generic interfaces to make z.object() return a typed schema based on the object shape provided.

Common Mistakes

Mistake 1 — Forgetting to pass type arguments
typescript

const box: Container = { value: "hello" };

// CORRECT — always provide the type argument
const box: Container<string> = { value: "hello" };
Mistake 2 — Generic with only one practical use
typescript

const w: Wrapper<User> = { user: { id: 1 } };

// CORRECT — just define it concretely
interface UserWrapper { user: User }
Mistake 3 — Using type alias when classes need to implement
typescript

type Repository<T> = { findById(id: number): Promise<T> };

interface Repository<T> { findById(id: number): Promise<T>; }

Best Practices

1
Add default type parameters for common cases

If 90% of usages need a specific type, make it the default: interface Result<T = unknown>. Reduces boilerplate without losing flexibility.

2
Document each type parameter with a comment

Especially for multiple params: /** @template T - the entity, ID - the primary key type */ prevents confusion.

3
Prefer interfaces over type aliases for extensible shapes

Generic interfaces can be extended and implemented by classes. If you expect the shape to grow or be implemented, use an interface.

4
Interface methods can have their own type parameters

map<U>(fn: (v: T) => U): Container<U> — the method's U is independent of the interface's T. Use this for fluent/builder patterns.

5
Use generic interfaces to make implementations interchangeable

The power of Repository<T> is that PostgresUserRepo, InMemoryUserRepo, and MockUserRepo all satisfy the same contract.

Interview Questions

EasyQ: What's the difference between a regular interface and a generic interface?

A regular interface describes a fixed shape — every property has a concrete type. A generic interface describes a shape template where one or more property types are parameters filled in at usage time. interface Box { value: string } always holds a string; interface Box<T> { value: T } holds whatever type you specify. Generic interfaces eliminate duplication when you need the same structure for different data types.

MediumQ: Can a class implement a generic interface?

Yes. A class provides concrete types for all type parameters in the implements clause: class UserRepo implements Repository<User>. TypeScript then checks that all methods match the resolved type. The class can also be generic itself: class GenericRepo<T> implements Repository<T>.

MediumQ: What happens if you use a generic interface without passing a type argument?

TypeScript uses the default type parameter if one is defined (e.g. T = unknown). If there's no default, it raises an error requiring you to supply the argument. With strict mode enabled you'll always get an error. Always pass type arguments explicitly — silent unknown propagation defeats the purpose.

HardQ: Can an interface method have its own type parameters independent of the interface's?

Yes. For example: interface Transformer<T> { map<U>(fn: (val: T) => U): Transformer<U>; }. Here T is the interface's type parameter and U is the method's own type parameter. This lets map return a differently-typed container. This pattern appears in fluent interfaces, builder patterns, and functional types like Option or Either monads.

HardQ: When do you choose a generic interface over a generic type alias?

Use a generic interface when the shape needs to be implemented by classes, extended by other interfaces, or benefits from declaration merging. Use a generic type alias when you need to express computed/conditional types, union/intersection shapes, or recursive types — things interfaces can't do. Rule of thumb: data shapes and contracts → interface; transformations and computed types → type alias.

Key Takeaways

  • Generic interfaces describe reusable shape templates where one or more property types vary at usage time.
  • They eliminate interface duplication when the structure is the same but the payload type differs.
  • Classes can implement generic interfaces with concrete types, enabling interchangeable implementations.

▶Generic Types
Intermediate

Simple Explanation

A generic type alias is a named, reusable type transformation — like a function that takes types as input and produces a new type as output. Write it once and use it to create typed variations by plugging in different types.

Technical Explanation

Generic type aliases use the type keyword with one or more type parameters. They can represent anything: object shapes, unions, function signatures, conditional types, and recursive structures. Unlike generic interfaces, they can express unions, intersections, and conditional types — making them the more powerful choice for type-level computations and transformations.

The Problem

In large codebases, you repeat the same type patterns: nullable values, optional wrappers, success/error results. Without generic type aliases you either duplicate code or write T | null inline everywhere — losing the semantic meaning of naming the concept.

typescript
// Without generic types — null patterns repeated everywhere
interface Service {
  getUser(): Promise<User | null>;
  getPost(): Promise<Post | null>;
  getOrder(): Promise<Order | null>;
}

// With generic type alias — named, semantic, reusable
type Maybe<T> = T | null;

interface Service {
  getUser(): Promise<Maybe<User>>;
  getPost(): Promise<Maybe<Post>>;
  getOrder(): Promise<Maybe<Order>>;
}

When to Use Generic Type Aliases

  • Union types with a parameter — type Maybe<T> = T | null, type Result<T> = T | Error
  • Conditional types — type NonNullable<T> = T extends null | undefined ? never : T
  • Function type aliases — type Handler<T> = (event: T) => void
  • Intersection / decoration — type WithId<T> = T & { id: string }
  • Utility type patterns — same approach TypeScript's built-in Partial<T>, Required<T>, Readonly<T> use

When NOT to Use Generic Type Aliases

  • When a class will implement the shape — classes can implement interfaces but not type aliases. Use a generic interface instead.
  • When you need declaration merging — interfaces support merging across multiple declarations; type aliases don't.
  • When the alias adds no clarity — if the name doesn't communicate more than the inline type, skip the alias.
  • When the alias is overly complex — if your type spans 10 lines with nested conditionals, break it into smaller named intermediate types.

How Generic Type Aliases Work Internally

Generic type aliases are eagerly evaluated when used, lazily defined — TypeScript doesn't resolve them until you instantiate them with type arguments. When you write Maybe<User>, TypeScript substitutes T = User and evaluates to User | null.

Type aliases can be recursive because TypeScript allows a type to reference itself in certain positions:

typescript
// Recursive generic type — TypeScript handles this correctly
type Tree<T> = {
  value: T;
  left: Tree<T> | null;
  right: Tree<T> | null;
};

// Infinite recursion — NOT valid: no base case
type Bad<T> = Bad<T>; // ✗ Error

Fully Annotated Syntax

typescript
// Simple union — nullable wrapper
type Maybe<T> = T | null;
//   ^^^^^  ^^^   ^^^^^^^^
//   |      |     type expression (T substituted at usage)
//   |      type parameter
//   alias name

// Generic function type alias
type Predicate<T> = (value: T) => boolean;

// Intersection — adds properties to T
type WithTimestamps<T> = T & { createdAt: Date; updatedAt: Date; };

// Discriminated union with default type parameter
type Result<T, E = string> =
  | { ok: true;  value: T }
  | { ok: false; error: E };

// Usage
const x: Maybe<string> = "hello"; // string | null
const y: Maybe<string> = null;    // also valid
const z: Result<User>  = { ok: true, value: user };

Practical Code Example

typescript
// Reusable generic type aliases

type Maybe<T>       = T | null | undefined;
type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E };
type AsyncResult<T> = Promise<Result<T>>;
type WithId<T>      = T & { id: string };
type Predicate<T>   = (val: T) => boolean;

interface User { name: string; email: string; age: number; }

async function findUser(id: string): AsyncResult<WithId<User>> {
  try {
    const user = { id, name: "Alice", email: "a@b.com", age: 28 };
    return { ok: true, value: user };
  } catch {
    return { ok: false, error: "User not found" };
  }
}

Best Practices

1
Choose type alias over interface for unions, intersections, and conditional types

Interfaces cannot express A | B, A & B, or T extends U ? X : Y. When your type involves any of these, use a type alias.

2
Name aliases semantically, not structurally

Name them after what they mean (Maybe, Result, Paginated), not what they look like (NullableT, ObjectOrError).

3
Add default type parameters for common defaults

type Result<T, E = Error> lets most callers write Result<User> while allowing Result<User, string> when needed.

4
Break deeply nested generics into named intermediate types

When a type expression exceeds ~60 characters, name its components. The extra lines save hours of debugging confusion.

5
Check TypeScript's built-in utility types before rolling your own

Before writing a mapped type manually, check if Partial<T>, Required<T>, Pick<T, K>, Omit<T, K> already does what you need.

Interview Questions

EasyQ: What's the difference between a generic interface and a generic type alias?

Both define named, reusable type shapes with type parameters. Key differences: (1) Only interfaces can be implemented by classes and extended with extends. (2) Only type aliases can express unions (A | B), intersections (A & B), and conditional types. (3) Interfaces support declaration merging; type aliases don't. Use interfaces for class contracts and extensible shapes; type aliases for computed or compositional types.

MediumQ: Can a generic type alias reference itself (be recursive)?

Yes — TypeScript supports recursive type aliases in certain positions. A type can reference itself in property value positions (not directly as the entire type). type Tree<T> = { value: T; children: Tree<T>[] } is valid because Tree<T> appears inside an array, giving TypeScript enough structure to avoid infinite expansion. However, type Bad<T> = Bad<T> is not valid — it has no base case.

MediumQ: What does type WithId<T> = T & { id: string } do?

This creates an intersection type that combines any type T with an additional id: string property. If T is { name: string; age: number }, then WithId<T> is { name: string; age: number; id: string }. It's used to "decorate" any type with extra properties — useful for adding database-assigned fields (ids, timestamps) to domain types that don't include them in their pure form.

HardQ: What is the Result<T, E> pattern and why is it preferred over thrown exceptions in some codebases?

The Result<T, E> pattern returns a discriminated union instead of throwing: type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E }. It's preferred when errors are expected outcomes (not exceptional), when callers must be forced to handle failures, and when you want typed error information instead of catching an untyped unknown. TypeScript's type narrowing on the ok discriminant makes handling both paths ergonomic and safe.

HardQ: How do TypeScript's built-in utility types like Partial<T> work?

Built-in utility types are generic type aliases using mapped types. Partial<T> is defined as type Partial<T> = { [K in keyof T]?: T[K] }. The keyof T produces a union of all keys in T, the in operator maps over them, and ? makes each property optional. This is entirely compile-time — no JavaScript is emitted. You can write your own: type Required<T> = { [K in keyof T]-?: T[K] } where -? removes optionality.

▶Constraints
Advanced

Simple Explanation

A generic constraint is a rule that limits what types are allowed as a type argument — like a job posting that says "must have 5 years of experience." Not just anyone qualifies, but many different people can, as long as they meet the requirement.

Technical Explanation

Generic constraints use the extends keyword to require that a type parameter satisfies a minimum shape. T extends { id: number } means T can be any type as long as it has at least a numeric id property. This allows the function body to safely access those required properties without TypeScript complaining that T might not have them.

The Problem Without Constraints

Without constraints, TypeScript can't let you access any properties on a generic type — because T could be anything, including a primitive that has no properties.

typescript
// Without constraints — TypeScript blocks property access
function getLength<T>(arg: T): number {
  return arg.length; // ✗ Error: Property 'length' does not exist on type 'T'
}

The Solution With Constraints

typescript
interface HasLength { length: number; }

function getLength<T extends HasLength>(arg: T): number {
  return arg.length; // ✓ T is guaranteed to have .length
}

getLength("hello");        // ✓ string has .length = 5
getLength([1, 2, 3]);      // ✓ arrays have .length = 3
getLength({ length: 10 });  // ✓ plain objects with length work too
getLength(42);              // ✗ Error: number has no .length

When to Use Generic Constraints

  • When you access properties on T inside the function — if you use arg.id or any property, T must be constrained to have it.
  • When you want to restrict a generic to specific types — T extends string | number limits T to primitives.
  • When using keyof to get a key of T — K extends keyof T ensures K is a valid key of T.
  • When building type-safe property getters — function get<T, K extends keyof T>(obj: T, key: K): T[K]
  • When building utilities that work on objects with specific shapes — sortable items, entities with IDs, objects with timestamps.

When NOT to Use Generic Constraints

  • Don't constrain to a concrete type — T extends User means T can only be User. At that point just use User directly.
  • Don't over-constrain — only require the properties you actually use. Constraining to a 10-property interface when you use 2 makes the function unnecessarily restrictive.
  • Don't confuse class extends with constraint extends — in generics, extends means "is assignable to", not "inherits from".
  • Don't use constraints as a substitute for proper type narrowing — inside the function body, you might still need typeof checks even with constraints.

How Constraints Work Internally

When TypeScript sees T extends SomeType, it stores this as a constraint on the type variable. At every call site, TypeScript checks if the supplied type argument satisfies the constraint using structural subtyping — the argument type must have at minimum all the properties and methods required by SomeType.

Inside the function body, TypeScript "widens" knowledge about T: it now knows T has everything SomeType has, plus potentially more. It won't let you access properties beyond what the constraint guarantees.

typescript
interface Named { name: string; }

function greet<T extends Named>(person: T): string {
  return `Hello, ${person.name}`; // ✓ name is guaranteed by constraint
  // person.age — ✗ NOT accessible: constraint only guarantees `name`
}

greet({ name: "Alice" });                          // ✓ satisfies Named
greet({ name: "Bob", dept: "Eng", salary: 100000 }); // ✓ extra props ok

}

Best Practices

1
Constrain minimally — only require what you actually use

If you only access .id, constrain to { id: number }, not to a full entity interface. Minimal constraints maximize reusability.

2
Name constraint interfaces to express intent

T extends Identifiable reads better than T extends { id: number } when "having an id" is a concept that appears in multiple places.

3
Master K extends keyof T — it's one of the most used patterns

The pattern getProperty<T, K extends keyof T>(obj: T, key: K): T[K] is foundational. It ensures keys are valid and return types are inferred correctly.

4
Combine constraints with intersection when you need multiple requirements

T extends HasId & HasTimestamps is cleaner than writing a new interface that extends both. For one-off combinations, inline intersection constraints are fine.

5
Acid test: can you replace the generic with a specific type and lose nothing? Remove it.

Unnecessary generics add complexity without benefit. If the function effectively only ever handles one real type, drop the generic.

Interview Questions

EasyQ: What does T extends SomeType mean in a generic constraint?

In a generic constraint, T extends SomeType means "T must be assignable to SomeType" — it must have at minimum all the properties SomeType requires. It does NOT mean T inherits from SomeType in the class inheritance sense. It's purely structural: any type with the right shape satisfies the constraint, regardless of how it was declared. Plain objects, classes, and interfaces can all satisfy the same constraint.

MediumQ: What is the K extends keyof T pattern and when do you use it?

K extends keyof T constrains K to be a union of T's property names. It's used for type-safe property access: function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] ensures key is a real property of obj and the return type automatically matches the value type at that key. This pattern appears in ORM query builders, typed config readers, and any code that manipulates objects by key.

MediumQ: Can you use a class as a generic constraint?

Yes. T extends ClassName means T must be assignable to ClassName — it must have all the class's public properties and methods. TypeScript's structural type system doesn't require T to actually extend the class via inheritance; a plain object or different class with the same public shape would also satisfy the constraint. If you need an actual runtime instance, accept the class type directly rather than using it as a generic constraint.

HardQ: What's the difference between T extends object and T extends {}?

T extends object constrains T to non-primitive types — excludes string, number, boolean, symbol, bigint, null, and undefined. T extends {} (empty object) allows everything that is not null or undefined — including primitives, because they're structurally compatible with {}. Use T extends object when you need an actual object; use T extends Record<string, unknown> for a key-value indexable object. Avoid T extends {} as a "non-null" constraint — use NonNullable<T> instead.

HardQ: How do you write a merge function where TypeScript knows the exact resulting type?

Use constraints and intersection types: function merge<A extends object, B extends object>(a: A, b: B): A & B { return { ...a, ...b } as A & B; }. TypeScript infers the intersection of A and B as the return type, so the caller gets a type that has all properties of both arguments. The as A & B cast is needed internally because TypeScript can't automatically verify that spread produces an intersection — a known limitation. This pattern is used in Object.assign-style utilities and deep merge helpers.
